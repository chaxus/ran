# im 规划：和 deepseek-harness 差在哪里

> 状态：分析与规划，不是承诺。写于 2026-08-22，对照的是同期的
> [deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)。

## 先说结论

差得远，而且**其中一部分差距不该被抹平**。

im 现在是 955 行的浏览器聊天客户端。dsh 是 50 个包组、63 个模型可见工具、168 种会话事件的
本地 agent harness。把两者当成同一类东西来比，得出的结论只会是"什么都缺"，而那份清单没有用。

有用的问题是三个：

1. 哪些差距是**范围不同**造成的，抹平反而是错的；
2. 哪些差距是 im 作为对话客户端**真的缺**的；
3. 哪些差距一旦补上，**ran 组件库会因此变强**——这才是 im 存在的理由。

im 不是产品，它是 ranui/ranuts 的真实消费者。这一路已经证明了它的价值：接一个真 key 抓出
4 个缺陷，跑起来抓出 1 个，在浏览器里看一眼抓出 3 个，全都是测试和 review 没抓到的。规划应该
围绕"下一个能逼出组件库缺口的功能"来排，而不是围绕"dsh 有而我没有"。

> 前四项（工具调用、token 计量与压缩、编辑/重新生成/分支、长对话性能）已完成。每一项下面都
> 记了它逼出的组件库缺口，以及**是怎么发现的**。汇总见[第四节](#四建议顺序)。

## 一、不该抹平的差距

| dsh 有                                             | 为什么 im 不该照做                                                                                                   |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 文件系统、子进程、终端、LSP、沙箱                  | 这些是本地 harness 的地基。浏览器里没有等价物，也不该有——`File System Access API` 只有 Chromium 支持，且语义完全不同 |
| Cordis 插件树、profile/bundle 组合、`isolate` 领域 | 一个可从配置替换每一层的运行时。im 是单页应用，引入这套抽象是数量级的过度设计                                        |
| 226 个包的粒度、capability seam 三角               | 由团队规模和可替换性需求决定。ran 是单人维护                                                                         |
| ACP / JSON-RPC / SDK 三套外部协议                  | dsh 要被别的程序驱动。im 是给人用的界面                                                                              |
| SQLite 全文检索、会话持久化的多后端                | 浏览器端 IndexedDB 就是答案，换后端没有消费者                                                                        |

**把这些列进 backlog 是给自己找活干。** 真正值得从 dsh 学的是**设计判断**，不是功能表——这一路
沉淀进 ranuts/ranui 的 `StreamChunk` 词汇表、投影引擎的发布节奏、渲染意图 union、
"model-visible ⟺ logged" 的对应物，都是判断而不是代码。

## 二、真的缺的

按"补上之后 ran 会不会变强"排序，而不是按 dsh 的重要性排序。

### P0 · 工具调用 —— 已完成

**当初的现状：** `r-tool-card` 已经写好并有 20 个契约测试，但 **im 里没有任何东西会产生工具卡片**。
组件库有了渲染意图 union，却没有真实消费者验证它。

**做完之后：** `client/tools/index.ts` 是工具表，`toolView` 把调用投影成卡片，`runStep` /
`continueWithTools` 组成最多 6 个来回的回路。三个内置工具覆盖了 `generic` 与 `diff` 两种意图
（`terminal` 在浏览器里没有诚实的生产者）。细节见 [README 的"工具调用"一节](./README.md#工具调用)。

**它逼出的组件库缺口**（这正是排第一的理由）：`r-tool-card` 对**所有**结果都用
`white-space: pre` 且不限高。终端输出确实该这样——列是对齐的，换行会毁掉对齐；但一个
`generic` 结果是任意文本，抓一个网页回来就变成一行要横向拖着读的 8000 字符。现在分成两种：
`generic` 换行，`terminal` 不换行，两者都限高 18rem 后滚动。**这个缺陷是在浏览器里看出来的，
20 个契约测试一个都没抓到。**

**缺什么：** `StreamChunk` 的 `tool-call-delta` 已经在词汇表里，累加器也会把参数攒成原始 JSON。
缺的是：请求里带 `tools` 定义、把工具调用投影成会话节点、执行、把结果回填进历史再发一轮。

**为什么排第一：** 它会逼出 `r-tool-card` 的真实缺口（就像真 key 逼出 `usage: null`），
而且它是"聊天客户端"和"agent 界面"之间的那道线。没有它，`r-conversation` 的多节点类型设计
只有一半被用到。

**代价：** 中。工具执行本身在浏览器里可以从最小的一两个开始（比如 `fetch` 一个 URL、算个表达式），
不需要沙箱。

### P0 · token 计量与上下文管理 —— 已完成

**当初的现状：** 用量已经在流里（`snapshot.usage`），**没有任何地方展示或累加**。历史无限增长，
直到某天请求被 provider 以超长拒绝。

**做完之后：** `ranuts/stream` 多了 `estimateTokens` / `addUsage` / `planCompaction`，
ranui 多了 `r-token-meter`，im 的 `client/budget.ts` 负责"一条消息值多少、切口能落在哪里"，
上限由服务端在 `X-IM-Context-Limit` 里报告。细节见 [README 的"Token 计量与压缩"一节](./README.md#token-计量与压缩)。

**它逼出的组件库缺口**（两个，都是在浏览器里看出来的）：

1. **`hidden` 在 19 个组件上是完全失效的。** `[hidden] { display: none }` 是 UA 规则，
   `:host` 上任何作者写的 `display` 都盖过它。于是 `element.hidden = true` 什么也不做，而且
   不报错。现在每个组件都带 `:host([hidden]) { display: none; }`，并由 `verify:design` 的
   第 6 条规则守着——因为这种失败是静默的。
2. **`r-markdown` 会把中文正文吞进裸链接里。** GFM 规定自动链接在空白处结束，这是按英文写的；
   中文里下一个词紧贴着 URL，于是 `https://example.com获取内容` 整段被当成一个地址，链接指向
   一个谁也没写过的 punycode 域名。**错的链接比没有链接更糟。** 现在在**权限部分**（host）
   遇到第一个 CJK 字符就截断——主机名不可能包含这些字符，而路径里可以
   （`https://zh.wikipedia.org/wiki/中文` 是一个完整的 URL，截断它会弄坏本来好的链接）。

**缺什么：** 每轮用量展示、会话累计、上下文接近上限时的提示，以及最基本的压缩（dsh 的 `compaction`
是一个完整的 capability seam；im 需要的只是"把早期若干轮换成一段摘要"）。

**为什么重要：** 这是**唯一一个不做就会真的坏掉**的项。其余都是"少了会遗憾"，这个是"用久了会崩"。

**代价：** 小到中。展示是小的；压缩要决定摘要由谁生成（再调一次模型）和何时触发。

### P1 · 消息编辑、重新生成、分支 —— 已完成

**当初的现状：** 消息发出去就固定了。说错一个字只能重发一遍，历史里留下两条。

**缺什么：** 编辑上一条并从那里重发；对同一问题重新生成；保留多个回答之间切换（dsh 的
`sessions.fork(source, boundary)` 就是这件事的持久化版本）。

**它逼出的组件库能力**（正如预期）：投影引擎多了 `truncate(key)`，`r-conversation` 把它转出去。
按 **`seq` 而不是位置**切，是这次真正学到的东西：一条在切口之前开启、最后一次更新发生在切口
之后的流式消息，必须留在上面——这和节点排序用的是同一条规则，所以"读者在切口之上看到的"
和"留下来的"永远一致。

滚动跟随器也被压到了：截断会让 scrollport 变短，而跟随器把变短读成"读者往上滚了"——不是读者，
是这次操作。编辑/重新生成之后要 `scrollToBottom()`，切换备选之后**不能**（读者正在同一个点比较
两个回答），要用 `captureAnchor` / `restoreAnchor`。两种做法都已经在 ranui 的 CLAUDE.md 里写明。

还发现一个只有在浏览器里才会暴露的约束：行挂在 `r-conversation` 的**闭合** shadow root 里，
页面上的点击监听器在 `composedPath()` 里看不到行内的按钮，所以行必须自己派发 composed 事件。
第一版按类名从事件路径里找按钮，静默地什么都没找到。

### P1 · 长对话的渲染性能 —— 已完成，但**不是**用虚拟滚动

**当初的假设：** "每个节点一行，全部挂在 DOM 里，几百轮之后会明显卡"，所以需要虚拟滚动。

**量出来的结果推翻了这个假设。** 600 条消息的恢复是**一个 5,440 ms 的阻塞任务**——不是因为
DOM 大，而是因为**重放是平方复杂度的**：每个事件都发布一次，每次发布都把整份节点列表交给
订阅者，DOM 订阅者再走一遍全部。修掉之后是 158 ms。

剩下的开销是**布局**：每个流式 delta 改变最后一行的高度，滚动跟随器紧接着读 `scrollHeight`，
于是整列重新布局。3000 条对话里这是每帧 44.9 ms。`content-visibility: auto` +
`contain-intrinsic-size: auto 8rem` 把它降到 8.3 ms，同时把行留在 DOM 里——Ctrl+F、文本选择、
屏幕阅读器都还能看到整段对话。

| 场景                    | 改之前   | 改之后 |
| ----------------------- | -------- | ------ |
| 恢复 600 条             | 5,440 ms | 158 ms |
| 恢复 3000 条            | 1,834 ms | 311 ms |
| 3000 条里流式输出，每帧 | 44.9 ms  | 8.3 ms |

**所以没有实现虚拟滚动，这是有意的。** 它会放弃查找、文本选择、屏幕阅读器对整段对话的可见性，
以及展开的工具卡片在滚走再回来之后的状态——而量出来的那个开销，用上面两条不放弃任何东西就
去掉了。真正需要窗口化的量级（几万行、DOM 节点本身成为内存压力）还没到。

**对组件库的价值**（比预期的更高，但不在预期的地方）：投影引擎多了 `batch(run)` 和
"发布时报告哪些 key 变了"。这两条是任何长转录的消费者都需要的，而且是**先量才发现**的——
review 和单元测试都不会告诉你恢复一段对话花了五秒半。

### P2 · 跨会话搜索

**现状：** 会话列表只能靠标题认。

**缺什么：** 全文检索。IndexedDB 没有 FTS，要么全量扫（几百条会话还能接受），要么自建倒排索引。

### P2 · 模型选择与每会话设置

**现状：** 模型由服务端环境变量固定。前端换不了模型、调不了温度、设不了 system prompt。

**对组件库的价值：** 会用到 `r-select`、`r-dropdown`，可能催生一个 schema 驱动的设置表单
（dsh 的 `client/schema-form` 就是这个思路，我早先分析里点过名）。

### P2 · 导出与分享

markdown / JSON 导出。`ranuts` 已有 `saveFileToDisk`。

### P3 · 键盘优先

`⌘K` 切换会话、`↑` 编辑上一条、`⌘↵` 发送。dsh 的 Web 端有完整的命令面板。

## 三、本地目录连接（单独说）

用户提过这一项，它值得单独一段，因为**它的可行性和其他项不同**。

- 只有 Chromium 系支持 `File System Access API`。Firefox、Safari 没有，且短期不会有。
- 因此它必须是**渐进增强**：没有它，应用完整可用；有它，多一条"把这个目录给模型看"的路径。
- 即便有 API，浏览器给的是**用户显式授权的目录句柄**，和 dsh 的 `ctx.fs` 是两种东西——后者是
  进程对文件系统的完全访问。不要把 im 的目录连接说成"等价于 dsh 的文件能力"。

合理的形态：选择目录 → 列出文件树 → 选若干文件读成文本附件。**读，不写。** 写入需要的信任
远超一个 demo 应该索取的。

## 四、建议顺序

```
1. 工具调用            → 已完成
2. token 计量 + 压缩   → 已完成
3. 编辑 / 重新生成     → 已完成
4. 虚拟滚动            → 已解决，但不是用虚拟滚动（见上）
5. 搜索 / 模型选择 / 导出 / 键盘
6. 本地目录（渐进增强）
```

### 前四项做完之后回头看

**沉淀进组件库的**：`r-token-meter`；投影引擎的 `truncate(key)`、`batch(run)`、
"发布时报告哪些 key 变了"；行上的 `content-visibility`；`ranuts/stream` 的
`estimateTokens` / `addUsage` / `planCompaction`；以及 `verify:design` 的第 6 条规则。

**这四项一共抓出 5 个组件库缺陷，全部是运行或在浏览器里看出来的，没有一个是 review 抓到的**：

| 缺陷                                                       | 怎么发现的   |
| ---------------------------------------------------------- | ------------ |
| `r-tool-card` 对任意文本也用 `white-space: pre` 且不限高   | 在浏览器里看 |
| `hidden` 在 19 个组件上完全失效                            | 在浏览器里看 |
| `r-markdown` 把中文正文吞进裸链接                          | 在浏览器里看 |
| 行在闭合 shadow root 里，页面监听器读不到 `composedPath()` | 在浏览器里点 |
| 恢复一段对话是平方复杂度（600 条 = 5.4 秒）                | 量出来的     |

最后一条尤其值得记下：**它是这四项里唯一一个"先假设、再量、结果假设是错的"的**。规划里
写的是"DOM 里节点太多，需要虚拟滚动"；量出来是重放的算法复杂度。按原计划做会得到一个
更慢、还砍掉了查找和无障碍的实现。

每一项都应当是一个可独立评审的 PR，并且遵循这一路已经成立的做法：

- **组件库拿走可复用的那部分**，im 只留下应用特有的接线；
- **接一个真实 provider 跑一遍**，不要只信测试；
- **在浏览器里看一眼**，5 个缺陷里有 4 个是这么发现的；
- **先量再改**，别照着假设做——第 4 项的假设就是错的；
- 拿不准的判断**写进注释和 PR**，不要留给下一个人重新推导。

## 五、一个提醒

dsh 有 12,293 次提交、30 多个贡献者、两个月。im 有 955 行。

差距的大部分不是"做得不够好"，是**投入量级不同**。规划文档如果读起来像"追平 dsh"，那它已经
错了。这份清单的目标是：**让 ran 的组件库在 agent 界面这个方向上足够扎实**，而 im 是那个负责
把问题挤出来的消费者。
