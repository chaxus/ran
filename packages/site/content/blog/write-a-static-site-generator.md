你现在看的这个页面，是 `packages/site/build/` 里几百行代码生成的。没有 VitePress、没有 Astro、没有 Next。

先说清楚一件事：**大多数情况下你不该自己写这个**。现成方案解决的问题比它看起来多得多。我自己写是因为有个具体目标 —— 需要验证一套东西能不能撑起文档站，而直接在 1,393 个页面的站上试错太贵。小站是试验场。

## 一个 SSG 到底要做什么

拆开来其实只有四件事：

1. **找到内容**，把 markdown 解析成结构化的页面对象
2. **渲染 markdown**，包括代码高亮、标题锚点、目录提取
3. **套进 HTML 骨架**，注入每页各自的 `<head>`
4. **写到磁盘**，加上 sitemap、RSS 这些机器读的文件

难点不在任何一件的实现，在于每一件都有一堆「不做也能跑，但做错了会静默坏掉」的细节。

## 内容发现：URL 就是路径

```ts
content/index.md        → /              首页
content/blog/index.md   → /blog/         归档
content/blog/<slug>.md  → /blog/<slug>   文章
content/<name>.md       → /<name>        普通页
```

这里有个刻意的决定：**一个文件是什么，由它在哪决定，而不是由 frontmatter 里的 `layout:` 字段决定**。少一个字段，就少一个新文章能写错的地方。

输出一律是 `<目录>/index.html`。这样 URL 不带扩展名，canonical、sitemap、站内链接三者天然一致，中间不会夹一次重定向。

::: warning 这是个真踩过的坑
文档站曾经有大约 214 个 canonical 和 sitemap URL 指向 `/foo.html`，而服务器实际服务的是 `/foo`，`.html` 那个形式会 308 跳转过去。页面全都正常显示，没有任何报错 —— 只是 canonical 信号一直指着一个重定向。这种错误不会有人报给你。
:::

## frontmatter：为五个字段引入一个 YAML 解析器？

我没有引 `js-yaml` 或者 `gray-matter`，而是写了个严格的小解析器，只支持这些：

```text
key: 裸文本                → 字符串
key: "带冒号: 的引号文本"   → 字符串
key: [a, b, "c d"]        → 字符串数组
key: true | false         → 布尔
```

其他一律**抛错**，而且报出文件名和行号。

理由不是「省一个依赖」，是**失败模式**。文档站出过一次事故：翻译的人把破折号打成了冒号，`description: 改了什么: 加了这个` 于是变成一个 mapping key，整个构建挂掉，报错信息只点名了六个坏文件里的一个。真正的 YAML 解析器在这种场景下会尽力去猜，而猜错的代价是静默的。

一个只认得四种写法、其余全部大声拒绝的解析器，在这里是更好的工程。

## markdown：为什么不用自己组件库里那个

ranui 里有 `<r-markdown>`。文档站的渲染问题看起来应该用它解决，但[试过之后发现完全不行](/blog/why-r-markdown-cannot-render-this-site) —— 它的净化配置会把所有自定义元素剥成纯文本。那是为流式 AI 输出设计的运行时渲染器，和构建期的可信源码管线是两回事。

所以这里用 `marked` 加 `shiki` 重新搭了一套。几个值得说的点：

**双主题高亮只渲染一次。** shiki 支持同时输出两套主题，每个 token 上挂 `--shiki-light` 和 `--shiki-dark` 两个自定义属性，配合 `defaultColor: false` 不写具体颜色：

```ts
highlighter.codeToHtml(code, {
  lang,
  themes: { light: 'github-light', dark: 'github-dark' },
  defaultColor: false,
});
```

CSS 里各取一边。一份标记同时服务两个主题，切换主题只是重绘，不用重新渲染。

**中文标题的锚点不能音译。** 常见做法是把标题转成 slug，但中文标题走完 `[^a-z0-9-]` 的过滤就只剩空字符串了，整页锚点会全部撞成 `section-1`、`section-2`。所以 CJK 字符原样保留，URL 里做百分号编码 —— 所有有标题链接的中文站都是这么干的。

重名标题加数字后缀。两个 `## 为什么` 是很正常的事，撞了就得区分。

**语言列表是白名单，不认识就抛错。** shiki 有六百多种语法，全加载会把构建从两秒变成四十秒。所以只列站里真正用到的，遇到没列的语言直接报错并说出名字 —— 而不是悄悄按纯文本渲染，让你三个月后才发现某篇文章的代码一直没有高亮。

## 摘要提取：一个很小但很典型的 bug

每页的 `<meta description>` 优先用 frontmatter，没写就取正文第一段。取的时候要把 markdown 标记洗掉：

```ts
.replace(/`([^`]*)`/g, '$1')   // 去掉行内代码的反引号
.replace(/<[^>]+>/g, '')       // 去掉 HTML 标签
```

看起来没问题。但这篇文章的第一段里有 `` `<r-markdown>` `` —— 反引号先被去掉，于是它变成了一个「HTML 标签」，紧接着被第二条规则删掉。摘要变成「给 ranui 写了 之后」，少了整句话的主语。

修法是先把行内代码抽出来占位，洗完标签再放回去。占位符用 U+E000 这种私用区字符，markdown 源码里不可能出现。

这个 bug 的典型之处在于：它不会报错，不会影响页面显示，只有搜索结果里那一行是坏的。我是截图看首页的时候肉眼发现的。

## 骨架：每个文件只装自己那一页

这是整个驱动最重要的一条性质，也是**没有直接用 ranui 自带 SSG 的原因**。

ranui 的 `generateStaticPages()` 是按路由渲染 `<r-router>` 元素树的，而 `<r-route>` 对未匹配的路由只是设 `hidden`，内容仍然留在 DOM 里。对 app shell 这完全正确 —— 壳很小，客户端接管之后就活了。

但对内容站，这意味着**每个 HTML 文件都装着其他所有页面的正文**。三十篇文章，就是三十个内容高度重合的页面，还有随归档线性增长的页面体积。

所以驱动只输出匹配的那一页。现在四个页面各是 2–9 KB，各自只含自己的内容。ranui 在这个站里负责的是组件和跨文档过渡，不负责页面结构。

## 值得吗

对这个站，值得 —— 但理由不是「造轮子好玩」。

它是一次**代价可控的验证**。文档站的 SEO 是多年积累的资产，1,393 个页面、8 种语言，换引擎要押上全部。而在这里，markdown 管线、SSG 驱动、主题层、SEO 装置四块都完整走了一遍，暴露出的问题 —— `<r-markdown>` 用不了、`generateStaticPages` 模型不对、摘要提取有 bug —— 每一个都比它在大站上暴露时便宜几个数量级。

如果这套东西在这里都跑不通，那就是想法本身不成立，代价是一个个人站。
