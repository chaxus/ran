# Ran Design

这份指南写给构建 Web 产品界面的人和编码代理，不限技术栈。它讲一个屏幕该怎么组织、怎么呈现、在输入下怎么表现、怎么运动，以及怎样证明一次改动确实可用。它默认你在一个已有自己令牌和组件的产品里工作：讲的是怎么用好它们，而不是该选哪些。

有三个词分量很重。**MUST** 表示违反后用户能察觉的要求：草稿丢失、焦点消失、文字看不清。违反一条就是缺陷。**SHOULD** 是默认做法；眼前的情况有具体理由时可以偏离，但要说明理由。**MAY** 是可选项。其余内容都是解释。

少数规则由机器检查：`verify:design` 会标出只适配浅色的颜色回退值、裸颜色值、不在尺度上的间距、不用 Pointer Events 的拖拽、失效的 `hidden` 属性，以及若干组件构建错误。这份指南的大部分内容无法静态检查。布局、焦点、动效和对比度只能在真实浏览器里、在真实宽度下、在两种主题中得到验证。

ranui 的[实现适配层](https://github.com/chaxus/ran/blob/main/packages/ranui/docs/adapters/DESIGN.md)把这些方法映射到 ranui 的令牌、层叠层级和组件细节上。本指南本身不绑定任何组件库。

## 原则

**任务优先。** 在挑任何组件之前，先想清楚读者需要看到什么、理解什么、做什么。

**先结构，后装饰。** 用间距、对齐和字重给内容分组；边框、填充和阴影只用于结构本身说不清的边界。

**强调是有预算的。** 颜色、字重、徽标和层级只有少用才有效，所以把它们留给最重要的那一件事。

**状态可见且真实。** 屏幕显示的是真实情况：已选中、处理中、失败、已保存。它不会提前宣布成功，也不会藏起尚未解决的错误。

**输入不会丢失。** 草稿、焦点、光标位置和阅读位置在更新、失败、模式切换和动画之后都还在。

**每条路径都不依赖鼠标。** 宽屏下指针能触达的每个操作，键盘、触摸和窄屏同样能触达。

**动效解释变化，然后让开。** 它短促、可打断、由状态驱动；关掉动效后界面依然能正确阅读。

**盒子要装得下它画出的东西。** 组件的布局盒包含它绘制的全部内容，并在组件加载完成前就预留好，因此不会跳动，也不会溢出。

**验证靠观察，不靠假设。** 有人在真实浏览器里亲眼看到它正常工作，改动才算完成；类型检查通过或截图整齐都不算。

## 从任务开始

动手画之前，在已有的任务记录或设计归属文档里写一份简短说明。小修复只需写清它涉及的决策。“高级感”“现代”“像某某产品”是值得调研的方向，不是规格。

先回答三个问题：

1. **读者一进来需要看到什么？** 这就是主要信息。
2. **还有什么必须一并可见，主要信息才说得通？** 相关对象、上下文、状态。
3. **他们接下来做什么？** 判断、操作，或者继续读。

一个页面只有一个主要模型。辅助信息帮助读者理解或操作它，而不是争夺首屏。完整的 API 返回数据不是页面设计：读者仍然需要一个顺序，先理解对象、它们的状态和关系，再去操作。

然后把说明里适用的部分定下来：

| 决策       | 要定下来的内容                                                   |
| ---------- | ---------------------------------------------------------------- |
| 任务与层级 | 真实内容、主操作、第一阅读焦点，以及哪些可以退后                 |
| 形态       | 哪种布局能回答读者的问题（见下文）                               |
| 状态       | 默认、空、加载、失败、长内容、窄宽度，以及它们的组合             |
| 表面       | 哪些区域真正需要边界，嵌套圆角和内缩之间是什么关系               |
| 动效       | 它解释哪种变化、触发方式和频率、怎么反向，以及减弱动效时显示什么 |
| 验收       | 你会在浏览器里观察到什么，从而证明或否定这次改动                 |

根据读者的问题选择形态，而不是根据数据结构：

| 读者想要……                 | 合适的形态                               |
| -------------------------- | ---------------------------------------- |
| 比较数值或差异             | 表格或差异对比                           |
| 认出并打开某个资源         | 列表；只有图片能标识条目时才用图片网格   |
| 了解某个对象的当前状态     | 分区详情                                 |
| 理解归属或依赖关系         | 树或邻接列表；只有路径重要时才用关系图   |
| 推动工作经过各个阶段       | 步骤流程；移动条目本身就是工作时才用看板 |
| 审计发生了什么、何时、由谁 | 时间线                                   |
| 阅读或讨论连续文本         | 文档或讨论串                             |
| 判断健康状况或发现异常     | 状态总览                                 |
| 一个接一个地处理条目       | 主从视图                                 |

不要把历史事件和未来步骤混为一谈，也不要混淆筛选和看板、正文和字段网格。光有日期不足以用日历。只有当每个视图都服务于一个值得维护的独立任务时，才为同一份数据提供多个视图。

把每类信息放在读者会去找的地方。身份和状态属于标题或摘要，而不是最后一列或某个标签页后面。属性按人的思考方式分组，而不是按 API 字段顺序。证据紧挨着它所支撑的判断。主操作放在标题区，其余操作放在各自对象旁边。反馈出现在触发它的操作旁边。每个事实只有一个权威位置；其他地方显示摘要并链接回去。

默认阅读顺序是：身份；当前状态或异常；主要任务和操作；判断所需的信息；关系、历史和证据；最后是次要信息和不常用的操作。

## 视觉语言

### 层级与强调的预算

先用字体和位置建立层级，再考虑容器。字号升一级、颜色降一级，就能把标题和第一句话变成标题加导语，不需要框，也不需要边框。

把颜色、字重、徽标、填充按钮和阴影当作稀缺资源。处处强调，等于没有强调。每个任务区域最多一个主操作，它应该是最可能的下一步，而不是最具破坏性的那一步。

先用间距、对齐、字重和细线，再考虑框。容器是在声明：里面的内容是一个独立对象。只把它留给真正独立的东西：实时演示、浮层、悬浮面板。代码块、表格、列表行或图库单元格不需要单独的卡片。避免把同一个分组重复包裹两次：面板外框、里面的卡片、行间分割线，再加一层内缩，四条边界都在说“这是一组”，只做了一件事。

每条常驻边界都应有独立的作用。对剩下的每个轮廓、填充或分割线，说出它传达的关系，再检查去掉它后哪里会变得含糊。如果它标出可输入值的区域、独立滚动区、悬浮层或放置目标，就保留。如果标题加间距已经把分组说清楚了，就去掉。把多余的线调淡，它照样多余。

焦点环和选中标记永远不能为了让静止布局显得安静而去掉。

### 颜色与主题

按角色分配颜色，而不是按色相：正文和次要文字、表面、边界、操作和状态。把默认、悬停、按下、禁用和焦点状态作为一个阶梯一起定义，确保它们彼此能区分开。

文字 MUST 在每个支持的主题下，相对它实际所在的背景达到 WCAG AA 对比度。检查的是组合后的结果，而不是孤立的令牌对：状态色底上的文字、图片上的文字、选中控件上的文字、加载状态下的文字，正是实际中对比度出问题的地方。

状态 MUST NOT 只靠颜色表达。要配上图标、文字或形状：检查失败时显示一个叉号和“失败”二字，而不只是一个红点。

当产品同时支持浅色和暗色时，首次绘制 MUST 遵循 `prefers-color-scheme` 或已保存的偏好，不能闪一下错误的主题。两种主题同等重要；每次改动都要在两种主题下检查。

使用产品权威的语义令牌。别名可以提高可读性，但要从这个来源解析；绝不另建一套平行调色板。组件里的裸颜色值意味着它不会跟随主题；只适配浅色的字面量回退值，一旦令牌缺失就会弄坏暗色模式。`verify:design` 会标出这两种情况，还会标出引用了主题从未定义的令牌的回退值（未定义的自定义属性会悄无声息地让整条声明失效）。

品牌强调色视场景而定。用在能标识产品的地方，而不是当作通用高亮。

### 用间距表达关系

间距取自 4px 尺度，每一级都表达一种关系。间距越小，关系越紧密；垂直节奏传达的就只有这个。

| 关系                             | 级别 |
| -------------------------------- | ---- |
| 同一控件的各部分（图标和标签）   | 4px  |
| 紧密相关的控件（一排按钮）       | 8px  |
| 同一内容组内的各行（一个列表项） | 12px |
| 相互独立的组（表单分组）         | 16px |
| 相关的小节                       | 24px |
| 主要区域                         | 32px |

更大的级别（40、64、96px）在关系需要时用来分隔页面级区域。不要自创 20px 或 28px 这样的中间值；正是有限的取值才让节奏看得出来。`verify:design` 会标出写成字面长度而非尺度令牌的间距，以及取自间距尺度而非尺寸尺度的固有尺寸（宽度、高度、字号、圆角）。

几个习惯能让间距保持诚实：

- 先定组件自己的内边距，再定组件之间的间距。
- 每个间距只有一个归属：要么是父元素的 `gap`，要么是子元素的外边距，不能两者都有。重置标题和段落的默认外边距，而不是把它们叠加到父元素的 gap 上。
- 行距、内边距和细线要分开算。16px 内边距加 1px 分割线，不等于一个 17px 的级别。
- 重复的是关系，而不是固定高度。标题到描述、字段到提示、组到组的间距在同级视图之间应保持一致；内容本身仍然可以变长。
- 提示和错误放在它们所解释的字段旁边。
- 不要用装饰性分割线抵消间距的含义。

隐藏的可选内容 MUST 不留下空隙。缺失的描述、隐藏的辅助文字或空的错误位都不应留下空白行。如果组件给宿主元素设置了 `display` 样式，就必须保证标准的 `hidden` 属性依然有效；`verify:design` 会检查这一点。

如果两样东西是同一个对象，所有属性都必须一致。共用边框、共用圆角，中间却有间距，这是自相矛盾。当一个值必须等于另一个值时，用自定义属性命名一次、引用两次，而不是在两处写同一个字面量。

只有内容存在时才预留列。无条件声明的轨道，在没有内容可放的页面上仍然是一列；要以元素存在为条件（例如用 `:has()`）。

### 圆角与嵌套

嵌套圆角只有在内圆角考虑了两个形状之间的内缩时，才显得同心：**内圆角 = 外圆角 − 间距**。16px 圆角的卡片配 8px 内边距，内层面板用 8px 圆角。同一张卡片配 16px 内边距就没有余量可传递；结果不超过 2px 时，两个形状已经看不出同心，内层形状改用自己角色的圆角，或者不用圆角。

![一张圆角 16 的卡片，内缩 8px 处是一块圆角 8 的面板，再内缩 4px 是一个圆角 4 的按钮，三者的圆角弧线共用一个圆心；旁边是一块仍保持圆角 16 的内层面板，导致间隔带从边上的 8px 鼓到拐角处约 11px](./assets/radius-nesting.svg)

调嵌套圆角之前，先问问这个嵌套表面是否需要存在。去掉一个多余的内层框，通常比把它的圆角调到完美更好。

### 对齐

对齐是结构，不是润色。给每条对齐线命名，并列出共用它的元素：标题、正文、列表行、操作，以及替代它们的空状态、加载和错误内容。页面内容对齐线、导航列和嵌套的表单标签对齐线可以有意不同；返回按钮和它的间距可以单独形成一个标题列。关键是这种差异是有意为之。

![贯穿页面的三条垂直对齐线：导航、内容和嵌套的表单标签；标题、行、操作和空状态都落在各自声明的对齐线上](./assets/alignment-spines.svg)

- 测量真正要紧的那一层。按钮外框和段落对齐，不代表按钮文字也对齐，因为内边距会让文字偏移。要拿文字和文字比。
- 计算从共同祖先到可见文字之间的每一层内缩：父元素内边距、嵌套面板内边距、控件自身的内边距和边框。
- 在声明多余内缩的地方把它删掉，而不是用负外边距抵消。
- 嵌套层级结束时，精确回到父级的对齐线上。
- 缺失的可选图标或徽标不应把标签挤出它所在的列；要么预留图标位，要么不管有没有图标都把标签对齐到列上。
- 空状态保持所在区域的对齐线和宽度。多留出的空白绝不能引入第二条左边缘。
- 当两条边或两个间距本应相等时，差一个像素就是缺陷。唯一的容差是对不对称字形（例如播放三角形）的视觉校正，而且它属于图标资源本身，不应靠反复微调页面外边距直到截图看着平衡。

### 密度

密度是每屏的有效信息量，而不是每英寸的控件数。压缩间距提高的是视觉密度，有效密度原地不动；删掉无关字段、把对比放在一处，提高的才是真正的密度。

一个页面最多使用两个相邻的密度级别：宽松用于首次使用和有风险的确认，标准用于大多数列表和详情，紧凑用于专家工作台。内边距和行高可以收紧。正文字号、可见的焦点环和指针目标尺寸 MUST NOT 随密度缩小。

间距、固有尺寸和点击区域解决的是不同问题。小图标可以放在更大的点击目标里。按实际输入方式选择目标范围（粗指针需要更大的目标），而不必放大每个图标。放大后的目标，悬停填充仍然只覆盖控件本身，不能铺到相邻内容上。产品特有的内缩和目标尺寸保留为应用层别名，而不是新增基础值。

### 表面与投影

层级说明的是堆叠关系，而不是重要性。阴影属于浮在内容之上的表面：弹出层、菜单、对话框、通知。不要为了显得重要就给每张卡片加阴影。浮层的阴影在两种主题下都应明显把它托离页面；菜单用卡片级阴影，看起来就像页面的一部分。

产品需要一套有序的堆叠层：页面内容、吸顶界面框架、弹出层和菜单、对话框，最上面是通知。在对话框里打开的菜单 MUST 出现在对话框之上；提示消息 MUST 出现在两者之上。把堆叠值设在真正定位的元素上；外层包裹元素只在它的浮层绘制期间（包括退出过程）才提升层级。

### 文字与图标

选择字体角色，而不是字号。标题、标签、正文、按钮和代码各自有一套协调的字号、字重和行高，并且只有一个归属。字号取自 `rem` 单位的令牌，这样浏览器的文字设置能让它们缩放；正文绝不用无视读者设置的 `px` 固定字号。

- 根据实际文字体系和字体选择易读的行宽。拉丁文正文每行 60–75 个字符是起点；CJK 和混排文字需要单独判断。行宽用 `rem` 声明，不要用 `em`：`em` 随元素自身字号变化，字越大行就越长。
- 限制的是文本元素，而不是整列。表格、代码块、演示或图片保留内容需要的宽度。
- 短标题用 `text-wrap: balance` 平衡换行。标题里不写手动换行，那种换行只适用于写它时的语言。
- 文字 MUST NOT 为了布局整齐而被截断。标题、标签、标识符和导航目标要么重排，要么使用有意义的简写；省略号或提示框绝不能藏起链接去向的唯一线索。
- 会变化的数字使用等宽数字，并为位数变化（从 99 到 100）预留空间。数值多一位时 MUST NOT 被截断。
- 用真实文案检查：较长的译文、回退字体、浏览器缩放。

同一场景里的图标共用一种描边粗细和视觉尺寸，与相伴的文字对齐；没有无障碍名称或可见标签时，图标绝不能单独承载含义。

## 布局

### 页面骨架

大多数产品屏幕属于少数几种外壳：导航栏或侧边栏加内容区；页头加单列；主从视图，列表旁边是选中的条目。根据任务选择外壳，并在整个产品中保持稳定，让读者记住东西在哪。

每个视图只提供一个上下文返回入口。不要同时显示外层的“返回项目”和内层的“返回文件”。详情视图返回它的直接上级，更上层的祖先通过路由层级或面包屑访问；返回上级时，焦点回到读者原先所在的条目。

模态框不是导航层。凡是需要可分享链接、历史记录、并排比较或刷新后保留的内容，都应该有自己的路由。模态框只用于简短确认或单个字段，弹出层或菜单用于临时上下文，展开收起用于逐步展示细节。标签页承载同一对象的同级视图，绝不放互不相关的模块。

### 行宽

连续文本限制在舒适的行宽内；不是连续文本的内容都不受这个限制。宽表格挨着窄段落是对的。一段文字铺满 1600px 的显示器则不对。

### 窄屏

每个屏幕从 320px 起都要可用。在 320–375px 时，每个操作 MUST 仍可触达：控件可以重排或移进溢出菜单，但绝不能把通往某个操作的唯一路径藏起来。在这些宽度下页面 MUST NOT 横向滚动，除非是某个特定区域（宽表格、代码块）自己滚动。

优先使用相对内容的边界（`min()`、`max()`、`clamp()`、容器查询），而不是随意的断点；确实需要断点时复用产品已有的断点。测试时要把窗口缩放到窄布局，而不只是直接在窄宽度下加载：测得的位置在缩放、重排和滚动之后会过时。

### 不发生布局偏移

内容首次出现后不会移动，除非是读者引起的。

- 延迟注册或延迟水合的组件 MUST 在定义之前预留好盒子。未定义的自定义元素会渲染成空的行内盒；用真实组件使用的同一组令牌给它一个占位尺寸（例如 `my-element:not(:defined) { display: block;
min-height: var(--control-height); }`），这样升级时填充的是已经存在的空间。
- 图片、嵌入内容和媒体要声明尺寸或宽高比。
- 状态变化 MUST NOT 改变控件尺寸。按钮文案从“复制”变成“已复制”或显示加载指示时，宽度、高度和焦点环位置保持不变。
- 可能稍后出现的异步状态行，要按说明的用途和范围预留空间，或者出现在不会挤开任何东西的位置。

### 没有脚本和动画也能看见

文字、标题、数值、表单和导航 MUST 在首次绘制时就可读。它们从不等待动画、交叉观察器或脚本才变得可见。脚本失败或开启减弱动效时，内容已经在那里。入场效果只用于文字旁边的装饰性视觉元素，只运行一次，并且在加载时视觉元素已在屏幕上就跳过。回到工作界面时，事实数值立即显示，不再重新滚动计数。

### 绘制不超出自己的盒子

组件的布局盒 MUST 包含它绘制的一切。旋转、扇形展开或偏移的子元素要在组件盒内预留完整的伸展范围；它们绝不溢出到相邻元素上，也绝不在 320–375px 时引起横向滚动。如果装饰必须超出盒子，就让盒子变大，或者有意裁剪装饰。

按正确的轴来定位旋转装饰。`translate()` 里的百分比相对的是元素自身尺寸，而不是容器尺寸，所以 `translate(-50%)` 是让元素以某个点居中，而不是把它移到父元素的一半处。围绕一个有意设定的 `transform-origin` 旋转，然后在浏览器里测量实际绘制范围，不要信任纸面计算。

## 组件与组合

### 先组合，再发明

从产品已有的组件和原生 HTML 元素入手。大多数新需求都是现有部件的组合：一组行、一个展开收起、一个菜单、一个表单。只有组合无法表达所需行为时才新建，并且底层使用原生语义（`button`、`a`、`input`、`dialog`、`details`）。绝不修补组件的私有内部实现；通过它公开的属性、事件、插槽、CSS 变量和 part 来集成。

统一不等于处处是等大的控件或带框的区块。同级组件共享比例、图标粗细、容器方式和动效语言；单靠共用一种颜色无法让它们协调。

### 不靠悬停也能触达操作

发现操作 MUST NOT 依赖悬停。悬停时显示的次要操作，在行内获得键盘焦点时也要显示，并且在触摸屏上要有常驻入口（始终可见，或放在可见的溢出菜单里）。重试、恢复这类关键的恢复操作保持可见。

独立命令在悬停之前就需要一个可辨认的形状：它自己的克制按钮表面或描边，在两种主题下都可见。如果某个可辨认的菜单或列表模式已经表明“这些是操作”，扁平的行也没问题。检查命令面板时，把指针移开再看。

被发现之后，悬停、按下、禁用和焦点状态要保持可区分。禁用控件 MUST NOT 触发操作，悬停时也保持安静。

把破坏性命令和恢复、转移类操作分开。用危险标签和图标表达意图；最强的危险填充色留给确认那一步。破坏性命令要保留确认步骤、取消路径、焦点归还，以及防止重复触发的保护。

### 按钮与链接

链接是离开，按钮是执行。任何改变应用状态的东西 MUST 是 `button`（或具备按钮角色和键盘行为），不管它长什么样。任何跳转到 URL 的东西都是链接，这样才能在新标签页打开和复制。两者在视觉上要能区分；在操作色和正文色接近的主题里，检查行内链接与周围正文的区别。做成按钮样式的链接不加下划线。导航用的箭头只属于会跳转的东西，不属于立即执行的命令。

每个只有图标的控件 MUST 有无障碍名称。

### 浮层

弹出层、菜单、提示框和对话框遵循同一套约定：

- **堆叠。** 浮层遵循产品的层级顺序，因此在对话框里打开的选择框出现在对话框之上，通知位于一切之上。
- **跟随触发元素。** 打开的浮层 MUST 在滚动、缩放和重排时跟随它的触发元素。它绝不会飘离打开它的东西，也绝不会从过时的位置执行退出动画。
- **对话框焦点。** 对话框 MUST 把初始焦点放在自身内部，让 Tab 和 Shift+Tab 留在其中，按 Escape 和取消时关闭，并把焦点还给打开它的元素。基础组件对键盘安全，不代表组合出来的对话框也安全；要测试组合后的结果。
- **Escape。** Escape 只关闭最上层，不会同时触发下面那一层。
- **关闭。** 点击外部会关闭菜单或弹出层，但不会关闭有未保存输入的对话框。

### 选中不是悬停

选中是持久状态，悬停是临时状态。选中 MUST NOT 看起来像悬停。如果当前项使用和悬停相同的填充，界面就让一种外观承担了两种含义，而且指针一移到附近，当前项就从视野中消失了。

悬停反馈是包住所属标签的一块填充，带有自己的内边距。它不会延伸到空白的页头区域或相邻内容上。标题或菜单触发器贴合自身内容；剩余宽度由单独的布局轨道吸收。有意整行选中的行属于另一种角色，并且要明确表现出来。

切换区块的分组标题，悬停时用墨色（文字和图标颜色）响应，而不是用导航目标所用的导航填充。这样“这会展开一个分组”和“这会带你去某处”就能明显区分开。

### 常见的 Web 习惯

| 常见的 Web 习惯                            | 更好的默认做法                                       |
| ------------------------------------------ | ---------------------------------------------------- |
| 只在悬停时出现的行操作                     | 行内获得焦点时可见，触摸时可触达                     |
| 做成链接样式的命令                         | 带克制表面的 `button`；链接只用于导航                |
| 通过动画 `height` 或 `max-height` 打开面板 | 预留或测量盒子；只对 `transform` 和 `opacity` 做动画 |
| 瞬间完成的操作也显示加载指示               | 立即反馈；只在耗时明显时显示进度                     |
| 用红点或绿点作为唯一的状态信号             | 颜色加图标或文字                                     |
| 固定 `px` 字号                             | 基于 `rem` 的字体角色，跟随读者的文字设置            |
| 组件上用 `transition: all`                 | 按属性逐一列出过渡；不包含调色属性                   |
| 用悬停填充标记当前页                       | 独立、持久的选中标记                                 |
| 每个区块都包上卡片和阴影                   | 间距、标题和细线；只有独立对象才用框                 |
| 每个结果都弹一条提示消息                   | 在被操作的对象旁边反馈                               |
| 用模态框承载多步骤任务                     | 一个刷新后仍在、可被链接的路由                       |

## 交互

### 输入与草稿

- **一次触发，一次提交。** 每次触发 MUST 只提交一次；双击或重复按 Enter 不会产生两次写入。
- **输入法组字不是提交。** 输入法正在组字时，Enter MUST NOT 提交（检查 `isComposing`）。只有字段的惯例要求时，Enter 才提交，多行输入照常可用。语音听写只更新文字，从不自行提交。
- **以最新意图为准。** 较旧的响应 MUST NOT 覆盖较新的结果：对“ab”的慢搜索绝不覆盖“abc”的结果，一个文件的预览也绝不出现在另一个文件下。把每个异步结果和发起它的请求绑定，丢弃过时的结果。
- **绝不重建正在输入的输入框。** 搜索响应、流式更新、尺寸变化或状态变化 MUST NOT 替换读者正在输入的元素。焦点、光标、选区和值都保持不动。
- **草稿要保住。** 未发送的输入 MUST 在保存失败、连接中断、模式切换、会话过期以及去设置页再回来之后依然存在。保留的草稿不等于已保存；要说清楚是哪一种。
- **恢复不是重试。** 恢复只把内容填回字段，不提交。重试按原来的范围和目标再次提交，绝不悄悄扩大范围。
- **转义用户文本。** 搜索高亮用文本节点构建，绝不把查询词当作 HTML 插入。

使用原生输入类型和 `autocomplete`，保留平台的编辑快捷键，把标签、前置条件和校验信息放在它们影响的字段旁边。区分“你还没填”和“服务不可用”；提交按钮被禁用而原因不明显时，要解释原因。

### 焦点

每个可交互元素通过键盘获得焦点时 MUST 显示可见的焦点环；一切 MUST 都能用键盘触达和操作：Tab 能到达，Enter 或空格能触发。组件不增加无处可去的 Tab 停留点，也不和内部控件重复。

焦点绝不会意外落回页面 body：

- 折叠包含焦点的区域时，MUST 把焦点还给它的切换按钮。
- 删除获得焦点的条目时，焦点移到下一个有意义的条目或一个稳定的上级控件。
- 关闭浮层时，焦点回到它的触发元素。
- 后台请求完成 MUST NOT 移动焦点。

折叠后的区域仍要说明其中的内容和状态，折叠也绝不能藏起尚未解决的错误。

### 反馈与恢复

成功 MUST 只在操作得到确认之后显示。服务器确认写入后才出现“已保存”；剪贴板调用完成后才出现“已复制”。反馈属于产生它的那次操作：如果复制尚未完成时内容就变了，旧的完成结果不会把新内容标成已复制。

在被操作的对象旁边显示反馈。复制按钮旁边的“已复制”比角落里的提示消息更容易对应起来；提示消息留给超出当前对象的变化，或者不这样就会被错过的反馈。一次失败只给一套连贯的恢复方式，而不是行内错误加提示消息再加横幅。

错误要说明什么失败了、有没有东西被改动、下一步该做什么。“导入在保存前中断了。你选择的文件还在。请重试导入。”只承诺产品能确定的事。不含凭据的诊断信息可以放进展开收起的详情里。

说出已知的阶段（“正在读取文件”“正在写入导出文件”），而不是只显示一个加载指示；播报阶段变化，而不是计时器的每次跳动。只有存在真实的分母时才显示百分比。

取消、重试和完成是不同的结果：

- `Cancel` MUST 在不提交任何内容的情况下离开。
- 发出取消请求不等于确认已取消。在工作真正停止之前显示等待状态；如果客户端只能停止等待，就如实说明。
- 取消不是失败，也不按失败的样式显示。
- 超时并不能证明什么都没发生。重试之前先弄清写入是否已经提交；产品有幂等或去重机制时就用它。
- 只有操作确实能撤回时才提供撤销。

| 情况             | 合适的响应                         | 避免                       |
| ---------------- | ---------------------------------- | -------------------------- |
| 网络中断         | 保留输入和部分输出；网络可达时重试 | 清空表单                   |
| 权限或配置被拒绝 | 说明类别；链接到相关设置           | 自动重试循环               |
| 用户取消         | 标记为已取消；保留可恢复的输出     | 红色失败样式               |
| 上下文已变化     | 把输出标为过时；基于当前数据刷新   | 把旧结果应用到更新的文档上 |

### 流式内容

实时日志和流式回答只在读者位于末尾时才跟随新内容。向上滚动 MUST 暂停跟随；新内容到达时不会移动读者正在看的地方，“跳到最新”控件可以恢复跟随。不要把每个流式字符都播报给辅助技术；只播报完成或有意义的片段。

点击 MUST NOT 依赖平滑滚动结束。滚动到锚点或选中某个条目的点击立即生效；滚动动画只是呈现。在开启减弱动效时测试这些路径：此时平滑滚动是瞬间完成的，竞态问题会暴露出来。

## 动效

动效解释东西从哪里来、到哪里去。高频反馈（悬停、焦点、按下、输入）是即时的，或者几乎即时。变化更大并不自动构成做动画的理由；“没有动效”也是一种有效的设计。

![三条位置随时间变化的曲线：进入在 250–400ms 内减速，停在目标上而不越过；离开在 150–200ms 内加速；第三条曲线标为应避免，它越过目标后又弹回](./assets/motion-curves.svg)

| 用途                           | 时长             | 曲线                         |
| ------------------------------ | ---------------- | ---------------------------- |
| 悬停、焦点、按下反馈           | 0–100ms          | 线性或无                     |
| 元素进入（菜单、面板、对话框） | 250–400ms        | 减速，无回弹                 |
| 元素离开                       | 150–200ms        | 加速                         |
| 相邻元素移动让位               | 与进入的元素相同 | 减速，通过 transform（FLIP） |
| 主题切换                       | 无               | —                            |
| 减弱动效                       | 约 100–150ms     | 只做透明度淡变，不位移       |

规则如下：

- **只对 `transform` 和 `opacity` 做动画。** 绝不通过动画 `height`、`padding`、`margin` 或 `max-height` 来显示或隐藏内容；这些属性每一帧都会让页面重排，过程中还会挤压文字。预留或测量最终的盒子，然后移动并淡入其中。
- **相邻元素靠 transform 移动。** 插入或删除条目时，相邻元素用 FLIP 移动：记录旧位置，应用新布局，再用 transform 从旧位置动画到零。不要让它们跳变，也不要逐帧重排。
- **进入减速，离开加速。** 东西快速到达然后稳住；离开比到达更快。默认不回弹。弹跳或弹簧式回弹只在特定的、俏皮的时刻显式启用，绝不作为库的默认值。
- **可打断、由状态驱动。** 新的意图 MUST 能从当前位置打断或反转正在运行的过渡，不出现跳变、过时的完成回调或重复事件。用状态（反映打开或关闭的类名或属性）驱动过渡，并在该元素的 `transitionend` 或 `animationend` 上结束；绝不用和 CSS 赛跑的 `setTimeout`。退出过程中重新打开，直接反向即可。
- **动画不是输入锁。** 过渡期间，输入、点击和键盘导航照常可用。锦上添花的效果绝不延迟输入或遮住状态。
- **动效保留上下文。** 动画 MUST NOT 清空草稿、移动焦点或改变读者的滚动位置。
- **减弱动效也保留含义。** 在 `prefers-reduced-motion: reduce` 下，动效 MUST NOT 产生位移：保留一个短暂的淡变，或者不要动效，让变化仍然能被注意到，最终状态清晰可见。每个区域都从最终状态开始。
- **主题不做淡变。** 主题切换是瞬间完成的。不要在组件过渡里列出调色属性（`color`、`background-color`、`border-color`、`fill`），也绝不使用 `transition: all`：过渡里的任何调色属性在切换主题时也会淡变，每个组件按自己的速度变化，而页面早已切换完毕。
- **脉冲表示进行中。** 状态脉冲只在活动真正运行时出现。
- **暂停屏幕外的东西。** 装饰性循环在离开视野时停止；采用开销大的效果之前，先用真实内容做性能分析。

交互含义相同的同级组件共享一套动效语言。这并不要求每个组件都有动画。

### 视图过渡

View Transitions API 会把每个具名元素提升到页面之上各自的快照层。被提升的元素在过渡期间会脱离父元素的 `overflow` 裁剪和圆角，因此平时被裁剪的元素会短暂地画到容器外面。只给在新旧两个状态下都完全可见的元素设置 `view-transition-name`，并保证名称在页面内唯一。在开启减弱动效时测试视图过渡，此时它应退化为淡变或者没有动效。

## 文字

### 文字是界面的一部分

增加了决策、约束或后果的文案保留。重复布局已经表达的内容的文案删掉。

- 避免不必要的次级标签和描述；让布局来解释。标题、分组或一目了然的控件，不需要一句话重复它的用途。
- 不要用装饰性徽标或提示框替代删掉的文案。
- 无障碍名称、字段标签、单位、错误和风险提示 MUST 保留。让界面安静下来绝不能删掉它们。保留有用的首次使用引导，并检查删掉文案后任务是否仍然好懂。
- 让上下文承担上下文：在管理后台里写“用户”，而不是“用户管理”。不要在对话框正文里重复它标题提出的问题。
- 按钮说出结果，而不是手势：写“保存”“移动”“删除”，不写“点击保存”或“确定”。上下文没交代对象时，把对象带上：“删除成员”“部署项目”。
- 错误先说发生了什么，再说怎么解决：“构建失败：产物体积超出上限。请减小体积或调高上限。”而不是“操作失败，请重试。”
- 确认信息说明已完成的变化：“项目已删除”，而不是“成功”。
- 用句子式大小写。短标签不加句号；完整句子加句号。
- 需要更多输入才能完成的命令，加一个省略号（…），例如“重命名…”。
- 全大写只用于简短的状态标签、眉标和缩写。
- 译文会变长。为更长的标签留出空间；长标签在同一列内换行，而不是让一排按钮参差不齐。

## 产品场景

这些模式只在任务需要时才适用。普通的表单或搜索页不需要队列、账号连接或版本历史。为其中任何一种选择控件之前，先弄清产品实际支持什么，只提供它能兑现的操作。精致的界面替代不了缺失的服务。

任务、配置、数据源和修订的状态留在它们现有的归属里。视图读取这些状态并派发命令；不要每个视图各自保存一份请求标志。

### 批量与队列

适用于任务运行期间，用户能从继续暂存更多上传、导入或导出中受益的场景。

- 新任务 MUST NOT 悄悄替换或取消正在运行的任务。不支持队列时，保留新的输入并说明限制。
- 在暂停的队列里编辑待处理条目，既不会提交它，也不会恢复队列；重新连接也不会启动排队中的任务，除非用户这样选择。
- 用一行概括队列（“已暂停 · 2 项排队中”）；展开后是行，而不是嵌套的卡片。
- 每一行写明它的条目，只提供支持的操作。明确“立即运行”是等待、抢占还是并行运行。

### 设置与可用性

适用于任务提供服务商、模式、设备或依赖网络的功能的场景。

- 保存配置和检查配置是否可用是两个独立的操作，各有各的结果。
- 区分未配置、已配置但未验证、已验证（附验证时间）、授权已过期、服务不可达和设备离线。保存了的接口地址不等于已授权的账号。
- 更改接口地址、账号或凭据时，清除此前的“已验证”状态；切换模式时，连同过时的状态信息一起隐藏无关字段。
- 切换模式时保留其他模式的配置，重新连接时保留已保存的工作。
- 浏览器的 online 和 offline 事件只是提示，不能证明某个具体接口可用。离线时，只要有数据，就让草稿、预览和本地工作保持可用。

### 账户与外部数据

适用于工作需要读写当前对象之外数据的场景。

- 在授权之前说明会读取什么、写入什么以及写到哪里。只申请需要的权限。
- 账号身份、重新连接和断开连接都能从连接页面访问；断开连接 MUST 停止后续访问。
- 凭据 MUST NOT 出现在 URL、日志或预览中。
- 导入的内容是不可信数据，绝不是要执行的指令。
- 移除数据源影响的是之后的工作，而不是历史记录。
- 权限错误、过时数据和离线副本是不同的状态，要用不同方式显示。为选中的数据源显示来源和新鲜度。

### 结果与修订

适用于结果有自己的身份和去处、不只是一条一闪而过的状态消息的场景。

- 预览绝不写入。应用之前写明目标和范围。
- 如果结果生成之后数据源发生了变化，先比较、变基或重新生成。较新的编辑 MUST NOT 被悄悄覆盖。
- 把复制、导出、比较和应用放在它们作用的结果旁边；只在产品支持时才提供比较、应用或撤销。
- 复制代码复制的是源文本，而不是高亮后的 DOM：制表符、空行和末尾换行都要保留。

## 无障碍检查清单

- [ ] 文字在每个支持的主题下都达到 WCAG AA 对比度，包括状态色底、图片上，以及禁用或加载状态。
- [ ] 没有任何状态只靠颜色表达。
- [ ] 每个可交互元素都能用 Tab 到达，并能用 Enter 或空格操作。
- [ ] 每个可聚焦元素都显示可见的焦点环。
- [ ] 每个只有图标的控件都有无障碍名称；每个字段都有标签。
- [ ] 悬停时显示的内容，在获得焦点时也会显示，并且触摸时可触达。
- [ ] 对话框会限制焦点、按 Escape 关闭，并把焦点还给打开它的元素。
- [ ] 折叠、删除或关闭之后，焦点绝不会落到页面 body 上。
- [ ] 改变状态的控件是按钮；导航是链接。
- [ ] 减弱动效去掉了位移，并且每个最终状态都可见。
- [ ] 字体使用 `rem`，在浏览器 200% 缩放下不截断文字、不横向滚动。
- [ ] 紧凑密度下指针目标保持尺寸；粗指针获得更大的目标。
- [ ] 流式内容不会淹没屏幕阅读器。
- [ ] 拖拽使用 Pointer Events，支持取消，并且只在拖拽表面设置 `touch-action`，让页面其余部分仍能滚动。（`verify:design` 会标出只支持鼠标的拖拽。）
- [ ] 首次绘制使用读者的配色方案。

## 验证一次改动

改动的是人们看到或操作的东西时，验收依据是有人在真实浏览器里观察到的结果。静态检查、类型检查和 `verify:design` 只是前提；它们无法证明焦点归还、最终生效的 CSS 规则、保住的阅读位置，或者过渡看起来怎么样。

**先确定预期，再去看。** 根据设计说明写下预期的几何结果或行为，而不是根据被测的实现。照着代码当前行为抄出来的断言什么也证明不了。

**截取改动前后。** 修复可见缺陷时，先在运行中的产品里复现它，修复后再截取同一状态；看的是带有真实内容和周围界面框架的完整面板，而不是裁出来的单个组件。

**走一遍发生变化的状态。** 默认、悬停、按下、焦点、禁用、加载、空、错误、长内容和大数字，凡是改动涉及的都要走到。包括组合状态：窄宽度下处于错误状态的长译文标签。

**检查各种变体。**

- 两种主题，包括屏幕打开时切换主题。
- 320px 宽度，要通过缩小窗口到达，而不只是直接在该宽度加载。确认没有横向滚动，每个操作都可触达。
- 键盘路径：用 Tab 走过改动部分，用 Enter 和空格触发，打开和关闭浮层，确认焦点落在哪里。
- 涉及悬停时，用触摸或粗指针检查。
- 减弱动效：最终状态可见，没有位移，点击仍然生效。
- 冷缓存下的首次加载，用来发现延迟注册的组件引起的布局偏移。

**测量，别靠目测。** 测量之前，等组件注册完成、字体加载完毕、内容稳定下来；目标缺失或尺寸为零时判定失败。测量真正要紧的那一层：包裹元素、它的内容盒、渲染出的文字（DOM `Range`）和实际的点击目标是不同的测量对象。当断言检查的是布局时，证明它能失败：引入缺陷（只移动标签、加一个重复的外边距），看着检查变红。

**按时间检查动效。** 静止的一帧看不出跳变。先以正常速度观看过渡，再逐帧采样（录屏，或者在每个动画帧读取 `getBoundingClientRect()`）找出不连续的地方。包括反向路径和打断：触发后，在它完成之前再次触发。最终状态、焦点、事件次数和滚动位置要和动画分开检查。

**如实报告。** 绝不声称没有观察到的东西。把三类结果分开：自动化检查（命令输出）、代理自己的视觉检查，以及人的决定。代理的检查不等于用户的验收，测试夹具通过也不等于宿主产品通过。说明哪些路径仍未验证，也不要拿旧截图当作新构建的证据。写一段简短说明就够了：

> 运行环境：构建或提交、视口、主题、语言区域。
> 自动化：命令和结果。
> 代理检查：观察到了什么，以及局限。
> 人的决定：未请求、待定，或实际的决定。
> 未验证：没有检查的内容。

## 给编码智能体的指引

要做：

- 写任何代码之前，先读现有组件、令牌和相邻页面。复用已有的东西；向本产品看齐，而不是向参考产品看齐。
- 动手修改之前，说明任务、主操作、状态归属和键盘路径。
- 在源码或生成的文档里核对公开 API。绝不根据一个看似合理的名字凭空编造属性、事件或令牌。
- 间距、颜色、圆角和字体都取自令牌；对改动涉及的包运行 `verify:design` 和产品自己的检查。
- 为任何稍后加载、注册或出现的东西预留盒子。
- 用 `transform` 和 `opacity` 做动画，在 `transitionend` 上结束，并检查减弱动效。
- 更新时保持正在输入的输入框挂载不动；改为更新它周围的内容。
- 把每个异步结果和产生它的请求绑定。
- 在真实浏览器里打开改动，在两种主题下、320px 和桌面宽度下检查，并用键盘走一遍。
- 报告你观察到的、只是推断的，以及没能检查的内容。

不要做：

- 为了显得完工，给每个区块都包上带阴影的卡片。
- 把行操作藏在悬停后面，或者用链接做改变状态的事。
- 对 `height`、`max-height` 或 `padding` 做动画，使用 `transition: all`，或者用 `setTimeout` 等待过渡结束。
- 在操作得到确认之前就加加载指示、提示消息或成功信息。
- 结果到达时替换用户正在输入的输入框。
- 为了让截图更安静而删掉焦点环、标签或错误文字。
- 加入不在尺度上的间距值、裸颜色值或只适配浅色的回退值。
- 让装饰溢出组件，或在手机上引起横向滚动。
- 把好看的截图当作焦点、键盘、动效或异步行为的证明。
- 把自己的检查标记为“已验收”或“已批准”。

## 评审清单

1. 新读者不用猜，就能认出页面的用途和主操作吗？
2. 强调是否稀缺：每个区域一个主操作，颜色和徽标很少用？
3. 能不能做得更少？有没有哪条边界、哪个选项、标签或状态可以去掉而不削弱任务？
4. 间距是否遵循尺度，在各处表达同样的关系，并且没有幽灵空行？
5. 文字是否对齐到声明的对齐线上，包括嵌套、空状态和错误状态？
6. 嵌套圆角和内缩是否一致，剩下的每条边界是否都有作用？
7. 在 320px 下是否可用，没有横向滚动，每个操作都可触达？
8. 首次加载、状态变化或延迟组件注册时，有没有东西发生偏移？
9. 每个操作是否都能用键盘和触摸触达，焦点可见，焦点归还正确？
10. 选中是否和悬停区分开，每个状态是否都如实显示（没有提前宣布成功）？
11. 草稿、焦点和阅读位置能否在更新、失败和动画之后保住？
12. 动效是否只用 transform 和 opacity，能干净地反向，并在减弱动效下退化为淡变？
13. 在两种主题下是否都能正确阅读，并在真实组合上检查了对比度？
14. 是否在真实浏览器里观察过，报告是否说明了检查了什么、没检查什么？
