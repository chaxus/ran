# Ran Design

面向宿主产品及其现有技术栈的设计方法。通过[任务索引](./INTERFACE_GUIDE.md)只读相关章节。组件库的令牌和 API 细节归各自的实现适配层，不属于这套可移植的方法。

每条规则都有 ID 和等级。**MUST** 违反即为缺陷，并注明验证方式；**SHOULD** 是默认做法，偏离时要说明这次的理由；**MAY** 可选。[规则索引](./RULES.md)列出了所有分级规则及其验证方式。

## 1. 颜色：状态阶梯，而不是调色板

- **D-COLOR-1 · SHOULD** 为内容、表面、边界、操作和状态选定语义角色。
- **D-COLOR-2 · SHOULD** 默认、悬停、按下、禁用和聚焦状态一起定义。
- **D-COLOR-3 · SHOULD** 浅色／暗色取值通过宿主的权威令牌解析，并在实际组合中验证对比度。

品牌强调色视场景而定。

## 2. 间距：有限而有节奏的尺度

- **D-SPACE-1 · SHOULD** 使用宿主已有的间距尺度。
- **D-SPACE-2 · SHOULD** 用紧凑的间距归拢相关部分，用较大的间距分隔任务或区域。
- **D-SPACE-3 · SHOULD** 先定内边距，再定外部间距。
- **D-SPACE-4 · SHOULD** 不评估内容、密度和输入方式，就不要照搬参考产品的尺寸。

## 3. 排版：选角色，不选字号

- **D-TYPE-1 · SHOULD** 为标题、标签、正文、操作和代码选定角色，字号、字重和行高协调一致，每个角色只有一个权威来源。
- **D-TYPE-2 · SHOULD** 用实际文字体系、回退字体度量和长内容来验证。
- **D-TYPE-3 · SHOULD** 先用排版建立层级，再考虑装饰性容器。

## 4. 圆角与层级

- **D-ELEV-1 · SHOULD** 嵌套圆角按实际内缩协调：内圆角 = 外圆角 − 内缩。结果不超过 2px 时，两个形状已经看不出同心，内层形状改用自己角色的圆角，或者不用圆角。

16px 圆角的卡片配 8px 内边距，内层面板用 8px 圆角。同一张卡片配 16px 内边距时没有余量可传递，面板就用它自身角色的圆角。

- **D-ELEV-2 · SHOULD** 层级用来说明浮起的图层，而不是表达重要性；通过宿主的层叠角色实现，并对照周围界面框架检查浮层。

## 5. 动效：能不用就不用

下面的时长只是起步参考。

- **D-MOTION-1 · SHOULD** 使用宿主系统的动效令牌，并在实际任务中验证频率、连续性和减弱动效。

| 时长   | 用途                                           |
| ------ | ---------------------------------------------- |
| 0ms    | 高频的悬停、聚焦和键盘反馈；用户已经理解的变化 |
| ~150ms | 可选、有目的的小动效，不是强制的悬停延迟       |
| ~200ms | 能说明图层变化时，用于菜单／弹出层             |
| ~300ms | 有助于用户定位时，用于对话框                   |

**原则：** 目的和频率决定动效值不值得占用时间。

- **D-MOTION-2 · SHOULD** 重复交互默认即时反馈；变化较大本身不是加动画的理由。
- **D-MOTION-3 · SHOULD** 有目的的动效使用现有令牌，保持短促、可打断。减弱动效由 D-MOTION-10 和 D-ACCESS-5 分级。

### 功能性动效契约

- **D-MOTION-4 · SHOULD** 先明确触发条件、状态变化和终点，再选效果。
- **D-MOTION-5 · MUST** 动效不影响无关内容、草稿和阅读位置。_Proof: recording_
- **D-MOTION-6 · SHOULD** 交互含义相同的兄弟组件共用一套动效语言；一致不等于每个组件都要动。
- **D-MOTION-7 · MUST** 使用动效时，新的意图可以从当前画面打断或反转它，不跳变、不出现过期的完成状态、不重复触发。_Proof: recording_
- **D-MOTION-8 · MUST** 反馈保持即时；动画不是输入锁。_Proof: recording_
- **D-MOTION-9 · SHOULD** 插入／移除时，避免肉眼可见地挤压文字，或让正在退出的控件划过仍可用的操作；协调透明度和布局，让结果始终可读。
- **D-MOTION-10 · MUST** 减弱动效时仍保留可见、可理解的最终状态。_Proof: browser_
- **D-MOTION-11 · MAY** 可以用弹簧动画，不一定要回弹过冲。

示例和边界见可选的[组件工艺研究](./REFERENCE_RESEARCH.md#component-craft-设计垂点--wxaddesign)，验证方式见[时间维度验收](./ACCEPTANCE.md#review-motion-over-time)。

- **D-MOTION-12 · SHOULD** 主题配色切换要整体一致地落定。避免隐式的配色渐变或 `transition: all`；只有宿主有意设计并验证了协调效果的地方，才显式开启。
- **D-MOTION-13 · MUST** 回到工作界面时，事实数值和可读内容立即显示，不做数字滚动动画。_Proof: browser_
- **D-MOTION-16 · SHOULD** 不要每次回到工作界面都重播装饰性的标题入场。
- **D-MOTION-17 · SHOULD** 按区域承载的内容从下表选择入场动效。错开入场只在一个区域内按阅读顺序进行，不跨整页。

| 区域内容                                 | 入场                                                       | 之后                                             |
| ---------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------ |
| 文字、标题、数值、表单、导航、行动号召   | 无：首帧即呈现（D-MOTION-13）                              | 无                                               |
| 文字旁的装饰性视觉：图标组、示意图、草图 | 仅用 transform，首次滚入视口时播放一次；加载时已可见则不播 | 在屏幕上时可以运行说明性的循环动画（D-CRAFT-19） |
| 产品样机或在线演示                       | 内容不做入场；加载演示可以动（D-MOTION-14）                | 由读者自己的交互驱动                             |
| 状态指示器                               | 无                                                         | 只在活动进行中脉动（D-MOTION-15）                |

开启减弱动效时，每个区域都直接处于最终状态（D-MOTION-10）。

- **D-MOTION-14 · MAY** 加载演示可以通过运动来演示加载。
- **D-MOTION-15 · MUST** 状态脉动只在活动进行中出现。_Proof: review_

## 6. 文案：文案也是系统的一部分

- **D-COPY-1 · SHOULD** 按钮写明结果。上下文没交代对象时带上对象：「部署项目」「删除成员」。在对象或对话框已经明确的地方，「保存」或「删除」就够了；避免笼统的「确定」。见[按上下文措辞](#words-are-part-of-the-interface)。
- **D-COPY-2 · SHOULD** 错误信息先说**发生了什么**，再说**怎么解决**。✅「构建失败：包体积超出上限。请减小体积或调高上限。」❌「操作失败，请重试。」
- **D-COPY-3 · SHOULD** 确认信息和 toast 说明完成了什么**变化**。✅「项目已删除」。❌「操作成功」。
- **D-COPY-4 · MUST** 操作确认完成后才显示完成反馈。_Proof: unit, browser_
- **D-COPY-5 · SHOULD** 写具体；每句话都应减少猜测，而不是增加猜测。

## 7. 无障碍：系统为所有人服务

- **D-ACCESS-1 · MUST** 文字与背景保持足够对比度（**WCAG AA**）。 _Proof: browser_
- **D-ACCESS-2 · MUST** 不能只靠颜色表达状态，要配合图标或文字（例如 ✓／✕ 标签，而不只是绿／红）。_Proof: review_
- **D-ACCESS-3 · MUST** 每个可交互元素都有与所在表面相称的**可见聚焦环**；不要为了「干净」去掉它。_Proof: browser_
- **D-ACCESS-4 · MUST** **完整的键盘导航**：没有只能用鼠标完成的操作。_Proof: browser_
- **D-ACCESS-5 · MUST** 遵循 `prefers-reduced-motion`。 _Proof: browser_
- **D-ACCESS-6 · MUST** 宿主同时支持两种配色方案时，首次渲染跟随 `prefers-color-scheme`。 _Proof: browser_

## 8. 输入与视口：移动端和桌面端都要顾及

- **D-INPUT-1 · MUST** 在窄屏和宽屏下都支持鼠标、键盘和触摸。_Proof: browser_
- **D-INPUT-2 · MUST** 控件要重新排布，而不是把通往某个操作的唯一入口藏起来。_Proof: browser_
- **D-INPUT-3 · MUST** 悬停提示有对应的点击／轻触替代方式。_Proof: browser_
- **D-INPUT-4 · MUST** 拖拽使用 Pointer Events，包括取消。_Proof: browser_
- **D-INPUT-5 · MUST** `touch-action` 只作用于实际的拖拽表面，并配合真实的事件处理；其他地方的正常滚动不受影响。_Proof: browser_
- **D-INPUT-6 · SHOULD** 优先用相对内容／视口的边界（`min()`、`max()`、`clamp()`），而不是随意设定的断点。
- **D-INPUT-7 · SHOULD** 使用宿主已有的断点；只有重复出现需求时，才引入有充分理由的共享角色。

测量得到的位置在窗口缩放、容器重排或滚动之后就会过期。

- **D-INPUT-8 · SHOULD** 测试从宽布局缩放到窄布局的过程，而不只是直接在窄布局下加载。
- **D-INPUT-9 · MUST** 浮层打开期间，位置始终跟随触发元素。_Proof: browser_

生命周期机制由宿主负责；[ranui 工程规范](https://github.com/chaxus/ran/blob/main/packages/ranui/docs/CODING.md#3-state-and-ownership)是其中一种实现适配。

- **D-INPUT-10 · SHOULD** 在受影响的地方测试真实的指针／触摸手势、悬停的替代路径和键盘路径；检查两种配色方案并不能说明输入方式已经对齐。

## 9. 组合：看整页，而不是单个组件

- **D-COMP-1 · SHOULD** 先按 §10 选定页面结构，再用下面的规则组合组件。

### 跨组件、跨页面的风格一致性

- **D-COMP-2 · SHOULD** 动手实现之前，在现有任务记录或产品设计归属处写一份简短的设计简报。沿用现有体系；小修复只需写受影响的决定。简报逐项落定下表中适用的决定（D-COMP-2）。

「高级」「现代」或「像 Claude 那样」是需要调研的方向，不是可以直接实现的规格。

| 决定       | 简报要落定的内容                                                                         |
| ---------- | ---------------------------------------------------------------------------------------- |
| 任务与层级 | 真实内容、主操作和首个阅读焦点；哪些可以弱化或去掉。                                     |
| 比例       | 用宿主令牌确定排版角色／行高、文字行宽、控件密度、图标粗细和对齐线。                     |
| 表面语言   | 哪些区域需要容器、嵌套圆角／内缩关系、语义强调色和层级角色。                             |
| 状态组合   | 有代表性的默认态，以及长内容、等待／失败和窄屏输入路径；包括组合状态。                   |
| 动效       | 它说明的状态变化、触发条件和频率、打断／反转行为和减弱动效后的结果；「无」也是有效答案。 |
| 参考决定   | 用到参考时，链接其出处、采纳的原则，以及宿主任务需要的调整。                             |
| 验收       | 可观察的结果，以及能证明或否定它的实际视图／录屏。                                       |

- **D-COMP-4 · SHOULD** 在兄弟组件和文档框架之间复用这份简报；按任务调整强调重点。

统一不意味着控件处处等大，也不意味着每个区块都要装进框里。

- **D-COMP-5 · SHOULD** 表现力强的演示要与周围的文档框架明显区分。
- **D-COMP-6 · SHOULD** 改变视觉方向之前先更新简报；不要为了给评审没通过的实现找理由，悄悄改写规范。
- **D-COMP-7 · SHOULD** 加动画之前，先用不同的真实内容对比一张有代表性的组合静态画面，再以正常速度检查状态变化和返回路径。

只靠共用一种颜色，调和不了不一致的比例、图标粗细、容器或动效。

- **D-COMP-8 · SHOULD** 某个示例看起来像从别的产品搬来时，在它所属的令牌／组件／样式处修正这层关系，而不是加一个页面专用补丁。
- **D-COMP-9 · SHOULD** 参考观察和验证边界放在可选的[研究索引](./REFERENCE_RESEARCH.md#style-coherence-and-transition-research)里。

### 先有结构，再谈容器

- **D-BOX-1 · SHOULD** **先用间距、对齐、字重和细线，最后才用框。**

容器在宣告：里面的内容是一个独立对象。多数区域只需要背景、一条细线和有意安排的间距，仅此而已。

- **D-BOX-2 · SHOULD** 框只留给**真正独立的对象**：在线演示舞台、浮层、悬浮面板。代码块、表格、列表行、上一页／下一页链接、图库中的单元格都不需要。
- **D-BOX-3 · SHOULD** **避免多余的嵌套容器和双重内边距。** 带内边距的面板里放卡片，不需要再加一层装饰框或内缩。
- **D-BOX-4 · SHOULD** 功能上必需的嵌套控件或表面要保留，并按实际内缩协调圆角；仅仅是「包含关系」不构成加框的理由。
- **D-BOX-5 · SHOULD** **每条常驻边界都要有独立的作用。** 先用标题、对齐和邻近关系给内容分组。只有这些结构仍让某个真实边界不清楚时，才加边框、表面填充或层级。
- **D-BOX-6 · SHOULD** 不要同时用面板框、嵌套卡片、行分隔线和又一层内缩重复表达同一个分组。

淡色线条依然是多出来的层级；降低对比度或缩短线条，多余的包围仍然多余。

下表是 D-BOX-5 和 D-BOX-8 的具体应用。

- **D-BOX-8 · MUST** 保留键盘焦点和常驻的选中提示；不要为了让静止布局更安静而去掉它们。_Proof: browser_

| 边界             | 在表达这些时保留                     | 只是重复时去掉                                 |
| ---------------- | ------------------------------------ | ---------------------------------------------- |
| 输入框／控件边框 | 可以输入值或做出选择的位置           | 包在本身已清楚可辨的命令外面的装饰层           |
| 区域边框或分隔线 | 独立视口、缩放边界或任务的明显切换   | 标题和间距已经清楚表达了同一分组               |
| 嵌套表面         | 独立的浮层、预览、放置目标或交互边界 | 已确立的设置面板里又套一层容器                 |
| 焦点／选中轮廓   | 键盘焦点或常驻的选中状态             | 即使去掉后静止布局更安静，也要保留这个状态提示 |

- **D-BOX-9 · SHOULD** 检查整个面板或整页，而不只是裁出来的那一组。对每一条留下的稳定轮廓、填充或分隔线，说出它表达的关系或交互，并检查去掉后哪里会变得含糊。

框是可选的；能触达、可辨认的控件不是。

### 强调是有预算的

**颜色、字重、徽标、填充和层级都是稀缺资源。** 什么都强调，就什么都不显得重要。

- **D-COMP-10 · SHOULD** 先用结构和邻近关系确立优先级，把强调留给真正值得的那一个。

**层级说明的是层叠关系，不是重要程度。**

- **D-ELEV-3 · SHOULD** 阴影只给真正浮在内容之上的表面：弹出层、菜单、对话框、通知。不要给每张卡片都加阴影。

### 间距本身就有含义

§2 的尺度不只是节奏，每一档都在表达一种关系。

按间距*表达的含义*选档位（D-SPACE-2）：

| 关系             | 相对间距       |
| ---------------- | -------------- |
| 同一控件的各部分 | 最紧的有意间距 |
| 紧密相关的控件   | 紧凑的组内间距 |
| 同一内容组       | 组内节奏       |
| 不同的组         | 更大的分隔     |
| 主要区域边界     | 最强的有意分隔 |

**先内后外：** 组件自身的内边距先于组件之间的间距确定（D-SPACE-3）。**间距越小，关系越紧密**：这是纵向节奏唯一要传达的信息。

- **D-SPACE-6 · SHOULD** 不要用装饰性分隔线抵消间距已经表达的关系。

### 兄弟视图之间的纵向节奏

- **D-SPACE-7 · SHOULD** 重复的是关系，不是固定高度。标题／描述、字段／提示、组和区域之间的间距，按各自的关系从宿主尺度中选取。

这些是组合层面的决定，不是通用的组件尺寸。

- **D-SPACE-8 · SHOULD** 让译文自然变长；缺少描述时不留空行。
- **D-SPACE-9 · SHOULD** 每个间距只有一个归属：父级堆叠，或子元素显式的外边距。重置局部标题／段落自带的外边距，而不是把它们叠加到父级间距上。
- **D-SPACE-10 · SHOULD** 把控件自带的内边距、外边距折叠和行内基线空间都算进去；不要用 transform 或缩小字号来补偿。
- **D-SPACE-11 · SHOULD** 提示放在它所解释的字段／操作旁边。
- **D-SPACE-12 · MUST** 隐藏的辅助信息不留下意外的空隙。_Proof: browser_
- **D-SPACE-16 · SHOULD** 为异步状态预留的行要有明确的用途和尺寸边界。等内容落定后测量两个方向；[ACCEPTANCE](./ACCEPTANCE.md) 将其分级为 V-PROOF-6。

`next.top - previous.bottom` 测的是外框之间的间隔，不是字形／行盒的空间。

- **D-SPACE-14 · SHOULD** 行距、内边距和细线要分开算：16px 内边距加 1px 分隔线，不等于一个 17px 的间距令牌。
- **D-SPACE-15 · SHOULD** 使用独立的预期值，并测试换行、缩放、辅助信息／错误的显隐和相关密度。

双重外边距、幽灵行和仅文字偏移的落定检查与变异检查，由 [ACCEPTANCE](./ACCEPTANCE.md#browser-proof) 负责。

### 行宽约束的是文字，不是栏

- **D-TYPE-4 · SHOULD** **按实际文字体系和字体选择易读的行宽。**

对拉丁文字的正文，每行 60–75 个字符是起步参考，不是适用于所有书写系统的通用范围。

- **D-TYPE-5 · SHOULD** 在支持的宽度、缩放级别和回退字体下检查真实文本；CJK 和混排文字需要单独判断。

[WCAG 视觉呈现](https://www.w3.org/WAI/WCAG22/Understanding/visual-presentation.html)在其 AAA 级准则中也单独区分了 CJK；这不是组件库必须采用的默认值。

- **D-TYPE-6 · SHOULD** 让表格、代码块、演示舞台或图片保留内容所需的宽度。限制的是文字元素，不是承载它们的栏。
- **D-TYPE-7 · SHOULD** **行宽用 `rem` 声明，不用 `em`。**

`em` 相对元素自身的字号计算，字越大行越长，恰好反了。

- **D-TYPE-8 · SHOULD** **先用排版建立层级，再考虑加框。**

字号提一档、颜色降一档，标题和首句就成了标题加导语，不需要新容器，也不需要新边框。

### 布局说两者是一个对象，间距就得同意

**共用边框、共用圆角，中间却留着间距，这是自相矛盾。**

- **D-ALIGN-1 · SHOULD** 先决定这些元素是一个对象还是两个，再让每个属性都表达同一件事。
- **D-ALIGN-2 · SHOULD** **一个值必须等于另一个值时，给它起名字。** 子元素需要减掉的间距不应在两处各写一个字面量，而是一个被引用两次的自定义属性。

### 只有内容存在时才预留栏

**无条件声明的栏依然是栏，哪怕某些页面根本没东西可放。**

- **D-ALIGN-3 · SHOULD** 让轨道以元素实际存在为条件（`:has()`），而不是以你假定意味着它存在的页面类型为条件。

### 对齐是结构，不是润色

- **D-ALIGN-4 · SHOULD** **为每条对齐线命名，并说明它对齐的几何。** 说明哪些兄弟元素共用同一条线；包括标题栏、正文、行、操作，以及空／加载／错误状态的内容。

页面内容对齐线、导航栏和嵌套的表单标签对齐线可以有意不同。

- **D-ALIGN-5 · SHOULD** 返回按钮加间距可能形成单独的标题栏：不要默认那个标题与正文对齐。
- **D-ALIGN-6 · MUST** 缺少可选的图标或徽标时，标签不会移出声明的栏。_Proof: browser_
- **D-ALIGN-7 · SHOULD** 嵌套层级结束时，准确回到父级的对齐线。比较的盒子要选对。即使数值碰巧相同，下表各项也是不同的测量；测量缺陷所在的那一层由 [ACCEPTANCE](./ACCEPTANCE.md) 分级为 V-PROOF-10。

| 几何     | 测量什么                                                       |
| -------- | -------------------------------------------------------------- |
| 外框     | 包裹元素／宿主元素的边框盒，来自 `getBoundingClientRect()`     |
| 内容     | 去掉实际边框和内边距后的内边缘，包括嵌套的包裹层               |
| 文字     | 包住渲染后标签文本节点的 DOM `Range`；换行时用首行／末行的矩形 |
| 图标视口 | SVG／viewBox 或图片的盒子；实际绘制的字形墨迹在其中可能不对称  |
| 点击区域 | 实际的事件目标及其悬停／聚焦表面；验证靠近边缘的点             |

按钮外框与段落对齐，不能证明按钮文字也对齐：外框不动时，内边距仍可能让标签偏移。`Range` 给出的是排版几何，不是精确的字形墨迹。

- **D-ALIGN-9 · SHOULD** 字形的视觉校正单独检查。对 Web Components，通过受支持的测试接口测量宿主元素、文档化的 shadow part 和插槽文本。这部分由 [ACCEPTANCE](./ACCEPTANCE.md) 的 V-PROOF-11 负责，包括禁止在生产代码中查询 shadow DOM，以及不要假定文档级 CSS 能穿过边界。
- **D-ALIGN-11 · SHOULD** **标题栏命令的点击区域与布局填充分开。** 标题／菜单触发器按内容加上有意的内边距收紧，受可用宽度约束。剩余空间交给单独的 flex／grid 轨道。
- **D-ALIGN-12 · SHOULD** 为长译文定义截断／换行方式，以及相邻操作的行为。
- **D-ALIGN-13 · MUST** 标题触发器的点击区域不覆盖标题栏中空闲的空间（例如给标题按钮加 `flex: 1`），除非适用 D-ALIGN-14。_Proof: browser_
- **D-ALIGN-14 · SHOULD** 有意让整行宽度都可选中的行是另一种角色；要明确记录这个契约。
- **D-ALIGN-15 · MAY** 粗指针下的目标可以更大。
- **D-ALIGN-22 · SHOULD** 放大后的目标，其悬停填充只覆盖控件自身的内容，不延伸到无关内容上。
- **D-ALIGN-16 · SHOULD** **从共同祖先到可见文字，把每一层内缩都算进去。** 父级内边距、嵌套面板内边距、控件自身的内边距、边框和导航栏都会产生影响。
- **D-ALIGN-17 · SHOULD** 多余的内缩在其归属处去掉，而不是用一个没有解释的负外边距抵消。
- **D-ALIGN-18 · SHOULD** 空状态保留所在区域的内容对齐线和宽度；多留的呼吸空间不能引入第二条左边缘，也不能让紧凑的操作撑满整个区域。
- **D-ALIGN-19 · SHOULD** 产品特有的内缩和目标尺寸作为应用别名保留，不要变成新的基础值或通用组件默认值。
- **D-ALIGN-20 · SHOULD** **两条布局边缘或两个间距本应相等时，差一像素就是缺陷。** 字形视觉校正（D-ALIGN-21）是唯一的容差。
- **D-ALIGN-21 · SHOULD** 不对称字形的视觉校正作为单独的、有文档记录的资源／组件决定，在支持的尺寸下复用，同时兄弟间距、基线和对齐线保持精确。

视觉校正不是让你一点点挪页面边距、直到截图看起来平衡的许可。

### 选中、链接以及其他语义上的谎言

- **D-SEM-1 · MUST** **选中是常驻状态，看起来绝不能像悬停。** _Proof: browser_

悬停是临时的；如果当前项用的是和悬停一样的填充，界面就给同一种外观起了两个名字。

- **D-SEM-2 · MUST** **操作和链接这两种角色要能区分。** _Proof: browser_
- **D-SEM-3 · SHOULD** 对照周围正文检查行内链接，包括操作色和正文色碰巧相同的主题。

**链接带你离开，按钮执行动作。**

- **D-SEM-4 · MUST** 凡是改变应用状态的都是按钮，不管它长什么样。_Proof: review, browser_
- **D-SEM-5 · SHOULD** 按钮样式的链接不带下划线。

### 受限面板中的命令层级

- **D-CMD-1 · SHOULD** **去掉多余的分组包围，但不抹掉控件的可操作提示。**

在设置面板里，标题、对齐和邻近关系负责分组；但仅靠它们，图标和标签看起来并不可点击。

- **D-CMD-2 · SHOULD** 当可识别的菜单／列表模式已经表达了操作含义时，使用扁平行；不要在所有场景都强求扁平行。
- **D-CMD-3 · SHOULD** 需要的话，给独立命令一个克制的按钮表面或功能性描边，在每个支持的主题下悬停之前就可见。
- **D-CMD-4 · SHOULD** 让按钮自己的形状标识其目标；外围卡片、低调的整组底色和行分隔线仍要通过独立边界的检验（D-BOX-5）。
- **D-CMD-5 · MUST** 首次发现不能只依赖悬停、指针光标、动词标签或键盘焦点。_Proof: browser_
- **D-CMD-6 · SHOULD** 把指针移开，检查静止状态下的整个面板，包括触屏使用的情况。
- **D-CMD-7 · MUST** 控件被发现之后，悬停、按下、禁用和键盘焦点仍能相互区分。_Proof: browser_
- **D-CMD-8 · SHOULD** 较长的译文标签在同一命令栏内换行，而不是排成参差不齐的横向按钮堆。
- **D-CMD-9 · MUST** 不要给立即执行的命令加导航箭头。_Proof: review_
- **D-CMD-10 · SHOULD** 声明哪些可见栏与相邻的勾选框或控件共用：测量图标／勾选框边缘和文字 Range，而不只是按钮矩形或命令组内部的对齐。
- **D-CMD-11 · MAY** 为了保持这些栏，点击目标可以延伸到它所属的边距里；要说明这处延伸。
- **D-CMD-12 · MUST** 延伸后的点击目标不超出所在面板，不与其他目标重叠，焦点保持可见。_Proof: browser_
- **D-CMD-13 · SHOULD** 破坏性命令与恢复、转移类操作分开放。
- **D-CMD-14 · SHOULD** 用危险标签和图标表达意图，不要给每个静止的命令都加大面积红色描边；最强的危险色填充留给明确的确认步骤。
- **D-CMD-15 · MUST** 破坏性命令保留确认、取消、焦点归还和忙碌防护。_Proof: browser_
- **D-CMD-16 · SHOULD** 按静止状态验收命令面板，而不只看悬停状态。

验收覆盖：静止时的可发现性、声明的共用栏、整个面板的边界层级、目标边界、标签裁切、对比度和交互状态。

- **D-CMD-17 · SHOULD** 也要检查实际渲染：自动化的表面差异检查能发现看不见的控件填充，但证明不了用户认得出这个操作。
- **D-CMD-18 · SHOULD** 复用基础角色和粗指针输入的目标尺寸要求；这份指南不改动任何组件默认值。

### 一个产品，一套令牌

- **D-TOKEN-1 · SHOULD** 使用产品的权威语义令牌。别名可以提高可读性，但要从这个来源解析，而不是另起一套相互竞争的调色板。
- **D-TOKEN-2 · SHOULD** 第三方组件通过其支持的主题 API 协调，并验证组合后的结果。

### 密度跟随控件角色

间距、固有尺寸和点击目标解决的是不同问题。一个小图标可以有更大的原生按钮目标。

- **D-TOKEN-3 · SHOULD** 测量实际的点击边界、焦点和相邻间距。
- **D-TOKEN-4 · SHOULD** 重复使用的宿主别名从基础令牌派生，而不是把某个应用的尺寸复制到整个组件库。
- **D-TOKEN-5 · SHOULD** 按实际输入方式选择目标边界，不要放大每个图标，也不要为隐藏的控件预留空间。使用受支持的公开主题 API。
- **D-TOKEN-6 · MUST** 纯图标控件要有无障碍名称。_Proof: browser_
- **D-TOKEN-7 · SHOULD** 把合理的视口、细线、插画和视觉几何例外写进文档。

### 用证据评判工艺

精致来自任务清晰，而不是一套预设的卡片、模糊或入场动画。

- **D-CRAFT-1 · SHOULD** 用真实的对象、文案和状态确定有意识的视觉方向；一个空洞的通用外壳证明不了产品质量。

工作型界面要承受持续阅读和高频操作；营销页可能需要不同的组合方式。

- **D-CRAFT-2 · SHOULD** 用真实内容、语言、设备和重复使用来评估最小的改动。

主要参考各自回答具体问题：[Linear 的层级](https://linear.app/now/behind-the-latest-design-refresh)、[Geist 排版](https://vercel.com/geist/typography)、[视觉对齐](https://craft.gustavofior.com/optical-alignment)和[可打断性](https://craft.gustavofior.com/interruptibility)。

- **D-CRAFT-3 · SHOULD** 用宿主的令牌和实际能力吸收它们的原则；不要照搬某个产品的像素尺寸，也不要把做法当成规则引入。
- **D-CRAFT-4 · SHOULD** 把参考当作决策的输入，而不是额外的指令集；例如 [Don't Make Me Think](https://sensible.com/dont-make-me-think/) 为扫读、层级和清晰的选择提供依据。

[taste-skill](https://github.com/leonxlnx/taste-skill) 为有意识的方向和评审提供依据；[ryugi](https://github.com/Innei/ryugi) 为可执行的工作和新鲜证据提供依据。

- **D-CRAFT-5 · SHOULD** 风格偏好需要语境；一项要求要说明它保护的是哪个任务或可观察的契约。
- **D-CRAFT-6 · SHOULD** 按参考支撑的工作来选：logo／应用标识、营销页组合和高频的工作交互，解决的是不同问题。
- **D-CRAFT-7 · SHOULD** 记录观察到的模式和你做的调整；用真实内容验证结果。

可选的[研究索引](./REFERENCE_RESEARCH.md)把参考来源对应到具体问题，演示这种转化，不额外增加一套规则。

- **D-CRAFT-8 · SHOULD** 方向未定时，在真实宿主中做两个小变体，内容、宽度和主题相同，每次只改一个维度。说明每处差异对任务起了什么作用。

方向明确或只是小修正时直接推进，不需要走固定的审批流程。

- **D-CRAFT-9 · SHOULD** 用 `text-wrap: balance` 渐进增强地平衡短标题，保留正常换行。
- **D-CRAFT-10 · MUST** 标题不包含依赖语言的手动换行，也不为了保住截图而被裁切。_Proof: browser_
- **D-CRAFT-11 · SHOULD** 在长篇动态内容上使用 `pretty` 之前，先确认开销和兼容性。
- **D-CRAFT-12 · SHOULD** 字体支持时，用等宽数字稳定数字的步进宽度。
- **D-CRAFT-13 · SHOULD** 为位数变化（例如 99 → 100）预留足够的栏宽。
- **D-CRAFT-14 · MUST** 位数变化绝不会截断数值。_Proof: browser_
- **D-CRAFT-15 · SHOULD** 在可复用的资源／组件中校正不对称字形，保持布局对齐线精确。
- **D-CRAFT-16 · SHOULD** 嵌套圆角的几何从实际内缩推导；先去掉不必要的嵌套表面。
- **D-CRAFT-17 · SHOULD** 给动效一个明确的职责：高频反馈即时、过渡可打断、支持减弱动效、主题切换瞬时完成。见 §5。
- **D-CRAFT-18 · MUST** 可选的惊喜效果绝不拖慢输入，也不遮挡状态。_Proof: recording_
- **D-CRAFT-19 · SHOULD** 屏幕外的装饰要暂停；采用高开销效果之前，先用真实内容做性能分析。

### 文字也是界面的一部分

- **D-COPY-6 · SHOULD** 避免不必要的次级标签和描述。让布局来说明。
- **D-COPY-7 · SHOULD** 标题、分组、邻近关系或一目了然的控件，不需要再用一句话重复它的用途。
- **D-COPY-8 · SHOULD** 删掉不带来新决定、约束或后果的文案；不要换成装饰性徽标或 tooltip。
- **D-COPY-9 · MUST** 保留无障碍名称、字段标签、单位、错误信息和风险提示。_Proof: browser_
- **D-COPY-10 · SHOULD** 保留有用的首次使用指引，并测试任务是否仍然好理解。
- **D-COPY-11 · SHOULD** 让上下文承担上下文：用 `Users` 而不是 `User Management`；对话框正文不要重复标题里的问题。
- **D-COPY-12 · SHOULD** 写结果（`Save`、`Move`、`Delete`），不写手势（`Click to save`）。只有上下文没交代对象时才带上对象。
- **D-COPY-13 · MUST** `Cancel` 离开且不提交任何改动。_Proof: browser_
- **D-COPY-14 · SHOULD** 使用句首大写；短标签不加句号，说明性句子加句号。
- **D-COPY-15 · SHOULD** 操作需要更多输入才能完成时，用一个 `…`；全大写只留给简短状态、眉标和缩写。

### 组合界面的评审清单

- **D-REVIEW-1 · SHOULD** 对受影响的界面及可达的已变更状态逐项提问。跳过无关的变体；小补丁不需要重新设计无关页面。范围内的任何一个「否」都是一项发现。

1. 新读者能否不靠猜就认出用途和主操作？
2. 每个控件的标签、状态和结果是否描述同一个结果？
3. 强调是否稀缺：核心内容拿到分量，颜色、徽标和主按钮保持少见？
4. 能不能做得更少：有没有哪个入口、选项或状态去掉后任务并不受影响？
5. 命名的对齐线在可见文字／内容层是否精确，包括嵌套和空状态，导航栏是有意设置的，没有双重内边距？
6. 相邻控件是否共用声明的图标／文字栏？
7. 标题的点击区域是否按内容收紧？
8. 重复出现的纵向关系是否使用一致且只有一个归属的间距，包括换行的文案和隐藏的辅助／错误内容？
9. 连续正文在实际文字体系、字体和缩放级别下是否读着舒服？**不是**连续正文的元素是否都没有被行宽上限约束？
10. 看起来属于同一对象的元素是否在边框、圆角**和**间距上都一致？每个预留的栏是否真的有内容？每个常驻的框、填充或分隔线是否表达了独立的边界，而不是再嵌套一次同一个分组？
11. 在相关的变更状态下是否成立：空、加载、失败、长译文、窄屏、支持的主题、减弱动效以及受影响时的 **RTL**？
12. 对布局或交互改动，是否已在真实浏览器中按相关宽度和主题检查过受影响的界面？独立操作在悬停前（包括触屏使用时）是否可辨认，且没有多余的分组包围？

一张正常路径的截图证明不了键盘行为、焦点、动态内容、窗口缩放或失败恢复。

- **D-REVIEW-2 · SHOULD** 按 [ACCEPTANCE](./ACCEPTANCE.md) 处理独立预期、实际运行时／截取内容的身份、浏览器测量，并分开报告自动化、智能体和人工的结果。

仅在源码中提供的[浏览器示例](https://github.com/chaxus/ran/blob/main/packages/ranui/test/e2e/layout-contract.md)包含环境搭建命令和测试工具细节；它们不是公开的包 API。

## 10. 信息架构：先定形态，再做组合

- **D-IA-1 · SHOULD** 信息密集的控制台、仪表盘和工作台，先选结构再做组合。

完整的 API 数据不等于页面设计：读者仍需要清晰的顺序，先理解对象、它们的状态和关系，再采取行动。

- **D-IA-2 · SHOULD** 单一转化页和落地页有自己的任务结构，不要套用高密度控制台的模板。

### 给组件命名之前，先回答三个问题

- **D-IA-3 · SHOULD** 选组件之前，先把三个答案都定下来。

1. **读者一到页面需要看到什么？** 这就是主要信息。
2. **还需要看到什么才能理解它？** 相关资源、相关模型、上下文。
3. **接下来做什么？** 判断、行动，或继续思考。

- **D-IA-4 · SHOULD** **一个页面只有一个主模型。** 辅助模型可以帮读者理解或操作它，但不能争夺首屏。
- **D-IA-5 · SHOULD** 与其追求某个随意的点击次数上限，不如给出清晰、无歧义的下一步选择。测试读者能否认出下一步操作，而不只是目标能否到达。

### 形态跟随任务，而不是数据载荷

- **D-IA-6 · SHOULD** 根据读者的问题选骨架，而不是根据 API 数组或路由 ID；参照下表。

| 任务                           | 合适的形态                             |
| ------------------------------ | -------------------------------------- |
| 比较数值／差异                 | 表格或 diff                            |
| 识别／打开资源                 | 列表；只有图片能标识资源时才用图片网格 |
| 了解单个对象的当前状态         | 分区详情                               |
| 了解归属／依赖关系             | 树或邻接列表；只有路径本身重要时才用图 |
| 规划下一步／推动工作经过各阶段 | 步骤流程／看板（移动本身就是工作时）   |
| 审计发生了什么、何时、由谁     | 时间线或追踪下钻                       |
| 讨论或阅读连续文本             | 讨论串或文档                           |
| 判断健康度、趋势或异常         | 状态墙或仪表盘                         |
| 查找占用／冲突或位置           | 日历或地图／画布                       |
| 处理下一项／修改规则           | 主从工作台／配置表单                   |

- **D-IA-7 · SHOULD** 不要把历史事件和未来步骤、筛选和看板、有序的文字和字段网格混为一谈。仅有日期不足以支撑日历。
- **D-IA-8 · SHOULD** 只有每个视图都服务于一个独立任务、值得为它维护筛选／状态／操作时，才提供多个视图。

### 每类信息都有自己的位置

- **D-IA-9 · SHOULD** 身份和状态放在标题或摘要区域打头，操作、反馈和证据放在它们的对象旁边，如下表所示。

| 信息 | 该放在                                   | 不该放在                       |
| ---- | ---------------------------------------- | ------------------------------ |
| 身份 | 标题、对象摘要                           | 最后一列，或藏在某个标签页后面 |
| 状态 | 标题或摘要区域                           | 只能在某个详情字段里找到       |
| 属性 | 详情主体，按人的思考方式分组             | 按 API 字段顺序平铺            |
| 关系 | 单独的区域或标签页；归属、依赖、引用分开 | 混在属性表里                   |
| 变更 | diff 区域、时间线                        | 只显示新值                     |
| 证据 | 判断旁边，可展开                         | 另一处的日志页                 |
| 操作 | 主操作在标题区域，其余在各自对象旁边     | 埋在「更多」下面               |
| 反馈 | 操作旁边，保留任务上下文                 | 与对象脱节的全局 toast         |

- **D-IA-10 · SHOULD** **每个事实只有一个权威位置。** 其他地方只显示摘要，或给出链回它的入口。
- **D-IA-11 · SHOULD** 遵循默认阅读顺序：页面身份 → 当前状态或异常 → 主任务和主操作 → 判断所需的信息 → 关系、变更、证据 → 次要信息和低频操作。
- **D-IA-12 · SHOULD** **每个任务区域只有一个主操作**，它是最可能的下一步，而不是破坏性最强的那个（它能占多少分量，由 §9「强调是有预算的」决定）。

### 密度指有效信息，而不是单位面积的控件数

收紧间距提高的是视觉密度，有效密度原地不动。去掉无关字段、把对比放在一处，提高的才是真正的密度。

- **D-IA-13 · SHOULD** **一个页面最多使用两个相邻的密度档位**：宽松用于首次使用和有风险的确认，标准用于大多数列表和详情，紧凑用于专家工作台。
- **D-IA-14 · MAY** 容器内边距和行高可以收紧。
- **D-IA-15 · MUST** 可读的正文、可见的聚焦环和指针目标尺寸不随密度缩小（§7、§8）。_Proof: browser_

### 容器修不好结构

- **D-IA-16 · SHOULD** **每个视图只有一个上下文返回入口。** 不要同时显示外层的「返回对话」和内层的「返回产物」。
- **D-IA-17 · SHOULD** 详情视图返回它的直接父级。
- **D-IA-18 · MUST** 祖先页面可以通过路由层级或命名清晰的面包屑到达。_Proof: browser_
- **D-IA-19 · SHOULD** 验证完整的路径，包括焦点归还和较长的译文目标名称。
- **D-IA-27 · MUST** 回到父级时，焦点恢复到发起跳转的那一项。_Proof: browser_
- **D-IA-20 · MUST** 文字放不下时，重新排布或改用有意义的较短目标名称；省略号或 tooltip 绝不能藏起唯一的目标提示。_Proof: browser_
- **D-IA-21 · SHOULD** 父级上下文只选一种组合方式。不要仅仅为了给多余的返回快捷入口换个名字就加面包屑，也不要在返回命令上方把同一个父级再重复成一个不可交互的面包屑。

如果经由父级返回已经能到达祖先页面，这条路径就保证了可达性，不需要在详情标题栏再加一行。

- **D-IA-22 · SHOULD** 层级本身对任务有帮助时才使用面包屑。

**模态框不是导航层。**

- **D-IA-23 · SHOULD** 需要可复制链接、历史记录、并排对比，或在刷新后仍要保留的工作，都给它一个路由。
- **D-IA-24 · SHOULD** 模态框只用于简短确认或单个字段，弹出层或菜单用于临时上下文，展开行用于渐进展开。
- **D-IA-25 · SHOULD** **标签页承载同一对象的平级视图**，比如它的对话、它的检查、它的 diff；绝不承载无关模块，那是导航的职责。
- **D-IA-26 · SHOULD** 所选组件库缺少合适的基础组件时，使用现有的语义元素和宿主令牌；验证所需的交互，而不是自创不受支持的 API。

## 验证清单（UI 上线前）

- **D-VERIFY-1 · SHOULD** 针对受影响的界面、支持的变体和变化的行为选择检查项；不要只为了凑齐清单而构造无关的流程。

仓库 CI 仍会运行完整的门禁。

- **D-VERIFY-2 · SHOULD** 主任务和主操作一眼就能认出。

受影响的布局／主题改动在相关的**窄屏和宽屏**宽度及支持的主题下正常工作（D-INPUT-1）。鼠标和触摸都能用：拖拽使用 Pointer Events，任何 `trigger="hover"` 都有轻触替代（D-INPUT-3、D-INPUT-4）。键盘和可见焦点由 D-ACCESS-3 和 D-ACCESS-4 覆盖。

- **D-VERIFY-5 · SHOULD** 测试所有变化的**状态**（悬停、按下、聚焦、禁用、加载、空、错误）。
- **D-VERIFY-7 · SHOULD** 覆盖相关的边界情况：长文本、大数字，以及宿主支持的文字体系／语言区域。
- **D-VERIFY-8 · SHOULD** 间距来自尺度；排版使用角色；颜色使用语义令牌。
- **D-VERIFY-9 · SHOULD** 运行宿主适用的检查，并查看实际的浏览器证据。
- **D-VERIFY-10 · SHOULD** 文案遵循 §6。

仅靠颜色的状态信号由 D-ACCESS-2 覆盖。

- **D-VERIFY-12 · SHOULD** 对高密度界面：一个主模型，骨架根据问题而不是数据载荷来选，每个事实只有一个权威位置（§10）。
