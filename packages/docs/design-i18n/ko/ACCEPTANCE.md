# UI 검증 — 증거와 결정

시각이나 상호작용의 결과가 바뀌었을 때 이 계약을 쓰세요. 겉모습과 구성은 [DESIGN](./DESIGN.md)이,
관찰 가능한 동작은 [INTERACTION](./INTERACTION.md)이 담당합니다.
[인터페이스 색인](./INTERFACE_GUIDE.md)이 작업을 안내합니다. 해당하는 절만 읽으세요.

각 규칙에는 ID 와 등급이 붙습니다. **MUST**는 어기면 결함이며 증거 방식을 명시합니다.
**SHOULD**는 기본값이고, 벗어날 때는 그 경우의 이유를 밝힙니다. **MAY**는 선택입니다.
[규칙 색인](./RULES.md)에 등급이 붙은 모든 규칙과 증거 방식이 정리되어 있습니다.

## 관찰 가능한 결과에 먼저 합의한다

- **V-AGREE-1 · SHOULD** 편집하기 전에 [디자인 브리프](./DESIGN.md#style-coherence-across-components-and-pages)를 정하고, 같은 노트에 영향받는 작업, 화면/상태, 독립적인 기대값을 적으세요.
- **V-AGREE-2 · SHOULD** 관련 담당, 지원되는 공개 API, 호스트 역량의 한계를 밝히세요.
- **V-AGREE-3 · SHOULD** 폭, 테마, 언어, 입력 경로는 실제 변경에 맞춰 고르고, 관련 없는 작업을 지어내지 마세요.
- **V-AGREE-4 · SHOULD** 구성에 대해서는 콘텐츠/텍스트/아이콘 축, 의도한 내비게이션 열, 히트 범위, 세로 관계를 밝히세요.
- **V-AGREE-5 · MUST** 기대값을 테스트 대상 구현에서 끌어내지 않습니다. _Proof: review_
- **V-AGREE-6 · SHOULD** 작업/위계, 정적 구성, 닿을 수 있는 겹친 상태, 모션 순서로 검토하세요.
- **V-AGREE-7 · SHOULD** 해결되지 않은 비율이나 불분명한 내비게이션을 메우려고 애니메이션을 더하지 마세요.
- **V-AGREE-8 · SHOULD** 검토 결과 의도한 디자인이 바뀐다면 기존 브리프부터 고치고, 그 계기가 된 증거를 밝히세요.

이것은 결정 기록이지, 사용자가 이미 승인한 작업에 새로 더하는 승인 의식이 아닙니다.

API/토큰 검사는 소스 계약을, 이미지 비교는 픽셀을, 에이전트 실행은 지침을 따랐는지를 확인합니다.

- **V-AGREE-9 · SHOULD** 규칙의 담당은 하나만 두세요.
- **V-AGREE-10 · MUST** 한 종류의 검사가 다른 종류를 대신하게 하지 않습니다. API/토큰 검사, 이미지 비교, 에이전트 실행은 각자 자기 결과만 확인합니다. _Proof: review_
- **V-AGREE-11 · MUST** 픽스처는 자기 결과를 보여 줄 뿐, 렌더링하지 않은 호스트 애플리케이션의 검증이 아닙니다. 호스트 검증이라고 주장하지 않습니다. _Proof: review_

## 브라우저 증거

- **V-PROOF-1 · MUST** 눈에 보이는 결함을 재현할 때는 수정 전에 실제로 실행 중인 화면을 캡처합니다. _Proof: browser_
- **V-PROOF-2 · MUST** 수정 뒤에는 같은 관련 상태를 캡처하고, 실제 같은 문구와 주변 크롬을 포함해 창 전체를 살펴봅니다. _Proof: browser_
- **V-PROOF-3 · MUST** 목업, 소스 diff, 바꾼 단언, 관련 없는 빌드의 스크린숏을 증거로 내놓지 않습니다. _Proof: review_
- **V-PROOF-4 · SHOULD** 링크 수만이 아니라 구성도 살펴보세요. 불필요한 돌아가기를 브레드크럼으로 이름만 바꿔도 여전히 같은 맥락을 되풀이하고 불필요한 헤더 행을 더할 수 있습니다.
- **V-PROOF-5 · SHOULD** 눈에 보이는 바로가기가 하나 더 필요하다고 판단하기 전에, 부모를 거쳐 조상에 닿을 수 있는지 따라가 보세요.
- **V-PROOF-6 · MUST** 측정하기 전에 컴포넌트 등록, 대기 중인 콘텐츠, 글꼴, 렌더링된 프레임을 기다립니다. _Proof: browser_
- **V-PROOF-7 · MUST** 대상이 없거나 크기가 0 이면 실패로 처리합니다. _Proof: browser_
- **V-PROOF-8 · MUST** 서브픽셀 허용 오차는 기록하고, 정확해야 하는 축에서는 CSS 1 픽셀 미만으로 유지합니다 (소스 예시는 0.5px). _Proof: review_
- **V-PROOF-9 · MUST** 열려 있는 오버레이는 캡처가 뷰포트를 유지하고 트리거/패널 전체를 담는지 확인합니다. 전체 페이지 스크린숏은 반응형 재배치나 포털 위치 변경을 일으켜 잘라 낸 영역을 무효로 만들 수 있습니다. _Proof: browser_
- **V-PROOF-10 · MUST** 결함이 있는 층을 측정합니다. 래퍼, 안쪽 콘텐츠, 렌더링된 텍스트 Range, 아이콘 뷰포트, 실제 포인터 대상은 서로 다릅니다. Range 는 정확한 글리프 잉크가 아닙니다. _Proof: browser_
- **V-PROOF-11 · MUST** 섀도 part 는 지원되는 테스트 접점으로 다루고, 검증을 위해 프로덕션 코드에 섀도 내부 조회를 넣지 않습니다. _Proof: review_
- **V-PROOF-12 · SHOULD** 영향받는 재배치, 줄바꿈된 번역, 선택적 콘텐츠, 입력 경로를 직접 시험하세요.
- **V-PROOF-13 · MUST** 정적 스크린숏을 포커스 복귀, 키보드 탐색, 터치 발견 가능성, 중단 가능성, 비동기 완료의 증거로 쓰지 않습니다. _Proof: review_
- **V-PROOF-14 · MUST** 결함이 시간에 걸쳐 드러난다면 연속된 상호작용을 녹화합니다. _Proof: recording_
- **V-PROOF-15 · MUST** 레이아웃 단언은 관련 결함을 실제로 잡아내는지 증명합니다. 프레임은 그대로 두고 레이블 텍스트만 옮기거나, 이중 마진/유령 보조 요소를 넣거나, 제목 대상을 빈 공간까지 늘려 봅니다. _Proof: browser_
- **V-PROOF-16 · MUST** 변형이 캐스케이드에서 이겼는지 확인하고, 실패를 관찰한 뒤, 되돌리고 성공을 관찰합니다. _Proof: browser_
- **V-PROOF-17 · SHOULD** 아주 작은 수정을 위해 예시 스위트 전체를 반복하지 말고 작업과 관련된 변형을 쓰세요.
- **V-PROOF-18 · MUST** 표시 방식을 바꿀 때는 원본 데이터를 확인합니다. _Proof: browser, unit_
- **V-PROOF-19 · MUST** 코드는 강조된 DOM 텍스트가 아니라 소스 페이로드를 복사합니다. 탭, 빈 줄, 마지막 줄바꿈, 스트리밍으로 추가된 내용을 보존합니다. _Proof: unit_
- **V-PROOF-20 · MUST** 클립보드 성공/실패, 네이티브 선택, 긴 줄 스크롤을 각각 따로 확인합니다. _Proof: browser_
- **V-PROOF-21 · MUST** 브라우저의 선택 정규화는 문서로 남기되, 그것이 원본 클립보드 페이로드를 바꾸게 두지 않습니다. _Proof: unit, review_

소스 저장소에만 있는 [레이아웃 예시](https://github.com/chaxus/ran/blob/main/packages/ranui/test/e2e/layout-contract.md)에는
실행 가능한 명령과 기하 유틸리티가 들어 있습니다. 소비자는 그 관계를 자기 호스트에 맞게 옮겨 쓰며,
이 헬퍼들은 새 ranui 내보내기가 아닙니다.

- **V-PROOF-22 · MUST** CSS zoom 스트레스 테스트를 근거로 네이티브 브라우저 확대나 텍스트 크기 접근성 지원을 주장하지 않습니다. _Proof: review_
- **V-PROOF-23 · MUST** 확인되지 않은 채 남은 경로를 밝힙니다. _Proof: review_

### 시간에 따른 모션 검토

- **V-MOTION-1 · MUST** 모션이 바뀌었다면 연속된 동작을 보통 속도로 살펴보고, 전환이 깨지는 곳은 느리게 다시 재생합니다. _Proof: recording_
- **V-MOTION-2 · MUST** 활성화, 중간 상태, 완료, 되돌아가는 경로를 포함하고, 완료 전에 입력을 반복하거나 되돌립니다. _Proof: recording_
- **V-MOTION-3 · MUST** 최종 상태, 포커스, 이벤트 수, 읽던 위치는 애니메이션과 별개로 확인합니다. _Proof: browser_
- **V-MOTION-4 · MUST** 느린 재생은 끊김을 진단하는 데 쓰고, 프레임률 벤치마크로 쓰지 않습니다. _Proof: review_
- **V-MOTION-5 · MUST** 모션 줄이기에는 더 짧은 녹화가 아니라 그 자체의 보이는 상태 검사를 둡니다. _Proof: browser_
- **V-MOTION-6 · SHOULD** 시간 축의 결함은 `element → input → observed frame/state → expected continuity` 형식으로 보고하세요.
- **V-MOTION-7 · SHOULD** 영향받는 형제 컴포넌트 전반에 대표적인 실제 작업 하나를 써서 어긋난 모션 언어를 찾아내세요.
- **V-MOTION-8 · SHOULD** 국소적인 수정 뒤에는 전체 구성을 다시 확인하세요.
- **V-MOTION-9 · SHOULD** 실패한 시도는 진단 자료로 남기되, 통과한 캡처와 섞지 마세요.

이 검사들은 아래의 기존 증거 연결을 보완합니다.

## 작업을 끝까지 따라가 본다

- **V-WALK-1 · SHOULD** 워크플로나 구성이 바뀌었다면, 쓸 컨트롤을 말하지 않은 채 표현한 실제 같은 목표에서 시작하세요.
- **V-WALK-2 · SHOULD** 해당하는 범위에서 실제 진입점부터 결과, 복구, 돌아오기까지 목표를 끝까지 수행하세요.
- **V-WALK-3 · SHOULD** 처음 고른 선택, 모호한 레이블, 망설임이나 되돌아가기, 그리고 결과가 다음 단계를 분명히 보여 주는지 기록하세요.

선택지가 불분명하다면 클릭 경로가 짧아도 쓸모가 없습니다.

- **V-WALK-4 · SHOULD** 다듬어진 빈 상태만이 아니라, 대표적인 긴 경우나 실패하는 경우를 포함한 실제 같은 콘텐츠를 쓰세요.
- **V-WALK-5 · SHOULD** 장식 효과를 더하기 전에 작업 구조와 콘텐츠 위계부터 고치세요.
- **V-WALK-6 · SHOULD** 관찰한 문제 가운데 가장 영향이 큰 것 (최대 세 개) 을, 각각을 보여 주는 상태와 증거와 함께 보고하세요.
- **V-WALK-7 · MUST** 할당량을 채우려고 발견 사항을 지어내지 않습니다. _Proof: review_
- **V-WALK-8 · SHOULD** 수정 뒤에 영향받는 경로를 다시 따라가 보세요.
- **V-WALK-9 · MUST** 에이전트의 따라가기는 사람 대상 사용성 연구가 아니라 결함 탐색으로 보고합니다. _Proof: review_
- **V-WALK-10 · SHOULD** 실제 참여자를 관찰할 때는 인터페이스를 설명하기 전에 먼저 목표를 시도하게 하고, 그 구분을 아래 결과에도 남기세요.

## 증거를 실제로 실행된 것에 묶는다

검토한 상태마다 다음 필드로 된 간단한 기록을 남깁니다.

- **V-FRESH-1 · MUST** 런타임: 테스트한 소스 리비전/빌드와 관련된 미커밋 입력이나 그 지문을 기록하며, 결과에 영향을 준다면 공유 스타일/컴포넌트와 들어오는 데이터도 포함합니다. 실행 중인 빌드나 작업 트리가 다르면 Git HEAD 만으로는 부족합니다. _Proof: review_
- **V-FRESH-2 · MUST** 범위/환경: 해당하는 경우 영향받는 화면/묶음 구성원, 라우트/상태, 뷰포트, 테마, 로케일, 브라우저, 입력이나 모션 줄이기 설정을 기록합니다. _Proof: review_
- **V-FRESH-3 · MUST** 미디어: 캡처/녹화 위치와 콘텐츠 식별값 (예: SHA-256) 을 그 런타임과 상태에 묶어 기록합니다. _Proof: review_
- **V-FRESH-4 · MUST** 이전과 이후를 구분하고, 하나뿐인 이전 이미지를 덮어쓰지 않습니다. _Proof: review_
- **V-FRESH-5 · MUST** 검토: 자동 검사와 에이전트 점검이 실제로 확인한 것을, 사람의 결정이나 확인되지 않은 상태와 분리해 기록합니다. _Proof: review_
- **V-FRESH-6 · MAY** 짧은 Markdown 기록이면 됩니다. 기존 매니페스트가 이 필드들을 대신할 수도 있습니다.
- **V-FRESH-7 · SHOULD** 평범한 변경을 위해 새 증거 서비스나 설정 프레임워크를 더하지 마세요.
- **V-FRESH-8 · MUST** 해시는 파일 옆이나 참조된 매니페스트에 두어, 주장한 연결을 독립적으로 확인할 수 있게 합니다. _Proof: review_

**검토는 그것이 살펴본 증거와 런타임 범위에만 적용됩니다.**

- **V-FRESH-9 · MUST** 이미지를 바꾸거나, 녹화를 편집하거나, 묶음 구성원을 바꾸거나, 관련 런타임 입력을 바꾼 뒤에는 해당 검토를 낡은 것으로 취급합니다. _Proof: review_
- **V-FRESH-10 · MUST** 공유 스타일/컴포넌트를 바꾼 뒤에는 영향받는 모든 상태를 새로 고치고, 필요하면 다시 빌드한 다음 새 증거를 살펴봅니다. _Proof: browser, review_
- **V-FRESH-11 · MUST** 옛 캡처를 현재 증거로 내놓지 않습니다. _Proof: review_
- **V-FRESH-12 · MUST** 문서만 고친 경우나 관련 없는 소스 변경 뒤에 런타임 증거를 유지한다면, 그 의존 범위가 영향받지 않는 이유를 기록합니다. _Proof: review_

옛 캡처는 기록으로 남겨 두어도 됩니다. 문서만 고쳤거나 관련 없는 소스가 바뀌었다면 똑같은 런타임 증거는
여전히 유효하므로, HEAD 가 바뀌었다는 이유만으로 모든 것을 다시 캡처할 필요는 없습니다.

## 권한을 사실대로 보고한다

| 결과               | 누가/무엇이 확인할 수 있나                                 | 확인하지 못하는 것           |
| ------------------ | ---------------------------------------------------------- | ---------------------------- |
| 자동 검사          | 선언한 런타임에 대한 최신 명령 출력이나 브라우저 단언      | 시각 품질이나 사람의 결정    |
| 에이전트 시각 검토 | 에이전트가 현재 캡처와 영향받는 상호작용을 살펴봄          | 사용자 승인                  |
| 사람의 결정        | 실제 사용자의 결정. 그 메시지/액션 참조와 증거 범위를 함께 | 이후에 바뀐 증거에 대한 승인 |

- **V-REPORT-1 · MUST** 한 문단짜리 보고에서도 이 세 결과를 분리합니다. _Proof: review_
- **V-REPORT-2 · MUST** 각 결과는 위 표가 밝힌 출처에서만 주장하고, 표가 확인하지 못한다고 한 것에 대해서는 주장하지 않습니다. _Proof: review_
- **V-REPORT-3 · SHOULD** `automated: passed`, `agent review: passed with limits`, `human: not requested`처럼 명시적인 결과를 쓰세요.
- **V-REPORT-4 · MUST** 사람의 검토를 요청했는데 아직 끝나지 않았다면 `pending`이라고 말합니다. _Proof: review_
- **V-REPORT-5 · MUST** 사용자가 거부했다면, 그 사용자가 갱신된 범위를 검토할 때까지 `rejected`와 그 발견 사항을 유지합니다. _Proof: review_
- **V-REPORT-6 · MUST** 에이전트는 자신의 수정과 최신 검사를 보고할 수 있지만, 사용자의 결정을 지어내거나 사람의 거부를 지우지 않습니다. _Proof: review_
- **V-REPORT-7 · MUST** 주체가 없는“accepted”, “approved”, “验收通过”를 쓰지 않습니다. _Proof: review_

푸시, PR 갱신, 그 밖의 외부 행동을 할지는 사용자 승인이 정합니다.
이 문서는 사람의 승인 게이트를 일괄적으로 더하지 않습니다.

- **V-REPORT-8 · SHOULD** 승인된 작업은 끝내서 전달하되, `not requested`/`pending`은 사실대로 보고하세요.
- **V-REPORT-9 · SHOULD** 실제 승인이나 꼭 필요한 제품 결정이 빠져 있을 때만 물어보세요.
- **V-REPORT-10 · MUST** 에이전트 자신의 시각 검사를“사용자 승인”으로 표시하지 않습니다. _Proof: review_

최소한의 전달 노트는 이렇게 쓸 수 있습니다.

> 런타임과 범위: 빌드/소스 …; 상태/환경 …; 관련 입력 지문 …
> 증거: 이전/이후/상호작용 …; 식별값 기록 위치 …
> 자동: 명령/결과 …
> 에이전트 검토: 관찰한 결과, 남은 발견 사항이나 한계 …
> 사람의 결정: 요청 안 함 / 대기 중 / 실제 결정과 참조 …
> 미확인: …; 승인된 PR/갱신: …

## 지침 자체의 회귀

결정론적 대조군은 모델을 호출하지 않고 평가기를 검사합니다. 실제 실행에는 사용 가능한 에이전트 하네스가
필요하며, 모든 문장 수정마다 거쳐야 하는 필수 게이트는 아닙니다.

- **V-EVAL-1 · SHOULD** 스킬/라우팅/검증 변경을 선택적으로 또는 작업 승인 범위 안에서 실제 평가할 때는, 소스 저장소에만 있는 [에이전트 시나리오 여섯 개](https://github.com/chaxus/ran/tree/main/plugins/ran/evals)를 쓰세요.
- **V-EVAL-2 · MUST** 실제 실행 전에 작업, 픽스처, 도구, 독립적인 채점 기준을 고정합니다. _Proof: review_
- **V-EVAL-3 · MUST** 모델/설정이 같은 새 세션을 씁니다. _Proof: review_
- **V-EVAL-4 · MUST** 기준 지침과 후보 지침을 별도의 작업 공간에 고정합니다. _Proof: review_
- **V-EVAL-5 · MUST** 실제 에이전트 작업, 프롬프트, 결과 검사, 증거를 보존합니다. _Proof: review_
- **V-EVAL-6 · MUST** 기준의 통과는 대조군으로, 후보의 실패는 실패로 기록합니다. _Proof: review_
- **V-EVAL-7 · MUST** 작업자에게 평가기의 임곗값이나 수정 패치를 보여 주지 않습니다. _Proof: review_

결함을 심어 둔 거부/복원 검사로 평가기의 민감도를 확인합니다.

- **V-EVAL-8 · MUST** 그 작업들에서의 동작은 실제 에이전트 실행으로만 주장합니다. 문장 일치, 손으로 쓴 답, 고친 테스트 기대값은 그 증거가 되지 않습니다. _Proof: review_
- **V-EVAL-9 · MUST** 시각적 판단은 기계적 검사와 별개로 살펴봅니다. _Proof: review_
- **V-EVAL-10 · MUST** 표본 크기, 도구, 다루지 못한 조건을 보고합니다. _Proof: review_
- **V-EVAL-11 · MUST** 성공한 작업 여섯 개는 모델 전반의 신뢰성을 증명하지 않습니다. 그것을 근거로 신뢰성을 주장하지 않습니다. _Proof: review_
