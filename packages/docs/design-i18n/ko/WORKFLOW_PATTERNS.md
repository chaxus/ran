# 선택적 워크플로 패턴

이 레시피들은 **작업에 도움이 될 때만** 적용합니다. 평범한 폼, 검색 페이지, 편집기에는 기본적으로
큐, 계정 연결, 버전 기록이 필요하지 않습니다.
겉모습은 [DESIGN.md](./DESIGN.md)가, 일반 동작은 [INTERACTION.md](./INTERACTION.md)가 담당합니다.
엔지니어링은 호스트가 담당하며, [ranui 엔지니어링](https://github.com/chaxus/ran/blob/main/packages/ranui/docs/CODING.md)은
선택적인 라이브러리 어댑터입니다. 이것들은 호스트 애플리케이션의 결정이지,
추가 컴포넌트 API, 저장 보장, 번들된 서비스가 아닙니다.

각 규칙에는 ID 와 등급이 붙습니다. **MUST**는 어기면 결함이며 증거 방식을 명시합니다.
**SHOULD**는 기본값이고, 벗어날 때는 그 경우의 이유를 밝힙니다. **MAY**는 선택입니다.
[규칙 색인](./RULES.md)에 등급이 붙은 모든 규칙과 증거 방식이 정리되어 있습니다.

- **W-RECIPE-1 · SHOULD** 고른 레시피마다, 컨트롤을 고르기 전에 애플리케이션이 무엇을 지원하는지 확인하세요.
- **W-RECIPE-2 · SHOULD** 작업, 설정, 선택한 소스, 리비전의 상태는 기존 담당에 두세요. 화면은 그 상태를 읽고 명령을 보내며, 패널마다 서비스 클라이언트와 요청 플래그를 중복해 두지 않습니다.

## 1. 일괄 작업과 큐

**쓸 때:** 작업이 실행되는 동안 다른 가져오기, 업로드, 내보내기를 준비해 두면 도움이 될 때.
**호스트 계약:** 보내기, 준비, 동시 실행/선점, 취소 확인, 부분 쓰기, 중복 방지, 저장.

| 상태              | 주요 액션                     | 정해야 할 계약                                               |
| ----------------- | ----------------------------- | ------------------------------------------------------------ |
| 준비됨            | 파일 업로드 / 보고서 내보내기 | 범위, 목적지, 중복 제출 방지                                 |
| 실행 중           | 취소 (지원한다면)             | 무엇이 멈추고 무엇이 남는지, 쓰기가 커밋되었는지             |
| 실행 중 + 새 작업 | 큐에 추가 (지원한다면)        | 진행 중인 작업은 계속 실행되고, 새 입력은 보존됨 (W-QUEUE-2) |
| 큐 일시 정지      | 큐 재개                       | 대기 항목을 편집해도 보내거나 재개하지 않음                  |
| 실패              | 재시도 / 입력 복원            | INTERACTION §5 의 서로 다른 결과를 따름                      |

- **W-QUEUE-1 · SHOULD** 위 큐 표의 상태마다 계약을 정하세요.
- **W-QUEUE-2 · MUST** 새 작업이 진행 중인 작업을 몰래 대체하거나 취소하지 않습니다. 큐를 지원하지 않으면 새 입력을 보존하고 그 제약을 설명합니다. _Proof: unit_
- **W-QUEUE-3 · MUST** 일시 정지된 큐의 대기 항목을 편집해도 그 항목을 보내거나 큐를 재개하지 않습니다. _Proof: unit_
- **W-QUEUE-4 · SHOULD** 대기 중인 작업은“2 개 대기 중”이나“일시 정지 · 2 개 대기 중”처럼 한 줄로 요약하세요.
- **W-QUEUE-5 · SHOULD** 필요 없을 때는 큐 상세를 접고, 펼칠 때는 중첩 카드가 아니라 행으로 보여 주세요.
- **W-QUEUE-6 · MUST** 각 행은 알아볼 수 있는 항목을 가지며, 지원되는 액션만 제공합니다: 편집, 제거, 지금 실행. _Proof: browser_
- **W-QUEUE-7 · SHOULD** 지금 실행이 기다리는지, 선점하는지, 동시에 실행되는지 정해 두세요.
- **W-QUEUE-8 · SHOULD** 준비 과정은 비활성 명령으로 가득 찬 큰 패널을 더하지 말고 행 안에서 표현하세요.
- **W-QUEUE-9 · MUST** 큐를 편집해도 현재 초안은 보존되고, 편집을 취소하면 초안이 복원됩니다. _Proof: unit_
- **W-QUEUE-10 · MUST** 사용자가 그 정책을 고르지 않았다면 다시 연결되어도 대기 중인 작업을 자동으로 보내지 않습니다. _Proof: unit_
- **W-QUEUE-11 · SHOULD** 행을 제거하거나, 큐를 접거나, 작업을 멈출 때는 [일반적인 포커스와 취소 규칙](./INTERACTION.md)을 적용하세요.

## 2. 역량을 고려한 설정과 오프라인 작업

**쓸 때:** 작업이 서로 다른 제공자, 모드, 기기, 네트워크에 의존하는 역량을 제공할 때.
**호스트 계약:** 설정 저장, 실제 확인 작업, 도달 가능성, 로컬 런타임 의존성.

- **W-SETTINGS-1 · MUST** 설정 저장과 사용 가능 여부 확인은 결과가 따로인 별개의 액션이며, 각각 무엇을 해냈는지 보여 줍니다. _Proof: unit, browser_
- **W-SETTINGS-2 · SHOULD** 컨트롤은 `connected` 불리언 하나가 아니라 역량과 상태에서 끌어내세요.

원격 저장소 계정, 데이터베이스 서비스, 로컬 변환기는 설정되어 있어도 지금 당장 쓸 수 없을 수 있습니다.

| 상태                    | 사용자가 이해하는 것                                          |
| ----------------------- | ------------------------------------------------------------- |
| 설정 안 됨              | 필요한 선택이나 자격 증명이 빠져 있음                         |
| 설정됨, 미확인          | 설정은 저장되었지만 사용 가능 여부는 확인되지 않음            |
| 확인됨                  | 이 설정으로 실제 확인이 성공함. 언제인지 기록                 |
| 승인 필요/만료          | 저장된 작업을 버리지 않고 계정을 다시 연결                    |
| 서비스에 연결할 수 없음 | 저장된 설정이 지금의 도달 가능성을 증명하지 않음              |
| 기기 오프라인           | 네트워크 작업은 쓸 수 없음. 가능한 로컬 작업은 계속할 수 있음 |

- **W-SETTINGS-3 · SHOULD** 위 설정 표의 각 상태를 사용자가 구별할 수 있게 하세요.
- **W-SETTINGS-4 · MUST** 승인이 필요하거나 만료된 계정을 다시 연결해도 저장된 작업은 남습니다. _Proof: unit_
- **W-SETTINGS-5 · MUST** 관련 엔드포인트, 계정, 자격 증명 설정이 바뀌면 확인 결과를 무효로 합니다. _Proof: unit_
- **W-SETTINGS-6 · SHOULD** 브라우저의 online/offline 이벤트는 특정 엔드포인트가 동작한다는 증거가 아니라 힌트로 다루세요.
- **W-SETTINGS-7 · SHOULD** 고른 경로에 맞는 설정을 드러내세요. 로컬 변환 경로에는 캐시/다운로드/기기 컨트롤이, 원격 경로에는 엔드포인트/계정 컨트롤이 필요할 수 있습니다.
- **W-SETTINGS-8 · MUST** 관련 없는 필드 **그리고 그 낡은 상태 메시지**를 숨깁니다. _Proof: browser_
- **W-SETTINGS-9 · SHOULD** 설정 헤더, 필드 묶음, 계정 행, 사용 불가/빈 상태는 [DESIGN 의 정렬 계약](./DESIGN.md#alignment-is-structure-not-polish)에서 이름 붙인 콘텐츠 축과 내비게이션 축을 유지합니다.
- **W-SETTINGS-10 · SHOULD** 제목/메뉴 명령은 콘텐츠만큼만 감싸고, 헤더의 빈 공간은 별도의 트랙이 흡수하게 하세요.
- **W-SETTINGS-11 · SHOULD** 영역이 정렬되었다고 판단하기 전에, 보이는 레이블까지 중첩 패널과 컨트롤의 패딩을 세어 보세요.
- **W-SETTINGS-12 · MUST** 모드를 바꿔도 다른 모드의 설정은 보존됩니다. _Proof: unit_
- **W-SETTINGS-13 · SHOULD** 다른 모드로 돌아가는 경로를 찾을 수 있게 두세요.
- **W-SETTINGS-14 · SHOULD** 데이터를 넘기기 전에 데이터가 어디로 가는지 설명하세요.
- **W-SETTINGS-15 · MUST** 설정된 API 엔드포인트를 승인된 계정처럼 보여 주지 않습니다. _Proof: review_
- **W-SETTINGS-16 · MUST** 오프라인에서도 데이터와 구현이 있다면 저장된 콘텐츠와 초안을 유지합니다. _Proof: unit, browser_
- **W-SETTINGS-17 · SHOULD** 오프라인에서도 데이터와 구현이 있다면 미리보기, 편집, 내보내기를 쓸 수 있게 두세요.
- **W-SETTINGS-18 · SHOULD** 오프라인에서는 쓸모 있는 경로가 없는 네트워크 전용 탐색이나 홍보를 숨기고, 이미 연결된 객체는 이해할 수 있는 사용 불가 상태로 유지하세요.
- **W-SETTINGS-19 · SHOULD** 캐시된 리소스가 있다고 모든 런타임 의존성이 갖춰졌다는 증거로 다루지 마세요.
- **W-SETTINGS-20 · SHOULD** 다시 연결된 뒤에는 의도적으로 이어 갈 지점을 제공하세요.

## 3. 계정 연결과 외부 소스

**쓸 때:** 작업이 로컬이든 원격이든 현재 객체 바깥의 데이터를 읽거나 쓸 때.
**호스트 계약:** 승인 범위, 신원, 접근 확인, 철회, 자격 증명, 출처, 가져온 사본의 보존.
엔드포인트 주소가 있다고 계정 접근이 확보되는 것은 아닙니다.

표시용 기본 요소는 OAuth 배포, 자격 증명 보관소, 커넥터 백엔드, 저장 보장을 제공하지 않습니다.
다듬어진 연결 화면이 호스트의 승인 계약을 대신할 수는 없습니다.

- **W-ACCOUNT-1 · SHOULD** 계정 승인, 선택한 소스에 대한 접근, 특정 작업에서의 사용을 구분하세요.
- **W-ACCOUNT-2 · SHOULD** 필요한 권한만 요청하세요.
- **W-ACCOUNT-3 · SHOULD** 승인하거나 데이터를 넘기기 전에 무엇을 읽고 쓰는지, 어디로 가는지 설명하세요.
- **W-ACCOUNT-4 · MUST** 계정 신원, 다시 연결, 철회/연결 해제는 연결 UI 에서 닿을 수 있습니다. _Proof: browser_
- **W-ACCOUNT-5 · MUST** 연결을 해제하면 이후의 접근이 멈춥니다. _Proof: unit_
- **W-ACCOUNT-6 · SHOULD** 연결을 해제했을 때 가져온 사본이 어떻게 되는지 따로 설명하세요.
- **W-ACCOUNT-7 · MUST** 자격 증명을 URL, 로그, 미리보기에 넣지 않습니다. _Proof: review_
- **W-ACCOUNT-8 · SHOULD** 로컬 파일이든 데이터베이스 레코드든 클라우드 문서든, 선택한 소스의 출처와 최신성을 보여 주세요.
- **W-ACCOUNT-9 · MUST** 소스를 제거하면 이후 작업에 영향을 줄 뿐, 과거의 증거에는 영향을 주지 않습니다. _Proof: unit_
- **W-ACCOUNT-10 · MUST** 권한 오류, 낡은 데이터, 오프라인 캐시 사본은 서로 다른 상태를 가집니다. _Proof: unit_
- **W-ACCOUNT-11 · MUST** 가져온 콘텐츠는 명령을 실행해도 된다는 허가가 아니라 신뢰할 수 없는 데이터로 다룹니다. _Proof: review_
- **W-ACCOUNT-12 · MUST** 쓰기와 그 목적지는 실제로 일어나기 전에 분명히 밝힙니다. _Proof: browser_
- **W-ACCOUNT-13 · SHOULD** 쓰기 전 검토 단계는 그 영향에 맞게 정하세요.

## 4. 결과, 미리보기, 리비전

**쓸 때:** 내보내기, 변환된 문서, 초안이 일시적인 상태 메시지를 넘어서는 정체와 목적지를 가질 때.
**호스트 계약:** 결과/리비전 식별, 소스 버전, 대상 범위, 커밋 확인, 충돌 처리, 되돌릴 수 있는 기록.

- **W-REVISION-1 · SHOULD** 실질적인 콘텐츠에는 알맞은 미리보기/편집기를 우선하세요.
- **W-REVISION-2 · MUST** 비교, 적용, 실행 취소는 호스트가 지원할 때만 제공합니다. _Proof: review_
- **W-REVISION-3 · SHOULD** 결과를 요약하고, 해당한다면 그 리비전, 소스, 목적지를 밝히세요.
- **W-REVISION-4 · SHOULD** 지원되는 복사, 내보내기, 비교, 적용 액션은 관련 결과 곁에 두세요.
- **W-REVISION-5 · MUST** 미리보기와 적용을 분리하고, 변경하기 전에 대상과 범위를 밝힙니다. _Proof: browser_
- **W-REVISION-6 · MUST** 소스 데이터가 바뀌었다면 적용 전에 비교/리베이스하거나 다시 생성합니다. 더 새로운 편집이 조용히 덮어쓰이지 않습니다. _Proof: unit_
- **W-REVISION-7 · SHOULD** 저장/적용된 상태와 복구 가능한 출력은 [상호작용 표준](./INTERACTION.md)에 따라 확인하세요.

## 레시피 적용하기

- **W-APPLY-1 · MUST** 호스트가 지킬 수 있는 상태와 액션만 남깁니다. _Proof: review_
- **W-APPLY-2 · SHOULD** 다듬어진 화면이 빠진 서비스 계약을 대신할 수는 없습니다. 그 전제 조건을 분명히 밝히세요.

핵심 전환에는 이미 단위 테스트 증거를 가진 MUST 규칙이 있습니다: 일시 정지된 작업은 그대로 멈춰 있고 (W-QUEUE-3),
바뀐 설정은 확인 결과를 무효로 하며 (W-SETTINGS-5), 소스 제거는 이후 작업에만 영향을 주고 (W-ACCOUNT-9),
낡은 리비전은 새 편집을 덮어쓸 수 없습니다 (W-REVISION-6). 해당하는 경우 그 테스트들은 중단된 작업과 오프라인 작업도 다룹니다.
