# Ran Design

호스트 제품과 그 제품이 이미 쓰는 기술을 위한 디자인 방법입니다. [작업 색인](./INTERFACE_GUIDE.md)을 거쳐
필요한 절만 읽으세요. 라이브러리 토큰과 API 세부 동작은 각 구현 어댑터의 몫이며, 이 이식 가능한 방법에는 들어가지 않습니다.

각 규칙에는 ID 와 등급이 붙습니다. **MUST**는 어기면 결함이며 증거 방식을 명시합니다.
**SHOULD**는 기본값이고, 벗어날 때는 그 경우의 이유를 밝힙니다. **MAY**는 선택입니다.
[규칙 색인](./RULES.md)에 등급이 붙은 모든 규칙과 증거 방식이 정리되어 있습니다.

## 1. 색 — 팔레트가 아니라 상태의 사다리

- **D-COLOR-1 · SHOULD** 콘텐츠, 표면, 경계, 액션, 상태에 각각 의미 역할을 정하세요.
- **D-COLOR-2 · SHOULD** 기본, 호버, 활성, 비활성, 포커스 상태를 한꺼번에 정의하세요.
- **D-COLOR-3 · SHOULD** 라이트/다크 값은 호스트의 권위 있는 토큰에서 가져오고, 대비는 실제 구성 안에서 확인하세요.

브랜드 강조색은 맥락에 따라 씁니다.

## 2. 간격 — 제한된, 리듬 있는 스케일

- **D-SPACE-1 · SHOULD** 호스트에 이미 있는 간격 스케일을 쓰세요.
- **D-SPACE-2 · SHOULD** 관련된 부분은 좁은 간격으로 묶고, 작업이나 영역은 더 넓은 간격으로 나누세요.
- **D-SPACE-3 · SHOULD** 바깥 간격보다 안쪽 패딩을 먼저 정하세요.
- **D-SPACE-4 · SHOULD** 콘텐츠, 밀도, 입력 방식을 따져 보지 않은 채 참고 제품의 치수를 베끼지 마세요.

## 3. 타이포그래피 — 크기가 아니라 역할을 고른다

- **D-TYPE-1 · SHOULD** 제목, 레이블, 본문, 액션, 코드 역할을 크기·굵기·행간이 서로 맞게 정하고, 역할마다 기준이 되는 곳은 하나만 두세요.
- **D-TYPE-2 · SHOULD** 실제 문자 체계, 대체 글꼴의 메트릭, 긴 콘텐츠로 확인하세요.
- **D-TYPE-3 · SHOULD** 장식용 컨테이너보다 타이포그래피로 먼저 위계를 세우세요.

## 4. 모서리 반경과 고도

- **D-ELEV-1 · SHOULD** 중첩된 모서리 반경은 실제 안쪽 여백에 맞춰 조정하세요. 안쪽 반경 = 바깥 반경 − 여백입니다. 결과가 2px 이하이면 두 모양이 더는 동심으로 보이지 않으니, 안쪽 모양에는 자기 역할의 반경을 주거나 반경을 없애세요.

16px 반경 카드에 패딩이 8px 이면 안쪽 패널의 반경은 8px 입니다. 같은 카드에 패딩이 16px 이면 넘겨줄 반경이
남지 않으므로, 패널은 자기 역할이 쓰는 반경을 그대로 씁니다.

- **D-ELEV-2 · SHOULD** 고도는 중요도가 아니라 떠 있는 레이어를 설명하는 데 쓰고, 호스트의 쌓임 역할을 따르며, 오버레이는 주변 크롬과 함께 확인하세요.

## 5. 모션 — 되도록 쓰지 않는다

아래 시간 값은 출발점으로 삼는 경험칙입니다.

- **D-MOTION-1 · SHOULD** 호스트 시스템의 모션 토큰을 쓰고, 빈도·연속성·모션 줄이기 설정을 실제 작업 안에서 확인하세요.

| 지속 시간 | 용도                                                         |
| --------- | ------------------------------------------------------------ |
| 0ms       | 자주 일어나는 호버, 포커스, 키보드 피드백. 이미 이해된 변화  |
| ~150ms    | 목적이 있는 작은 모션 (선택). 호버에 의무로 거는 지연이 아님 |
| ~200ms    | 레이어 변화를 분명히 해 줄 때의 메뉴/팝오버 모션             |
| ~300ms    | 방향 감각에 도움이 될 때의 대화상자 모션                     |

**원칙:** 모션에 시간을 써도 되는지는 목적과 빈도가 정합니다.

- **D-MOTION-2 · SHOULD** 반복되는 상호작용은 기본적으로 즉시 피드백하세요. 변화가 크다고 해서 그 자체로 애니메이션을 넣을 이유가 되지는 않습니다.
- **D-MOTION-3 · SHOULD** 목적이 있는 모션에는 기존 토큰을 쓰고, 짧고 중단할 수 있게 유지하세요. 모션 줄이기는 D-MOTION-10 과 D-ACCESS-5 에서 등급을 매깁니다.

### 기능적 모션 계약

- **D-MOTION-4 · SHOULD** 효과를 고르기 전에 트리거, 상태 변화, 도착 지점을 먼저 정하세요.
- **D-MOTION-5 · MUST** 모션은 관련 없는 콘텐츠, 초안, 읽던 위치를 보존합니다. _Proof: recording_
- **D-MOTION-6 · SHOULD** 상호작용의 의미가 같은 형제 컴포넌트에는 같은 모션 언어를 주세요. 일관성이 모든 컴포넌트에 애니메이션을 넣으라는 뜻은 아닙니다.
- **D-MOTION-7 · MUST** 모션을 쓸 때는 새 의도가 현재 표시 상태에서 바로 모션을 중단하거나 되돌릴 수 있어야 하며, 튐·뒤늦은 완료·중복 활성화가 없어야 합니다. _Proof: recording_
- **D-MOTION-8 · MUST** 피드백은 즉시 나타납니다. 애니메이션은 입력 잠금이 아닙니다. _Proof: recording_
- **D-MOTION-9 · SHOULD** 삽입/제거 중에 텍스트가 눈에 띄게 찌그러지거나, 사라지는 컨트롤이 살아 있는 액션 위를 지나가지 않게 하세요. 불투명도와 레이아웃을 맞춰 결과가 읽히도록 하세요.
- **D-MOTION-10 · MUST** 모션 줄이기에서도 눈에 보이고 이해할 수 있는 최종 상태가 남습니다. _Proof: browser_
- **D-MOTION-11 · MAY** 스프링을 써도 됩니다. 꼭 오버슈트할 필요는 없습니다.

예시와 한계는 선택 자료인 [컴포넌트 완성도 리서치](./REFERENCE_RESEARCH.md#component-craft-设计垂点--wxaddesign)를,
증거는 [시간 축 검증](./ACCEPTANCE.md#review-motion-over-time)을 참고하세요.

- **D-MOTION-12 · SHOULD** 테마 팔레트는 한꺼번에 일관되게 자리 잡게 하세요. 암묵적인 팔레트 페이드나 `transition: all`은 피하고, 호스트가 의도하고 검증한 조율된 효과에만 명시적으로 켜세요.
- **D-MOTION-13 · MUST** 작업 화면으로 돌아왔을 때 사실 값과 읽을 콘텐츠는 숫자 카운트 애니메이션 없이 바로 보입니다. _Proof: browser_
- **D-MOTION-16 · SHOULD** 작업 화면으로 돌아올 때마다 장식용 제목 등장 효과를 다시 재생하지 마세요.
- **D-MOTION-17 · SHOULD** 등장 모션은 영역에 무엇이 담겼는지에 따라 아래 표에서 고르세요. 시차 (stagger) 는 한 영역 안에서 읽는 순서대로 주고, 페이지 전체에 걸쳐 주지 마세요.

| 영역에 담긴 것                                   | 등장                                                                      | 그 이후                                        |
| ------------------------------------------------ | ------------------------------------------------------------------------- | ---------------------------------------------- |
| 텍스트, 제목, 값, 폼, 내비게이션, 행동 유도      | 없음: 첫 페인트에 이미 있음 (D-MOTION-13)                                 | 없음                                           |
| 텍스트 옆 장식 비주얼: 아이콘 세트, 도식, 스케치 | 처음 화면에 스크롤되어 들어올 때 한 번, transform 만. 로드 시 보이면 없음 | 화면에 있는 동안 설명용 루프 가능 (D-CRAFT-19) |
| 제품 목업이나 라이브 데모                        | 콘텐츠에는 없음. 로딩 시연은 움직일 수 있음 (D-MOTION-14)                 | 읽는 사람의 상호작용이 이끔                    |
| 상태 표시기                                      | 없음                                                                      | 활동이 진행 중일 때만 펄스 (D-MOTION-15)       |

모션 줄이기에서는 모든 영역이 최종 상태로 시작합니다 (D-MOTION-10).

- **D-MOTION-14 · MAY** 로딩 시연은 로딩을 보여 주기 위해 움직여도 됩니다.
- **D-MOTION-15 · MUST** 상태 펄스는 활동이 진행 중일 때만 나타납니다. _Proof: review_

## 6. 콘텐츠 — 문구도 시스템의 일부

- **D-COPY-1 · SHOULD** 버튼은 결과를 이름으로 씁니다. 맥락이 대상을 정해 주지 않으면 대상을 포함하세요: "프로젝트 배포", "멤버 삭제". 대상이 분명히 드러난 화면이나 대화상자에서는 "저장"이나 "삭제"로 충분합니다. 막연한 "확인"은 피하세요. [맥락에 맞는 문구](#words-are-part-of-the-interface)를 참고하세요.
- **D-COPY-2 · SHOULD** 오류는 **무슨 일이 일어났는지**, 그다음 **어떻게 고치는지**를 말합니다. ✅ "빌드 실패: 번들이 크기 제한을 넘었습니다. 줄이거나 제한을 올리세요." ❌ "작업에 실패했습니다. 다시 시도해 주세요."
- **D-COPY-3 · SHOULD** 확인 메시지와 토스트는 완료된 **변화**를 말합니다. ✅ "프로젝트를 삭제했습니다". ❌ "작업 성공".
- **D-COPY-4 · MUST** 완료 피드백은 작업이 확인된 뒤에만 보여 줍니다. _Proof: unit, browser_
- **D-COPY-5 · SHOULD** 구체적으로 쓰세요. 모든 문장은 추측을 늘리지 않고 덜어 주어야 합니다.

## 7. 접근성 — 시스템은 모두를 위한 것

- **D-ACCESS-1 · MUST** 텍스트는 배경과 충분한 대비를 유지합니다 (**WCAG AA**). _Proof: browser_
- **D-ACCESS-2 · MUST** 색만으로 상태를 알리지 않습니다. 아이콘이나 텍스트와 함께 씁니다 (예: 초록/빨강만이 아니라 ✓ / ✕ 레이블). _Proof: review_
- **D-ACCESS-3 · MUST** 모든 상호작용 요소에는 그 표면에 맞는 **보이는 포커스 링**이 있습니다. "깔끔함"을 위해 없애지 않습니다. _Proof: browser_
- **D-ACCESS-4 · MUST** **완전한 키보드 탐색**: 마우스로만 되는 것은 없습니다. _Proof: browser_
- **D-ACCESS-5 · MUST** `prefers-reduced-motion`을 존중합니다. _Proof: browser_
- **D-ACCESS-6 · MUST** 호스트가 두 색 구성표를 모두 지원하면 첫 렌더링은 `prefers-color-scheme`을 따릅니다. _Proof: browser_

## 8. 입력과 뷰포트 — 모바일과 데스크톱 모두

- **D-INPUT-1 · MUST** 좁은 폭과 넓은 폭 모두에서 마우스, 키보드, 터치를 지원합니다. _Proof: browser_
- **D-INPUT-2 · MUST** 액션으로 가는 유일한 경로를 숨기지 말고 컨트롤을 다시 배치합니다. _Proof: browser_
- **D-INPUT-3 · MUST** 호버로 드러나는 어포던스에는 클릭/탭 대안이 있습니다. _Proof: browser_
- **D-INPUT-4 · MUST** 드래그는 취소를 포함해 Pointer Events 를 씁니다. _Proof: browser_
- **D-INPUT-5 · MUST** `touch-action`은 실제 드래그 표면에만 적용하고 실제 핸들러와 짝지어, 다른 곳의 일반 스크롤은 계속 동작하게 합니다. _Proof: browser_
- **D-INPUT-6 · SHOULD** 임의의 중단점보다 콘텐츠/뷰포트 기준의 범위 (`min()`, `max()`, `clamp()`) 를 우선하세요.
- **D-INPUT-7 · SHOULD** 호스트에 있는 중단점을 쓰고, 같은 필요가 반복될 때만 근거 있는 공유 역할을 새로 만드세요.

측정한 위치는 크기 변경, 컨테이너 재배치, 스크롤 뒤에는 낡은 값이 됩니다.

- **D-INPUT-8 · SHOULD** 좁은 레이아웃에서 로드만 하지 말고, 좁은 레이아웃으로 크기를 줄여 가는 경우도 직접 해 보세요.
- **D-INPUT-9 · MUST** 오버레이는 열려 있는 동안 트리거를 따라 위치를 맞춥니다. _Proof: browser_

수명 주기 동작은 호스트의 몫입니다. [ranui 엔지니어링](https://github.com/chaxus/ran/blob/main/packages/ranui/docs/CODING.md#3-state-and-ownership)은 구현 어댑터 중 하나일 뿐입니다.

- **D-INPUT-10 · SHOULD** 영향을 받는 곳에서는 실제 포인터/터치 제스처, 호버 대체 경로, 키보드 경로를 테스트하세요. 두 색 구성표를 확인했다고 입력 방식 간 동등성이 확인되는 것은 아닙니다.

## 9. 구성 — 컴포넌트가 아니라 페이지

- **D-COMP-1 · SHOULD** 먼저 §10 에서 페이지 구조를 고르고, 그다음 이 규칙들로 컴포넌트를 구성하세요.

### 컴포넌트와 페이지를 아우르는 스타일 일관성

- **D-COMP-2 · SHOULD** 구현 전에 기존 작업 노트나 제품 디자인 담당 문서에 짧은 디자인 브리프를 남기세요. 기존 시스템을 쓰고, 작은 수정이라면 영향을 받는 결정만 적으면 됩니다. 브리프는 아래 표에서 해당하는 결정을 하나씩 정합니다 (D-COMP-2).

"고급스럽게", "모던하게", "Claude 처럼"은 조사할 방향이지 구현할 수 있는 명세가 아닙니다.

| 결정           | 브리프가 정하는 것                                                                                 |
| -------------- | -------------------------------------------------------------------------------------------------- |
| 작업과 위계    | 실제 콘텐츠, 주요 액션, 처음 시선이 갈 곳. 뒤로 물러나거나 사라져도 되는 것.                       |
| 비율           | 호스트 토큰을 쓴 타입 역할/행간, 텍스트 폭, 컨트롤 밀도, 아이콘 굵기, 정렬 축.                     |
| 표면 언어      | 어느 영역에 경계가 필요한지, 중첩 반경/여백 관계, 의미 강조색과 고도 역할.                         |
| 상태 구성      | 대표 기본 상태와 긴 콘텐츠, 대기/실패, 좁은 폭 입력 경로. 상태가 겹친 경우도 포함.                 |
| 모션           | 설명하는 상태 변화, 트리거와 빈도, 중단/되돌리기 동작, 모션 줄이기 결과. "없음"도 유효한 답입니다. |
| 참고 자료 결정 | 참고 자료를 쓴다면 그 출처 링크, 받아들인 원칙, 호스트 작업에 맞춘 변형.                           |
| 검증           | 관찰 가능한 결과, 그리고 그것을 입증하거나 반박할 수 있는 실제 화면/녹화.                          |

- **D-COMP-4 · SHOULD** 형제 컴포넌트와 문서 크롬 전반에 브리프를 재사용하고, 작업에 따라 강조점만 바꾸세요.

통일성이 모든 곳에 같은 크기의 컨트롤이나 상자로 둘러싼 섹션을 두라는 뜻은 아닙니다.

- **D-COMP-5 · SHOULD** 표현력이 큰 데모는 문서 크롬과 눈에 띄게 구분하세요.
- **D-COMP-6 · SHOULD** 시각 방향을 바꾸기 전에 브리프부터 고치세요. 리뷰를 통과하지 못한 구현을 정당화하려고 표준을 슬그머니 고쳐 쓰지 마세요.
- **D-COMP-7 · SHOULD** 애니메이션을 넣기 전에 대표적인 정지 화면을 다른 실제 콘텐츠와 비교하고, 그다음 상태 변화와 돌아오는 경로를 보통 속도로 살펴보세요.

색 하나를 공유한다고 해서 어긋난 비율, 아이콘 굵기, 경계, 모션이 맞춰지지는 않습니다.

- **D-COMP-8 · SHOULD** 예시가 다른 제품에서 가져온 것처럼 보이면, 페이지 전용 패치를 덧대지 말고 그 관계를 담당하는 토큰/컴포넌트/스타일에서 고치세요.
- **D-COMP-9 · SHOULD** 참고 자료 관찰과 검증의 한계는 선택 자료인 [리서치 색인](./REFERENCE_RESEARCH.md#style-coherence-and-transition-research)에 남기세요.

### 컨테이너보다 구조가 먼저

- **D-BOX-1 · SHOULD** **상자를 쓰기 전에 간격, 정렬, 굵기, 헤어라인을 먼저 쓰세요.**

컨테이너는 그 안의 것이 별개의 객체라는 주장입니다. 대부분의 영역에는 배경, 헤어라인, 의도한 간격이면
충분합니다. 그 이상은 필요 없습니다.

- **D-BOX-2 · SHOULD** 상자는 **정말로 별개인 객체**에만 쓰세요: 라이브 데모 무대, 오버레이, 떠 있는 패널. 코드 블록, 표, 목록 행, 이전/다음 링크, 갤러리의 칸에는 쓰지 마세요.
- **D-BOX-3 · SHOULD** **불필요한 중첩 컨테이너와 이중 패딩을 피하세요.** 패딩이 있는 패널 안의 카드에는 장식 테두리나 여백이 또 필요하지 않습니다.
- **D-BOX-4 · SHOULD** 기능상 필요한 중첩 컨트롤이나 표면은 남기고, 그 반경은 실제 여백에 맞추세요. 담고 있다는 사실만으로 상자를 더할 이유가 되지는 않습니다.
- **D-BOX-5 · SHOULD** **오래 남는 모든 경계에는 고유한 역할이 있어야 합니다.** 먼저 제목, 정렬, 근접성으로 콘텐츠를 묶으세요. 그 구조로도 실제 경계가 불분명할 때만 테두리, 표면 채움, 고도를 더하세요.
- **D-BOX-6 · SHOULD** 같은 묶음을 패널 테두리, 중첩 카드, 행 구분선, 또 다른 여백으로 한꺼번에 되풀이하지 마세요.

흐린 선도 여전히 덧붙은 위계입니다. 대비를 낮추거나 길이를 줄여도 불필요한 테두리는 여전히 불필요합니다.

아래 표는 D-BOX-5 와 D-BOX-8 을 적용한 것입니다.

- **D-BOX-8 · MUST** 키보드 포커스와 지속되는 선택 표시는 남깁니다. 평소 레이아웃을 조용하게 하려고 없애지 않습니다. _Proof: browser_

| 경계                 | 이것을 전할 때는 남김                                     | 이것만 되풀이할 때는 제거                                       |
| -------------------- | --------------------------------------------------------- | --------------------------------------------------------------- |
| 필드/컨트롤 테두리   | 값을 입력하거나 선택할 수 있는 곳                         | 이미 알아볼 수 있는 명령을 감싼 장식용 래퍼                     |
| 영역 테두리나 구분선 | 독립된 뷰포트, 크기 조절 경계, 작업의 큰 전환             | 제목과 간격만으로 이미 같은 묶음이 분명한 경우                  |
| 중첩 표면            | 별개의 떠 있는 레이어, 미리보기, 드롭 대상, 상호작용 경계 | 이미 자리 잡은 설정 창 안의 또 다른 컨테이너                    |
| 포커스/선택 외곽선   | 키보드 포커스나 지속되는 선택 상태                        | 없으면 평소 레이아웃이 더 조용해 보이더라도 이 상태 표시는 남김 |

- **D-BOX-9 · SHOULD** 잘라 낸 묶음만 보지 말고 창이나 페이지 전체를 검토하세요. 남아 있는 고정 외곽선, 채움, 구분선마다 그것이 전하는 관계나 상호작용을 말할 수 있어야 하고, 없앴을 때 무엇이 모호해지는지 확인하세요.

테두리는 선택이지만, 닿을 수 있고 알아볼 수 있는 컨트롤은 선택이 아닙니다.

### 강조는 예산이다

**색, 굵기, 배지, 채움, 고도는 귀합니다.** 모든 것을 강조하면 아무것도 중요해 보이지 않습니다.

- **D-COMP-10 · SHOULD** 우선순위는 먼저 구조와 근접성으로 세우고, 강조는 정말 그럴 만한 하나에 쓰세요.

**고도는 중요도가 아니라 쌓임을 설명합니다.**

- **D-ELEV-3 · SHOULD** 그림자는 콘텐츠 위에 정말로 떠 있는 표면에만 쓰세요: 팝오버, 메뉴, 대화상자, 알림. 모든 카드에 그림자를 주지 마세요.

### 간격에는 의미가 있다

§2 의 스케일은 리듬만이 아닙니다. 단계마다 하나의 관계를 말합니다.

간격이 무엇을 _의미하는지_에 따라 단계를 고르세요 (D-SPACE-2).

| 관계               | 상대적 간격              |
| ------------------ | ------------------------ |
| 한 컨트롤의 부분들 | 의도한 간격 중 가장 좁게 |
| 밀접한 컨트롤들    | 촘촘한 묶음 간격         |
| 하나의 콘텐츠 묶음 | 묶음 리듬                |
| 서로 다른 묶음     | 더 큰 분리               |
| 주요 영역 경계     | 의도한 분리 중 가장 크게 |

**안쪽 먼저, 바깥은 나중:** 컴포넌트 자체의 패딩을 컴포넌트 사이 간격보다 먼저 정합니다 (D-SPACE-3).
**간격이 좁을수록 관계가 가깝습니다.** 세로 리듬이 전하는 것은 이것뿐입니다.

- **D-SPACE-6 · SHOULD** 장식용 구분선으로 간격이 만든 관계를 무너뜨리지 마세요.

### 형제 화면 사이의 세로 리듬

- **D-SPACE-7 · SHOULD** 고정 높이가 아니라 관계를 반복하세요. 제목/설명, 필드/힌트, 묶음, 영역 사이 간격은 관계에 따라 호스트 스케일에서 고르세요.

이것은 구성상의 결정이지, 어디에나 통하는 컴포넌트 치수가 아닙니다.

- **D-SPACE-8 · SHOULD** 번역문은 자연스럽게 늘어나게 두고, 설명이 없을 때 빈 행을 남기지 마세요.
- **D-SPACE-9 · SHOULD** 간격마다 담당을 하나만 두세요: 부모 스택이든 자식의 명시적 마진이든. 직접 넣은 제목/문단의 로컬 마진은 부모 간격에 더하지 말고 초기화하세요.
- **D-SPACE-10 · SHOULD** 컨트롤이 가진 패딩, 마진 상쇄, 인라인 기준선 공간을 계산에 넣으세요. transform 이나 더 작은 글자로 보정하지 마세요.
- **D-SPACE-11 · SHOULD** 힌트는 그것이 설명하는 필드/액션 곁에 두세요.
- **D-SPACE-12 · MUST** 숨겨진 보조 요소는 의도치 않은 간격을 남기지 않습니다. _Proof: browser_
- **D-SPACE-16 · SHOULD** 미리 자리를 잡아 둔 비동기 상태 줄에는 밝혀 둔 목적과 범위가 있어야 합니다. 콘텐츠가 자리 잡은 뒤 두 축을 모두 측정하세요. [ACCEPTANCE](./ACCEPTANCE.md)에서 V-PROOF-6 으로 등급을 매깁니다.

`next.top - previous.bottom`은 프레임 사이 거리를 잴 뿐, 글리프/줄 상자의 공간을 재지 않습니다.

- **D-SPACE-14 · SHOULD** 행간, 패딩, 헤어라인은 따로 다루세요. 16px 패딩에 1px 선을 더한 것은 17px 간격 토큰이 아닙니다.
- **D-SPACE-15 · SHOULD** 독립적인 기대값을 쓰고, 줄바꿈, 크기 조절, 보조/오류 표시 여부, 관련된 밀도를 직접 시험하세요.

이중 마진, 유령 행, 텍스트만 어긋나는 문제에 대한 안정화 대기와 변형 검사는 [ACCEPTANCE](./ACCEPTANCE.md#browser-proof)가 담당합니다.

### 폭 제한은 열이 아니라 텍스트에 건다

- **D-TYPE-4 · SHOULD** **실제 문자 체계와 글꼴에 맞는 읽기 좋은 줄 길이를 고르세요.**

라틴 문자 산문에서 한 줄 60–75 자는 출발점이 되는 경험칙일 뿐, 모든 문자 체계에 통하는 범위가 아닙니다.

- **D-TYPE-5 · SHOULD** 지원하는 폭, 확대 수준, 대체 글꼴에서 실제 같은 텍스트를 검토하세요. CJK 와 여러 문자 체계가 섞인 텍스트는 따로 판단해야 합니다.

[WCAG 시각적 표현](https://www.w3.org/WAI/WCAG22/Understanding/visual-presentation.html)도 Level AAA 기준에서
CJK 를 따로 다루지만, 라이브러리가 반드시 따라야 할 기본값은 아닙니다.

- **D-TYPE-6 · SHOULD** 표, 코드 펜스, 데모 무대, 이미지는 콘텐츠에 필요한 폭을 그대로 갖게 두세요. 폭 제한은 그것을 담는 열이 아니라 텍스트 요소에 거세요.
- **D-TYPE-7 · SHOULD** **줄 길이는 `em`이 아니라 `rem`으로 선언하세요.**

`em`은 요소 자신의 글자 크기를 기준으로 계산되므로, 글자가 클수록 줄이 길어집니다. 정확히 거꾸로입니다.

- **D-TYPE-8 · SHOULD** **상자를 찾기 전에 글자로 위계를 만드세요.**

크기를 한 단계 올리고 색을 한 단계 낮추면, 컨테이너도 테두리도 새로 없이 제목과 첫 문장이 제목과 부제가 됩니다.

### 레이아웃이 하나의 객체라고 말하면 간격도 그렇게 말해야 한다

**테두리와 반경을 공유하면서 그 사이에 간격이 있으면 모순입니다.**

- **D-ALIGN-1 · SHOULD** 요소들이 하나의 객체인지 둘인지 정하고, 모든 속성이 같은 말을 하게 하세요.
- **D-ALIGN-2 · SHOULD** **어떤 값이 다른 값과 같아야 한다면 이름을 붙이세요.** 자식이 빼야 하는 간격은 두 곳에 적힌 리터럴이 아니라, 두 번 참조되는 하나의 사용자 정의 속성입니다.

### 열은 그 콘텐츠가 있을 때만 잡아 둔다

**조건 없이 선언한 열은, 넣을 것이 없는 페이지에서도 여전히 열입니다.**

- **D-ALIGN-3 · SHOULD** 트랙은 그 요소가 있을 거라고 짐작한 페이지 유형이 아니라, 요소가 실제로 있는지 (`:has()`) 를 조건으로 거세요.

### 정렬은 마감 손질이 아니라 구조다

- **D-ALIGN-4 · SHOULD** **정렬 축마다 이름을 붙이고, 그 축이 맞추는 기하를 밝히세요.** 각 축을 어떤 형제들이 공유하는지 적되, 헤더, 본문, 행, 액션, 빈/로딩/오류 콘텐츠를 포함하세요.

페이지 콘텐츠 축, 내비게이션 열, 중첩된 폼 레이블 축은 의도적으로 다를 수 있습니다.

- **D-ALIGN-5 · SHOULD** 뒤로 가기 버튼과 간격이 별도의 제목 열을 만들 수 있습니다. 그 제목이 본문 텍스트와 정렬된 것으로 슬쩍 간주하지 마세요.
- **D-ALIGN-6 · MUST** 선택 사항인 아이콘이나 배지가 없더라도 레이블이 선언된 열 밖으로 밀리지 않습니다. _Proof: browser_
- **D-ALIGN-7 · SHOULD** 중첩 단계가 끝나면 부모의 축으로 정확히 돌아오세요. 올바른 상자끼리 비교하세요. 우연히 겹치더라도 이들은 별개의 측정입니다. 결함이 있는 층을 측정하는 일은 [ACCEPTANCE](./ACCEPTANCE.md)에서 V-PROOF-10 으로 등급을 매깁니다.

| 기하          | 측정할 것                                                                             |
| ------------- | ------------------------------------------------------------------------------------- |
| 프레임        | `getBoundingClientRect()`로 얻는 래퍼/호스트의 테두리 상자                            |
| 콘텐츠        | 중첩 래퍼를 포함해 실제 테두리와 패딩을 뺀 안쪽 가장자리                              |
| 텍스트        | 렌더링된 레이블 텍스트 노드를 감싼 DOM `Range`. 줄바꿈되면 첫/마지막 줄 사각형을 사용 |
| 아이콘 뷰포트 | SVG/viewbox나 이미지 상자. 그 안에 칠해진 글리프 잉크는 비대칭일 수 있음              |
| 히트 영역     | 실제 이벤트 대상과 그 호버/포커스 표면. 가장자리 근처 지점을 확인                     |

버튼 프레임이 문단과 정렬됐다고 해서 그 텍스트가 정렬됐다는 증거는 아닙니다. 내부 패딩 때문에 프레임은
그대로인데 레이블만 움직일 수 있습니다. `Range`는 타이포그래피상의 기하를 줄 뿐, 정확한 글리프 잉크는 아닙니다.

- **D-ALIGN-9 · SHOULD** 글리프의 광학 보정은 따로 살펴보세요. 웹 컴포넌트라면 호스트, 문서화된 섀도 part, 슬롯 텍스트를 지원되는 테스트 접점으로 측정하세요. 이는 [ACCEPTANCE](./ACCEPTANCE.md)의 V-PROOF-11 이 담당하며, 프로덕션 코드에서 섀도 내부를 조회하지 않을 것과 문서 CSS 가 경계를 넘는다고 가정하지 않을 것도 여기에 포함됩니다.
- **D-ALIGN-11 · SHOULD** **헤더 명령의 히트 영역을 레이아웃의 빈 공간과 분리하세요.** 제목/메뉴 트리거는 콘텐츠와 의도한 패딩만큼만 감싸고, 사용할 수 있는 폭 안에서 끝납니다. 남는 공간은 별도의 flex/grid 트랙이 흡수하게 하세요.
- **D-ALIGN-12 · SHOULD** 긴 번역문에 대한 말줄임/줄바꿈과 이웃한 액션의 동작을 정해 두세요.
- **D-ALIGN-13 · MUST** 제목 트리거의 히트 영역은 D-ALIGN-14 에 해당하지 않는 한 헤더의 남는 공간까지 뻗지 않습니다 (예: 제목 버튼에 `flex: 1`). _Proof: browser_
- **D-ALIGN-14 · SHOULD** 의도적으로 폭 전체를 선택 영역으로 삼는 행은 다른 역할입니다. 그 계약을 명시적으로 기록하세요.
- **D-ALIGN-15 · MAY** 거친 포인터용 대상은 더 커져도 됩니다.
- **D-ALIGN-22 · SHOULD** 커진 대상의 호버 채움은 관련 없는 콘텐츠까지 덮지 않고 컨트롤 자신의 콘텐츠에 머물러야 합니다.
- **D-ALIGN-16 · SHOULD** **공통 조상에서 보이는 텍스트까지 모든 여백을 세세요.** 부모 패딩, 중첩 패널 패딩, 컨트롤 내부 패딩, 테두리, 내비게이션 열이 모두 더해집니다.
- **D-ALIGN-17 · SHOULD** 불필요한 여백은 설명 없는 음수 마진으로 상쇄하지 말고 그 여백을 가진 곳에서 없애세요.
- **D-ALIGN-18 · SHOULD** 빈 상태도 영역의 콘텐츠 축과 폭을 유지합니다. 여유 공간을 더 준다고 두 번째 왼쪽 가장자리를 만들거나 작은 액션이 영역을 꽉 채우게 하지 마세요.
- **D-ALIGN-19 · SHOULD** 제품 고유의 여백과 대상 크기는 새 기초 값이나 범용 컴포넌트 기본값이 아니라 애플리케이션 별칭으로 두세요.
- **D-ALIGN-20 · SHOULD** **두 레이아웃 가장자리나 간격이 같아야 한다면, 1 픽셀 차이도 결함입니다.** 허용되는 오차는 글리프 광학 보정 (D-ALIGN-21) 뿐입니다.
- **D-ALIGN-21 · SHOULD** 비대칭 글리프의 광학 보정은 별도로 문서화한 에셋/컴포넌트 결정으로 다루고, 지원하는 크기에서 재사용하되 형제 간격, 기준선, 축은 정확하게 유지하세요.

광학 보정은 스크린숏이 균형 잡혀 보일 때까지 페이지 여백을 조금씩 밀어도 된다는 허락이 아닙니다.

### 선택, 링크, 그 밖의 의미상의 거짓말

- **D-SEM-1 · MUST** **선택은 지속되는 상태이며 절대 호버처럼 보이지 않습니다.** _Proof: browser_

호버는 일시적입니다. 현재 항목을 호버와 같은 채움으로 표시하면, 인터페이스가 하나의 모양에 두 가지 이름을 붙이는 셈입니다.

- **D-SEM-2 · MUST** **액션과 링크의 역할은 구별할 수 있게 남습니다.** _Proof: browser_
- **D-SEM-3 · SHOULD** 인라인 링크는 주변 본문과 함께 확인하세요. 액션 색과 본문 색이 우연히 같은 테마도 포함합니다.

**링크는 떠나고, 버튼은 실행합니다.**

- **D-SEM-4 · MUST** 애플리케이션 상태를 바꾸는 것은 어떻게 보이든 버튼입니다. _Proof: review, browser_
- **D-SEM-5 · SHOULD** 버튼 모양의 링크에는 밑줄을 넣지 마세요.

### 좁은 창 안의 명령 위계

- **D-CMD-1 · SHOULD** **컨트롤의 어포던스를 지우지 않으면서 불필요한 묶음 테두리를 없애세요.**

설정 창 안에서는 제목, 정렬, 근접성이 묶음을 만들지만, 그것만으로는 아이콘과 레이블이 클릭할 수 있어 보이지 않습니다.

- **D-CMD-2 · SHOULD** 익숙한 메뉴/목록 패턴이 이미 액션임을 전한다면 평평한 행을 쓰세요. 모든 맥락에서 그렇게 하라는 것은 아닙니다.
- **D-CMD-3 · SHOULD** 그것이 필요한 독립 명령에는 절제된 자체 버튼 표면이나 기능적인 선을 주고, 지원하는 모든 테마에서 호버 전부터 보이게 하세요.
- **D-CMD-4 · SHOULD** 대상은 버튼 자체의 모양이 알려 주게 하세요. 감싸는 카드, 흐린 묶음 채움, 행 구분선도 여전히 고유 경계 시험 (D-BOX-5) 을 통과해야 합니다.
- **D-CMD-5 · MUST** 처음 발견할 때 호버, 포인터 커서, 동사 레이블, 키보드 포커스 중 하나에만 의존하지 않습니다. _Proof: browser_
- **D-CMD-6 · SHOULD** 포인터를 치운 상태에서 창 전체의 평소 모습을 살펴보세요. 터치 사용도 포함합니다.
- **D-CMD-7 · MUST** 컨트롤을 발견한 뒤에도 호버, 누름, 비활성, 키보드 포커스는 서로 구별됩니다. _Proof: browser_
- **D-CMD-8 · SHOULD** 긴 번역 레이블은 들쭉날쭉한 가로 버튼 무리로 늘어놓지 말고 하나의 명령 열 안에서 줄바꿈하세요.
- **D-CMD-9 · MUST** 즉시 실행되는 명령에 내비게이션 꺾쇠를 붙이지 않습니다. _Proof: review_
- **D-CMD-10 · SHOULD** 이웃한 체크박스나 컨트롤과 공유하는 보이는 열을 밝히세요. 버튼 사각형이나 명령 묶음 안의 정렬만이 아니라 아이콘/체크박스 가장자리와 텍스트 Range 를 측정하세요.
- **D-CMD-11 · MAY** 그 열을 지키기 위해 히트 대상이 자기 몫의 여백까지 뻗어도 됩니다. 그 확장에는 이름을 붙이세요.
- **D-CMD-12 · MUST** 확장된 히트 대상은 자기 창 안에 머물고, 다른 대상과 겹치지 않으며, 포커스가 계속 보입니다. _Proof: browser_
- **D-CMD-13 · SHOULD** 파괴적인 명령은 복구·이전 액션과 떨어뜨려 두세요.
- **D-CMD-14 · SHOULD** 평소의 모든 명령에 커다란 빨간 외곽선을 두르지 말고 위험 레이블과 아이콘으로 의도를 전하세요. 가장 강한 위험 채움은 명시적인 확인 단계에 아껴 두세요.
- **D-CMD-15 · MUST** 파괴적인 명령은 확인, 취소, 포커스 복귀, 처리 중 중복 방지를 유지합니다. _Proof: browser_
- **D-CMD-16 · SHOULD** 명령 창은 호버 상태만이 아니라 평소 상태를 기준으로 검증하세요.

검증 범위는 평소 상태에서의 발견 가능성, 선언한 공유 열, 창 전체의 경계 위계, 대상 범위, 레이블 잘림, 대비, 상호작용 상태입니다.

- **D-CMD-17 · SHOULD** 실제 렌더링도 직접 살펴보세요. 표면 차이를 자동으로 검사하면 보이지 않는 컨트롤 채움은 잡아내지만, 사용자가 그 액션을 알아본다는 것까지 증명하지는 못합니다.
- **D-CMD-18 · SHOULD** 기초 역할과 거친 입력의 대상 크기 요건을 재사용하세요. 이 지침으로 컴포넌트 기본값이 바뀌지는 않습니다.

### 하나의 제품, 하나의 토큰 세트

- **D-TOKEN-1 · SHOULD** 제품의 권위 있는 의미 토큰을 쓰세요. 별칭으로 읽기 쉽게 만들 수는 있지만, 경쟁하는 팔레트를 새로 만들지 말고 그 원천에서 값을 가져오세요.
- **D-TOKEN-2 · SHOULD** 서드파티 컴포넌트는 지원되는 테마 API 로 맞추고, 합쳐진 결과를 확인하세요.

### 밀도는 컨트롤 역할을 따른다

간격, 고유 치수, 히트 대상은 서로 다른 문제를 풉니다. 작은 글리프에도 더 큰 네이티브 버튼 대상이 있을 수 있습니다.

- **D-TOKEN-3 · SHOULD** 실제 히트 범위, 포커스, 이웃 간격을 측정하세요.
- **D-TOKEN-4 · SHOULD** 반복되는 호스트 별칭은 한 애플리케이션의 치수를 라이브러리 전체에 복사하지 말고 기초 토큰에서 끌어내세요.
- **D-TOKEN-5 · SHOULD** 모든 글리프를 키우거나 숨겨진 컨트롤 자리를 잡아 두지 말고, 실제 입력 방식에 맞게 대상 범위를 고르세요. 지원되는 공개 테마 API 를 쓰세요.
- **D-TOKEN-6 · MUST** 아이콘만 있는 컨트롤에는 접근 가능한 이름을 붙입니다. _Proof: browser_
- **D-TOKEN-7 · SHOULD** 정당한 뷰포트, 헤어라인, 아트워크, 광학 기하 예외는 문서로 남기세요.

### 완성도는 증거로 평가한다

완성도는 카드, 블러, 등장 효과의 프리셋이 아니라 작업의 명확함에서 나옵니다.

- **D-CRAFT-1 · SHOULD** 실제 같은 객체, 문구, 상태로 의도한 시각 방향을 고르세요. 텅 빈 범용 껍데기로는 제품 품질을 세울 수 없습니다.

작업용 인터페이스는 오래 읽고 자주 조작해야 하고, 마케팅 페이지는 다른 구성이 필요할 수 있습니다.

- **D-CRAFT-2 · SHOULD** 가장 작은 개입을 실제 콘텐츠, 언어, 기기, 반복 사용에 비추어 평가하세요.

주요 참고 자료는 각각 구체적인 질문에 답합니다:
[Linear 의 위계](https://linear.app/now/behind-the-latest-design-refresh),
[Geist 타이포그래피](https://vercel.com/geist/typography),
[광학 정렬](https://craft.gustavofior.com/optical-alignment),
[중단 가능성](https://craft.gustavofior.com/interruptibility).

- **D-CRAFT-3 · SHOULD** 그 원칙들은 호스트의 토큰과 실제 역량에 맞게 변형하세요. 어떤 제품의 픽셀 크기를 베끼거나 레시피를 규칙으로 들여오지 마세요.
- **D-CRAFT-4 · SHOULD** 참고 자료는 추가 지시 세트가 아니라 결정의 입력으로 다루세요. 예를 들어 [Don't Make Me Think](https://sensible.com/dont-make-me-think/)는 훑어보기, 위계, 분명한 선택지에 대한 판단을 돕습니다.

[taste-skill](https://github.com/leonxlnx/taste-skill)은 의도한 방향과 비평에,
[ryugi](https://github.com/Innei/ryugi)는 실행 가능한 작업과 최신 증거에 도움을 줍니다.

- **D-CRAFT-5 · SHOULD** 스타일 취향에는 맥락이 필요하고, 요구 사항은 그것이 지키는 작업이나 관찰 가능한 계약을 밝혀야 합니다.
- **D-CRAFT-6 · SHOULD** 참고 자료는 그것이 돕는 일에 따라 고르세요. 로고/앱 아이덴티티, 마케팅 구성, 자주 쓰는 작업용 상호작용은 서로 다른 문제를 풉니다.
- **D-CRAFT-7 · SHOULD** 관찰한 패턴과 그 변형을 기록하고, 결과는 실제 콘텐츠로 확인하세요.

선택 자료인 [리서치 색인](./REFERENCE_RESEARCH.md)은 출처를 질문에 연결하고, 규칙 세트를 더하지 않고 이렇게 옮겨 쓰는 방법을 보여 줍니다.

- **D-CRAFT-8 · SHOULD** 방향이 정해지지 않았다면, 같은 콘텐츠·폭·테마로 실제 호스트에서 작은 변형 두 개를 만들어 한 번에 한 가지 차원만 바꿔 비교하세요. 각 차이가 작업에 무엇을 해 주는지 설명하세요.

방향이 분명하거나 작은 수정이라면 바로 진행합니다. 반드시 거쳐야 하는 승인 의식은 없습니다.

- **D-CRAFT-9 · SHOULD** 짧은 제목은 `text-wrap: balance`로 점진적으로 균형을 맞추고, 일반 줄바꿈은 유지하세요.
- **D-CRAFT-10 · MUST** 제목에는 로케일에 따라 달라지는 수동 줄바꿈이 없고, 스크린숏을 지키려고 잘리지도 않습니다. _Proof: browser_
- **D-CRAFT-11 · SHOULD** 길게 바뀌는 콘텐츠에 `pretty`를 쓰기 전에 비용과 지원 여부를 확인하세요.
- **D-CRAFT-12 · SHOULD** 글꼴이 지원하면 표 형식 숫자로 숫자 폭을 고정하세요.
- **D-CRAFT-13 · SHOULD** 99 → 100 처럼 자릿수가 바뀌는 경우를 위해 의미 있는 열을 잡아 두세요.
- **D-CRAFT-14 · MUST** 자릿수가 바뀌어도 값이 잘리지 않습니다. _Proof: browser_
- **D-CRAFT-15 · SHOULD** 비대칭 글리프는 재사용 가능한 에셋/컴포넌트에서 보정하고, 레이아웃 축은 정확하게 유지하세요.
- **D-CRAFT-16 · SHOULD** 중첩 모서리 기하는 실제 여백에서 끌어내고, 불필요한 중첩 표면부터 없애세요.
- **D-CRAFT-17 · SHOULD** 모션에는 할 일을 주세요: 자주 일어나는 일엔 즉시 피드백, 중단 가능한 전환, 모션 줄이기, 즉시 바뀌는 테마. §5 를 참고하세요.
- **D-CRAFT-18 · MUST** 선택적인 즐거움 요소가 타이핑을 늦추거나 상태를 가리지 않습니다. _Proof: recording_
- **D-CRAFT-19 · SHOULD** 화면 밖의 장식은 멈추고, 비용이 큰 효과를 쓰기 전에 실제 같은 콘텐츠로 프로파일링하세요.

### 말도 인터페이스의 일부다

- **D-COPY-6 · SHOULD** 불필요한 보조 레이블과 설명은 피하세요. 설명은 레이아웃이 하게 하세요.
- **D-COPY-7 · SHOULD** 제목, 묶음, 근접성, 누가 봐도 분명한 컨트롤에는 그 목적을 되풀이하는 문장이 따로 필요 없습니다.

- **D-COPY-9 · MUST** 접근 가능한 이름, 필드 레이블, 단위, 오류, 위험 고지는 남깁니다. _Proof: browser_
- **D-COPY-10 · SHOULD** 처음 쓰는 사람에게 유용한 안내는 남기고, 작업이 여전히 이해되는지 시험하세요.
- **D-COPY-11 · SHOULD** 맥락은 맥락에 맡기세요: `User Management`가 아니라 `Users`. 대화상자 본문에서 그 질문을 되풀이하지 마세요.

- **D-COPY-13 · MUST** `Cancel`은 아무것도 확정하지 않고 나갑니다. _Proof: browser_
- **D-COPY-14 · SHOULD** 문장형 대소문자를 쓰고, 짧은 레이블에는 마침표를 찍지 말며, 설명하는 문장에는 마침표를 찍으세요.
- **D-COPY-15 · SHOULD** 완료 전에 입력이 더 필요한 액션에는 `…`을 하나 붙이세요. 모두 대문자는 짧은 상태, 머리 레이블 (eyebrow), 약어에만 쓰세요.

- **D-REVIEW-1 · SHOULD** 영향을 받는 화면과 닿을 수 있는 바뀐 상태에 이 질문들을 적용하세요. 관련 없는 변형은 건너뛰세요. 작은 패치 때문에 상관없는 페이지를 다시 디자인할 필요는 없습니다. 범위 안에서 나온 "아니요"는 발견 사항입니다.

2. 모든 컨트롤의 레이블, 상태, 결과가 하나의 일관된 결과를 말하나요?
3. 강조가 아껴 쓰였나요? 핵심에 무게가 실리고 색, 배지, 주요 버튼은 드문가요?
4. 덜어 낼 수 있나요? 작업을 약하게 만들지 않고 없앨 수 있는 진입점, 옵션, 상태가 있나요?
5. 이름 붙인 축이 중첩 상태와 빈 상태까지 포함해 보이는 텍스트/콘텐츠 층에서 정확한가요? 내비게이션 열은 의도한 것이고 이중 패딩은 없나요?
6. 이웃한 컨트롤들이 선언된 아이콘/텍스트 열을 공유하나요?
7. 제목의 히트 영역이 콘텐츠만큼만 감싸나요?
8. 반복되는 세로 관계가 담당이 하나인 일관된 간격을 쓰나요? 줄바꿈된 문구와 숨겨진 보조/오류 콘텐츠도 포함해서요.
9. 본문이 실제 문자 체계, 글꼴, 확대 수준에서 읽기 편한가요? 그리고 본문이 **아닌** 모든 것은 그 폭 제한에서 자유로운가요?
10. 하나의 객체로 보이는 요소들이 테두리, 반경, **그리고** 간격에서 모두 일치하나요? 잡아 둔 열마다 실제로 콘텐츠가 있나요? 오래 남는 테두리, 채움, 구분선이 같은 묶음을 다시 감싸는 대신 저마다 고유한 경계를 전하나요?
11. 영향을 받는 범위에서 바뀐 상태들, 즉 빈 상태, 로딩, 실패, 긴 번역, 좁은 폭, 지원 테마, 모션 줄이기, **RTL**에서도 유지되나요?
12. 레이아웃이나 상호작용이 바뀌었다면, 영향받는 화면을 관련 폭과 테마로 실제 브라우저에서 확인했나요? 독립 액션이 터치 사용을 포함해 호버 전에 알아볼 수 있고, 불필요한 묶음 테두리는 없나요?

정상 경로의 스크린숏 한 장으로는 키보드 동작, 포커스, 동적 콘텐츠, 크기 조절, 실패 복구를 증명할 수 없습니다.

- **D-REVIEW-2 · SHOULD** 독립적인 기대값, 실제 런타임/캡처의 정체, 브라우저 측정, 그리고 자동·에이전트·사람의 결과를 서로 분리하는 일은 [ACCEPTANCE](./ACCEPTANCE.md)를 따르세요.

소스 저장소에만 있는 [브라우저 예시](https://github.com/chaxus/ran/blob/main/packages/ranui/test/e2e/layout-contract.md)에는
설정 명령과 테스트 유틸리티 세부 내용이 들어 있습니다. 이것들은 공개 패키지 API 가 아닙니다.

## 10. 정보 구조 — 구성보다 형태가 먼저

- **D-IA-1 · SHOULD** 정보가 빽빽한 콘솔, 대시보드, 작업대에서는 구성보다 구조를 먼저 고르세요.

API 데이터가 빠짐없다고 해서 페이지 디자인이 되는 것은 아닙니다. 읽는 사람에게는 여전히 객체와 그 상태, 관계를
이해하고 그다음 행동하기 위한 분명한 순서가 필요합니다.

- **D-IA-2 · SHOULD** 단일 전환 페이지와 랜딩 페이지에는 빽빽한 콘솔 템플릿이 아니라 그 작업에 맞는 구조를 주세요.

### 컴포넌트 이름을 대기 전에 세 가지 질문에 답한다

- **D-IA-3 · SHOULD** 컴포넌트를 고르기 전에 세 가지 답을 모두 정하세요.

1. **도착했을 때 무엇을 봐야 하나요?** 그것이 주요 정보입니다.
2. **그것이 이해되려면 무엇이 함께 보여야 하나요?** 관련 리소스, 관련 모델, 맥락.
3. **그다음 무엇을 하나요?** 판단하거나, 행동하거나, 계속 생각합니다.

- **D-IA-4 · SHOULD** **한 페이지에는 주요 모델이 정확히 하나입니다.** 보조 모델은 그것을 이해하거나 조작하는 데 도울 수 있지만, 첫 화면을 두고 경쟁해서는 안 됩니다.
- **D-IA-5 · SHOULD** 임의의 클릭 수 예산보다 분명하고 헷갈리지 않는 다음 선택을 우선하세요. 목적지에 닿을 수 있는지만이 아니라, 읽는 사람이 다음 액션을 알아보는지 시험하세요.

### 형태는 데이터가 아니라 작업을 따른다

- **D-IA-6 · SHOULD** 뼈대는 API 배열이나 라우트 ID 가 아니라 읽는 사람의 질문에서 골라, 아래 표를 참고하세요.

| 작업                                    | 쓸모 있는 형태                                |
| --------------------------------------- | --------------------------------------------- |
| 값/차이 비교                            | 표나 diff                                     |
| 리소스를 알아보고 열기                  | 목록. 이미지가 식별 수단일 때만 이미지 그리드 |
| 한 객체의 현재 상태 이해                | 섹션으로 나눈 상세                            |
| 소유/의존 관계 이해                     | 트리나 인접 목록. 경로가 중요할 때만 그래프   |
| 다음 단계 계획 / 작업을 단계별로 옮기기 | 단계 흐름 / 옮기는 일 자체가 작업일 때 칸반   |
| 무엇이 언제 누구에 의해 일어났는지 감사 | 타임라인이나 추적 드릴다운                    |
| 이어지는 텍스트를 논의하거나 읽기       | 스레드나 문서                                 |
| 상태, 추세, 이상 판단                   | 상태 월이나 대시보드                          |
| 점유/충돌이나 위치 찾기                 | 캘린더나 지도/캔버스                          |
| 다음 항목 처리 / 규칙 변경              | 마스터 - 디테일 작업대 / 설정 폼              |

- **D-IA-7 · SHOULD** 과거의 이벤트와 앞으로의 단계, 필터와 칸반, 순서 있는 산문과 필드 그리드를 혼동하지 마세요. 날짜가 있다는 것만으로 캘린더를 쓸 이유가 되지는 않습니다.
- **D-IA-8 · SHOULD** 여러 화면은 각각이 필터/상태/액션을 유지할 만한 고유한 작업에 쓰일 때만 내보내세요.

### 정보마다 제자리가 있다

- **D-IA-9 · SHOULD** 아래 표처럼 제목이나 요약 영역에서 정체와 상태를 먼저 보여 주고, 액션·피드백·근거는 그 대상 곁에 두세요.

| 정보   | 있어야 할 곳                                   | 잘못된 곳                       |
| ------ | ---------------------------------------------- | ------------------------------- |
| 정체   | 제목, 객체 요약                                | 마지막 열이나 탭 뒤             |
| 상태   | 제목이나 요약 영역                             | 상세 필드에서만 찾을 수 있음    |
| 속성   | 상세 본문. 사람이 생각하는 방식대로 묶음       | API 필드 순서대로 평평하게 나열 |
| 관계   | 자기 영역이나 탭. 소유, 의존, 참조를 구분      | 속성 표에 섞임                  |
| 변경   | diff 영역, 타임라인                            | 새 값만 보여 줌                 |
| 근거   | 판단 곁에, 펼칠 수 있게                        | 다른 곳의 로그 페이지           |
| 액션   | 주요 액션은 제목 영역에, 나머지는 그 대상 곁에 | "더 보기" 아래 묻힘             |
| 피드백 | 액션 곁에, 작업 맥락을 유지한 채               | 대상과 떨어진 전역 토스트       |

- **D-IA-10 · SHOULD** **모든 사실에는 권위 있는 위치가 정확히 하나 있습니다.** 다른 곳에서는 요약을 보여 주거나 그곳으로 돌아가는 진입점을 둡니다.
- **D-IA-11 · SHOULD** 기본 읽기 순서를 따르세요: 페이지 정체 → 현재 상태나 예외 → 주요 작업과 주요 액션 → 판단에 필요한 정보 → 관계, 변경, 근거 → 부차적인 정보와 드물게 쓰는 액션.
- **D-IA-12 · SHOULD** **작업 영역마다 주요 액션은 하나**이고, 그것은 가장 파괴적인 것이 아니라 가장 가능성 높은 다음 단계입니다 (얼마나 무게를 줄지는 §9 의 "강조는 예산이다"가 정합니다).

### 밀도는 단위 면적당 컨트롤 수가 아니라 유효한 정보다

간격을 좁히면 시각적 밀도는 올라가지만 유효 밀도는 그대로입니다. 관련 없는 필드를 없애고 비교할 것을
한곳에 모아야 진짜 밀도가 올라갑니다.

- **D-IA-13 · SHOULD** **한 페이지에는 이웃한 밀도 단계를 최대 두 개까지만 쓰세요.** 넉넉함은 처음 사용과 위험한 확인에, 표준은 대부분의 목록과 상세에, 촘촘함은 전문가용 작업대에 씁니다.
- **D-IA-14 · MAY** 컨테이너 패딩과 행간은 좁혀도 됩니다.
- **D-IA-15 · MUST** 읽을 수 있는 본문 글자, 보이는 포커스 링, 포인터 대상 크기는 밀도에 따라 줄어들지 않습니다 (§7, §8). _Proof: browser_

### 컨테이너로 구조를 고칠 수는 없다

- **D-IA-16 · SHOULD** **한 화면에는 맥락상 돌아가기가 하나뿐입니다.** 바깥의“채팅으로 돌아가기”와 안쪽의“아티팩트로 돌아가기”를 함께 보여 주지 마세요.
- **D-IA-17 · SHOULD** 상세 화면은 바로 위 부모로 돌아갑니다.
- **D-IA-18 · MUST** 조상은 라우트 계층이나 이름이 분명한 브레드크럼으로 계속 닿을 수 있습니다. _Proof: browser_
- **D-IA-19 · SHOULD** 포커스 복귀와 긴 번역 목적지 이름을 포함해 전체 이동 경로를 확인하세요.
- **D-IA-27 · MUST** 부모로 돌아가면 포커스가 출발한 항목으로 돌아옵니다. _Proof: browser_
- **D-IA-20 · MUST** 텍스트가 들어가지 않으면 다시 배치하거나 의미 있는 더 짧은 목적지 이름을 씁니다. 말줄임표나 툴팁이 유일한 목적지 단서를 가리지 않습니다. _Proof: browser_
- **D-IA-21 · SHOULD** 부모 맥락에는 하나의 구성을 고르세요. 불필요한 돌아가기 바로가기의 이름만 바꾸려고 브레드크럼을 더하거나, 돌아가기 명령 위에 같은 부모를 동작하지 않는 크럼으로 되풀이하지 마세요.

부모를 거쳐 돌아가는 것만으로 이미 조상에 닿는다면, 상세 헤더에 행을 더하지 않아도 접근성은 유지됩니다.

- **D-IA-22 · SHOULD** 브레드크럼은 계층 자체가 작업에 도움이 될 때 쓰세요.

**모달은 내비게이션 레이어가 아닙니다.**

- **D-IA-23 · SHOULD** 복사할 수 있는 링크, 방문 기록, 나란히 비교, 새로 고침 뒤에도 남는 작업이 필요한 것에는 라우트를 주세요.
- **D-IA-24 · SHOULD** 모달은 짧은 확인이나 필드 하나에, 팝오버나 메뉴는 일시적인 맥락에, 펼침 행은 점진적 공개에 쓰세요.
- **D-IA-25 · SHOULD** **탭은 한 객체의 대등한 화면을 담습니다.** 그 객체의 대화, 검사, diff 처럼요. 서로 관련 없는 모듈을 담지는 않습니다. 그건 내비게이션의 일입니다.
- **D-IA-26 · SHOULD** 고른 라이브러리에 알맞은 기본 요소가 없다면 기존 시맨틱 요소와 호스트 토큰을 쓰세요. 지원하지 않는 API 를 지어내지 말고 필요한 상호작용을 확인하세요.

## 검증 체크리스트 (UI 를 내보내기 전에)

- **D-VERIFY-1 · SHOULD** 영향받는 화면, 지원하는 변형, 바뀐 동작에 맞춰 검사를 고르세요. 목록을 채우려고 관련 없는 흐름을 만들지 마세요.

저장소 CI 는 여전히 전체 게이트를 실행합니다.

- **D-VERIFY-2 · SHOULD** 주요 작업과 주요 액션을 착각할 여지가 없어야 합니다.

영향받는 레이아웃/테마 변경은 관련된 **좁은 폭과 넓은 폭**, 지원하는 테마에서 동작합니다 (D-INPUT-1).
마우스와 터치 모두 동작합니다. 드래그는 Pointer Events 를 쓰고, `trigger="hover"`에는 탭 대체 경로가 있습니다 (D-INPUT-3,
D-INPUT-4). 키보드와 보이는 포커스는 D-ACCESS-3 과 D-ACCESS-4 가 다룹니다.

- **D-VERIFY-5 · SHOULD** 바뀐 모든 **상태**(호버, 활성, 포커스, 비활성, 로딩, 빈 상태, 오류) 를 직접 해 보세요.
- **D-VERIFY-7 · SHOULD** 관련된 경계 사례를 다루세요: 긴 텍스트, 큰 숫자, 호스트가 지원하는 문자 체계/로케일.
- **D-VERIFY-8 · SHOULD** 간격은 스케일에서, 글자는 역할에서, 색은 의미 토큰에서 옵니다.
- **D-VERIFY-9 · SHOULD** 호스트에 해당하는 검사를 실행하고 실제 브라우저 증거를 살펴보세요.
- **D-VERIFY-10 · SHOULD** 문구는 §6 을 따릅니다.

색만으로 상태를 알리는 문제는 D-ACCESS-2 가 다룹니다.

- **D-VERIFY-12 · SHOULD** 빽빽한 화면이라면: 주요 모델은 하나, 뼈대는 데이터가 아니라 질문에서 고르고, 모든 사실에는 권위 있는 위치가 하나 (§10).
