# UI の検証 — 証拠と判断

視覚や操作の結果が変わるときは、この契約を使います。見た目と構成は [DESIGN](./DESIGN.md) が、観察できる振る舞いは [INTERACTION](./INTERACTION.md) が持ちます。タスクの振り分けは[インターフェース索引](./INTERFACE_GUIDE.md)が行います。当てはまる節だけを読んでください。

各ルールには ID と等級が付いています。**MUST** は破れば欠陥であり、その証拠の種類を明記します。**SHOULD** は既定であり、外れるときはその場合の理由を述べます。**MAY** は任意です。[ルール索引](./RULES.md)に、等級付きのすべてのルールとその証拠をまとめています。

## 観察できる結果について合意する

- **V-AGREE-1 · SHOULD** 編集の前に[デザインブリーフ](./DESIGN.md#style-coherence-across-components-and-pages)を決め、影響するタスク、画面／状態、独立した期待値を同じメモに書きます。
- **V-AGREE-2 · SHOULD** 関係する持ち主、サポートされた公開 API、ホストの能力の限界を明示します。
- **V-AGREE-3 · SHOULD** 幅、テーマ、言語、入力経路は、無関係な作業を作り出さずに、実際の変更から選びます。
- **V-AGREE-4 · SHOULD** 構成については、内容／テキスト／アイコンの背骨、意図したナビゲーションのカラム、ヒット範囲、縦の関係を明示します。
- **V-AGREE-5 · MUST** 期待値を、テスト対象の実装から導かないでください。_Proof: review_
- **V-AGREE-6 · SHOULD** レビューは、タスク／階層、静的な構成、たどり着ける組み合わせの状態、そして動き、の順に行います。
- **V-AGREE-7 · SHOULD** 解決していない比率やはっきりしないナビゲーションを補うために、アニメーションを足さないでください。
- **V-AGREE-8 · SHOULD** レビューによって意図したデザインが変わるときは、まず既存のブリーフを更新し、そのきっかけになった証拠を示します。

これは判断の記録であって、ユーザーがすでに許可した作業に対する新しい承認の儀式ではありません。

API／トークンの検査はソースの契約を、画像の比較はピクセルを、エージェントの実行はガイダンスに従ったかどうかを検証します。

- **V-AGREE-9 · SHOULD** ルールの持ち主はひとつに保ちます。
- **V-AGREE-10 · MUST** ある種類の検査で別の種類の検査を代用させないでください：API／トークンの検査、画像の比較、エージェントの実行は、それぞれ自分の結果だけを示します。_Proof: review_
- **V-AGREE-11 · MUST** フィクスチャーが示すのは自分自身の結果であって、それが描画していないホストアプリケーションの検証ではありません。ホストの検証として主張しないでください。_Proof: review_

## ブラウザーでの証拠

- **V-PROOF-1 · MUST** 目に見える欠陥を再現するときは、修正の前に、実際に動いている面をキャプチャします。_Proof: browser_
- **V-PROOF-2 · MUST** 修正の後に、同じ関係する状態をキャプチャし、実際に近い文言と周囲の外枠を含めてパネル全体を確かめます。_Proof: browser_
- **V-PROOF-3 · MUST** モックアップ、ソースの差分、変更したアサーション、無関係なビルドのスクリーンショットを証拠として出さないでください。_Proof: review_
- **V-PROOF-4 · SHOULD** リンクの数だけでなく構成も確かめます：冗長な戻るリンクをパンくずリストに付け替えても、同じ文脈を繰り返し、不要なヘッダーの行を増やしていることがあります。
- **V-PROOF-5 · SHOULD** 別の見えるショートカットが必要だと決める前に、親を通って祖先にたどり着けるかを確かめます。
- **V-PROOF-6 · MUST** 測る前に、コンポーネントの登録、保留中の内容、フォント、描画されたフレームを待ちます。_Proof: browser_
- **V-PROOF-7 · MUST** ターゲットがない、または大きさがゼロなら失敗とします。_Proof: browser_
- **V-PROOF-8 · MUST** サブピクセルの許容範囲はすべて記録し、正確であるべき背骨では CSS の 1px 未満に保ちます（ソースの例では 0.5px を使います）。_Proof: review_
- **V-PROOF-9 · MUST** 動いているオーバーレイについては、キャプチャがビューポートを保ち、トリガー／パネル全体を含むことを確かめます。ページ全体のスクリーンショットは、レスポンシブな再配置やポータルの位置の付け直しを引き起こして、切り抜きを無効にすることがあります。_Proof: browser_
- **V-PROOF-10 · MUST** 欠陥のある層を測ります：ラッパー、内側の内容、描画されたテキストの Range、アイコンのビューポート、実際のポインターのターゲットはそれぞれ別物です。Range は正確な字形のインクではありません。_Proof: browser_
- **V-PROOF-11 · MUST** シャドウパーツは、サポートされたテストの継ぎ目を通して扱います。検証のために、本番コードにシャドウへの問い合わせを持ち込まないでください。_Proof: review_
- **V-PROOF-12 · SHOULD** 影響する再配置、折り返した翻訳、任意の内容、入力経路を試します。
- **V-PROOF-13 · MUST** 静止したスクリーンショットを、フォーカスの戻り、キーボードナビゲーション、タッチでの見つけやすさ、中断可能性、非同期の落ち着きの証拠として使わないでください。_Proof: review_
- **V-PROOF-14 · MUST** 欠陥が時間とともに展開するときは、連続した操作を録画します。_Proof: recording_
- **V-PROOF-15 · MUST** レイアウトのアサーションについては、それが関係する欠陥を確かに拒否することを証明します：枠を固定したままラベルのテキストだけを動かす、二重のマージンや幻の補助要素を持ち込む、タイトルのターゲットを埋め草まで広げる、など。_Proof: browser_
- **V-PROOF-16 · MUST** 変異がカスケードで勝ったことを確かめ、失敗を観察し、元に戻して成功を観察します。_Proof: browser_
- **V-PROOF-17 · SHOULD** 小さな修正のために例のテスト一式をすべて繰り返すのではなく、タスクに関係する変異を使います。
- **V-PROOF-18 · MUST** 表示を変えるときは、生のデータを確かめます。_Proof: browser, unit_
- **V-PROOF-19 · MUST** コードについては、強調表示された DOM のテキストではなく、ソースのペイロードをコピーします：タブ、空行、最後の改行、ストリームで追加された部分を保ちます。_Proof: unit_
- **V-PROOF-20 · MUST** クリップボードの成功／失敗、ネイティブの選択、長い行のスクロールを、それぞれ独立して確かめます。_Proof: browser_
- **V-PROOF-21 · MUST** ブラウザーによる選択の正規化は文書化し、それが生のクリップボードのペイロードを変えないようにします。_Proof: unit, review_

ソースにのみある[レイアウトの例](https://github.com/chaxus/ran/blob/main/packages/ranui/test/e2e/layout-contract.md)には、実行できるコマンドと幾何のユーティリティが含まれます。利用側はその関係を自分のホストに合わせて取り入れます。これらの補助関数は新しい ranui の export ではありません。

- **V-PROOF-22 · MUST** CSS の zoom による負荷テストから、ブラウザー本来のズームや文字サイズのアクセシビリティ対応を主張しないでください。_Proof: review_
- **V-PROOF-23 · MUST** どの経路が未検証のまま残っているかを述べます。_Proof: review_

### 時間軸で動きをレビューする

- **V-MOTION-1 · MUST** 変わった動きについては、連続した操作を通常の速度で確かめ、遷移が崩れる箇所はゆっくり再生します。_Proof: recording_
- **V-MOTION-2 · MUST** 起動、途中の状態、完了、逆の経路を含め、完了前に入力を繰り返したり反転させたりします。_Proof: recording_
- **V-MOTION-3 · MUST** 最終状態、フォーカス、イベントの回数、読んでいる位置は、アニメーションとは独立して確かめます。_Proof: browser_
- **V-MOTION-4 · MUST** ゆっくりした再生は、途切れを診断するために使い、フレームレートのベンチマークとしては使いません。_Proof: review_
- **V-MOTION-5 · MUST** モーション軽減には、短い録画だけでなく、それ自体の見える状態の確認を与えます。_Proof: browser_
- **V-MOTION-6 · SHOULD** 時間軸の欠陥は `element → input → observed frame/state → expected continuity` の形で報告します。
- **V-MOTION-7 · SHOULD** 影響を受ける兄弟コンポーネントをまたいで代表的な実際のタスクをひとつ使い、モーションの言葉の不一致を見つけます。
- **V-MOTION-8 · SHOULD** 局所的な修正の後に、構成全体をもう一度確かめます。
- **V-MOTION-9 · SHOULD** 失敗した試行は診断材料として、採用したキャプチャとは分けて残します。

これらの確認は、下にある既存の証拠の結び付けを補うものです。

## タスクを通して歩く

- **V-WALK-1 · SHOULD** ワークフローや構成が変わったときは、使うべきコントロールを名指しせずに表した、実際に近い目標から始めます。
- **V-WALK-2 · SHOULD** 関係する範囲で、実際の入口から結果、復旧、戻りまで、目標をやり遂げます。
- **V-WALK-3 · SHOULD** 最初の選択、あいまいなラベル、ためらいや引き返し、そして結果が次の一歩をはっきりさせるかを記録します。

選択肢がはっきりしないなら、クリックの経路が短くても役に立ちません。

- **V-WALK-4 · SHOULD** 整った空の状態だけでなく、代表的な長いケースや失敗するケースを含めて、実際に近い内容を使います。
- **V-WALK-5 · SHOULD** 装飾的な効果を足す前に、タスクの構造と内容の階層を直します。
- **V-WALK-6 · SHOULD** 観察したうちでもっとも影響の大きい問題（最大 3 つ）を、それぞれを示す状態と証拠とともに報告します。
- **V-WALK-7 · MUST** 数を満たすために指摘をでっち上げないでください。_Proof: review_
- **V-WALK-8 · SHOULD** 修正の後に、影響を受ける経路をもう一度たどります。
- **V-WALK-9 · MUST** エージェントによるウォークスルーは、人間によるユーザビリティ調査ではなく、欠陥の探索として報告します。_Proof: review_
- **V-WALK-10 · SHOULD** 実際の参加者を観察するときは、インターフェースを説明する前に目標に挑戦してもらい、その区別を下の結果でも保ちます。

## 証拠を、実際に動いたものに結び付ける

レビューした状態ごとに、次の項目を持つ簡潔な記録を残します：

- **V-FRESH-1 · MUST** ランタイム：テストしたソースのリビジョン／ビルドと、関係する未コミットの入力またはそのフィンガープリントを記録します。結果に影響するなら、共有のスタイル／コンポーネントや取り込むデータも含めます。動いているビルドや作業ツリーが異なるなら、Git の HEAD だけでは不十分です。_Proof: review_
- **V-FRESH-2 · MUST** 範囲／環境：関係する範囲で、影響する画面／グループの所属、ルート／状態、ビューポート、テーマ、ロケール、ブラウザー、入力やモーション軽減の設定を記録します。_Proof: review_
- **V-FRESH-3 · MUST** メディア：キャプチャ／録画の保存場所と内容の識別（たとえば SHA-256）を、そのランタイムと状態に結び付けて記録します。_Proof: review_
- **V-FRESH-4 · MUST** 修正前と修正後は区別したままにします。唯一の修正前の画像を決して上書きしません。_Proof: review_
- **V-FRESH-5 · MUST** レビュー：自動の検査とエージェントの確認が実際に何を示したかを、人間の判断や未検証の状態とは分けて記録します。_Proof: review_
- **V-FRESH-6 · MAY** 短い Markdown の記録を使ってかまいません。既存のマニフェストがこれらの項目を提供してもかまいません。
- **V-FRESH-7 · SHOULD** 普通の変更のために、新しい証拠のサービスや設定の枠組みを足さないでください。
- **V-FRESH-8 · MUST** 主張した結び付けを独立して確かめられるように、ハッシュはファイルの隣か、参照するマニフェストに置きます。_Proof: review_

**レビューが当てはまるのは、それが確かめた証拠とランタイムの範囲だけです。**

- **V-FRESH-9 · MUST** 画像を差し替えた、録画を編集した、グループの所属を変えた、関係するランタイムの入力を変えた、といった後は、影響するレビューを古いものとして扱います。_Proof: review_
- **V-FRESH-10 · MUST** 共有のスタイル／コンポーネントを変えた後は、影響するすべての状態を更新し、必要ならビルドし直し、そのうえで新しい証拠を確かめます。_Proof: browser, review_
- **V-FRESH-11 · MUST** 古いキャプチャを現在の証拠として出しません。_Proof: review_
- **V-FRESH-12 · MUST** ドキュメントだけの編集や無関係なソースの変更をまたいでランタイムの証拠を保つときは、その依存の範囲が影響を受けない理由を記録します。_Proof: review_

古いキャプチャは履歴として残してかまいません。ドキュメントだけの編集や無関係なソースの変更では、同一のランタイムの証拠は有効なままなので、HEAD が変わっただけですべてをキャプチャし直す必要はありません。

## 権限を偽りなく報告する

| 結果                       | それを示せる人／もの                                                       | それが示さないもの           |
| -------------------------- | -------------------------------------------------------------------------- | ---------------------------- |
| 自動の検査                 | 宣言したランタイムに対する、新しいコマンドの出力やブラウザーのアサーション | 視覚的な質、または人間の判断 |
| エージェントの視覚レビュー | エージェントが現在のキャプチャと影響する操作を確かめた                     | ユーザーによる検証           |
| 人間の判断                 | 実際のユーザーの判断。そのメッセージ／アクションへの参照と証拠の範囲を伴う | 後で変わった証拠に対する検証 |

- **V-REPORT-1 · MUST** 一段落の報告であっても、この 3 つの結果は分けておきます。_Proof: review_
- **V-REPORT-2 · MUST** それぞれの結果は、上の表が挙げる出どころからだけ主張し、表が示さないとしているものについては決して主張しません。_Proof: review_
- **V-REPORT-3 · SHOULD** `automated: passed`、`agent review: passed with limits`、`human: not requested` のような明示的な結果を使います。
- **V-REPORT-4 · MUST** 人間のレビューを依頼していて、まだ済んでいないなら、`pending` と書きます。_Proof: review_
- **V-REPORT-5 · MUST** ユーザーが却下したなら、そのユーザーが更新後の範囲をレビューするまで、`rejected` とその指摘を残します。_Proof: review_
- **V-REPORT-6 · MUST** エージェントは自分の修正と新しい検査を報告してかまいませんが、ユーザーの判断をでっち上げたり、人間による却下を取り消したりは決してしません。_Proof: review_
- **V-REPORT-7 · MUST** 誰によるものか示さない「accepted」「approved」「验收通过」を避けます。_Proof: review_

push するか、PR を更新するか、その他の外部のアクションをとるかを決めるのは、ユーザーの許可です。この文書は、包括的な人間の承認ゲートを何も加えません。

- **V-REPORT-8 · SHOULD** 許可された作業は最後までやり遂げて届け、`not requested`／`pending` は偽りなく報告します。
- **V-REPORT-9 · SHOULD** 尋ねるのは、実際の許可か必要な製品上の判断が欠けているときだけにします。
- **V-REPORT-10 · MUST** エージェント自身の視覚的な確認を、決して「user accepted」と表記しません。_Proof: review_

最小限の納品メモは、たとえば次のようになります：

> ランタイムと範囲：ビルド／ソース …；状態／環境 …；関係する入力のフィンガープリント …
> 証拠：修正前／修正後／操作 …；識別の記録先 …
> 自動：コマンド／結果 …
> エージェントのレビュー：観察した結果、残っている指摘や限界 …
> 人間の判断：not requested / pending / 実際の判断と参照 …
> 未検証：…；許可された PR／更新：…

## ガイダンス自体の回帰

決定的な対照検査はモデルを呼ばずに評価者を確かめます。ライブ実行には利用できるエージェントの実行環境が必要で、文章を編集するたびに必須となるゲートではありません。

- **V-EVAL-1 · SHOULD** スキル／振り分け／検証の変更を、任意で、またはタスクで許可されてライブ評価するときは、ソースにのみある[6 つのエージェントのシナリオ](https://github.com/chaxus/ran/tree/main/plugins/ran/evals)を使います。
- **V-EVAL-2 · MUST** ライブ実行の前に、タスク、フィクスチャー、ツール、独立した採点基準を固定します。_Proof: review_
- **V-EVAL-3 · MUST** モデル／設定を揃えた新しいセッションを使います。_Proof: review_
- **V-EVAL-4 · MUST** 基準となるガイダンスと候補のガイダンスを、別々のワークスペースに固定します。_Proof: review_
- **V-EVAL-5 · MUST** エージェントの実際の作業、プロンプト、結果の検査、証拠を残します。_Proof: review_
- **V-EVAL-6 · MUST** 基準側の合格は対照として、候補側の失敗は失敗として記録します。_Proof: review_
- **V-EVAL-7 · MUST** 作業者に、評価者のしきい値や修正パッチを見せないでください。_Proof: review_

欠陥を仕込んだうえでの拒否／復元の検査が、評価者の感度を示します。

- **V-EVAL-8 · MUST** それらのタスクでの振る舞いは、エージェントのライブ実行からだけ主張します。文章の一致、手書きの解答、修正したテストの期待値は、その証拠になりません。_Proof: review_
- **V-EVAL-9 · MUST** 視覚的な判断は、機械的な検査とは独立して確かめます。_Proof: review_
- **V-EVAL-10 · MUST** サンプルの大きさ、ツール、扱えていない条件を報告します。_Proof: review_
- **V-EVAL-11 · MUST** 6 つのタスクが成功しても、モデルをまたいだ信頼性の証明にはなりません。そこから主張しないでください。_Proof: review_
