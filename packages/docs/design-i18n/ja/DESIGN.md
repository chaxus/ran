# Ran Design

ホストとなる製品と、その製品がすでに持っている技術のための設計方法です。[タスク索引](./INTERFACE_GUIDE.md)からたどって、関係する節だけを読んでください。ライブラリのトークンや API の仕組みは、この持ち運べる方法ではなく、それぞれの実装アダプターに属します。

各ルールには ID と等級が付いています。**MUST** は破れば欠陥であり、その証拠の種類を明記します。**SHOULD** は既定であり、外れるときはその場合の理由を述べます。**MAY** は任意です。[ルール索引](./RULES.md)に、等級付きのすべてのルールとその証拠をまとめています。

## 1. 色 — パレットではなく状態のはしご

- **D-COLOR-1 · SHOULD** 内容、面、境界、アクション、ステータスに意味的な役割を割り当てます。
- **D-COLOR-2 · SHOULD** 既定、ホバー、アクティブ、無効、フォーカスの各状態をまとめて定義します。
- **D-COLOR-3 · SHOULD** ライト／ダークの値はホストの正式なトークンを通して解決し、実際の構成の中でコントラストを確かめます。

ブランドのアクセントは文脈に応じて使います。

## 2. 余白 — 限られた、リズムのあるスケール

- **D-SPACE-1 · SHOULD** ホストに既にある余白スケールを使います。
- **D-SPACE-2 · SHOULD** 関連する部品は狭い間隔でまとめ、タスクや領域は広い間隔で分けます。
- **D-SPACE-3 · SHOULD** 外側の間隔より先に、内側の余白を決めます。
- **D-SPACE-4 · SHOULD** 内容、密度、入力方法を検討せずに、参考にした製品の寸法を写さないでください。

## 3. 文字 — 大きさではなく役割を選ぶ

- **D-TYPE-1 · SHOULD** 見出し、ラベル、本文、アクション、コードの役割を、大きさ・太さ・行の高さが一貫した形で選び、役割ごとに決める場所をひとつに保ちます。
- **D-TYPE-2 · SHOULD** 実際の文字体系、フォールバックフォントの寸法、長い内容で確かめます。
- **D-TYPE-3 · SHOULD** 装飾的な入れ物より先に、文字で階層をつくります。

## 4. 角丸と高さ

- **D-ELEV-1 · SHOULD** 入れ子になった角丸は、実際の内側余白に合わせます。内側の半径 = 外側の半径 − 内側余白です。結果が 2px 以下なら形は同心に見えなくなるので、内側の形には自分の役割の半径を与えるか、角丸をなくします。

8px の内側余白を持つ 16px のカードなら、内側のパネルは 8px の角丸になります。同じカードでも内側余白が 16px なら引き継ぐものは残らないので、パネルは自分の役割が使う角丸を取ります。

- **D-ELEV-2 · SHOULD** 高さ（影）は重要度ではなく浮いた層を説明するために、ホストの重なりの役割を通して使い、周囲の外枠に対してオーバーレイを確かめます。

## 5. モーション — 基本はなし

以下のタイミングは出発点となる目安です。

- **D-MOTION-1 · SHOULD** ホストシステムのモーショントークンを使い、頻度、連続性、モーション軽減を実際のタスクの中で確かめます。

| 長さ   | 用途                                                                       |
| ------ | -------------------------------------------------------------------------- |
| 0ms    | 頻繁なホバー、フォーカス、キーボードのフィードバック。すでに理解された変化 |
| ~150ms | 任意で目的のある小さな動き。必須のホバー遅延ではありません                 |
| ~200ms | 層の変化をはっきりさせるときのメニュー／ポップオーバーの動き               |
| ~300ms | 位置の把握に役立つときのダイアログの動き                                   |

**原則：** 動きに時間を使う価値があるかは、目的と頻度で決まります。

- **D-MOTION-2 · SHOULD** 繰り返す操作は即時のフィードバックを既定にします。変化が大きいことは、それだけでアニメーションさせる理由にはなりません。
- **D-MOTION-3 · SHOULD** 目的のある動きには既存のトークンを使い、短く、中断できるように保ちます。モーション軽減は D-MOTION-10 と D-ACCESS-5 で等級付けしています。

### 機能的なモーションの契約

- **D-MOTION-4 · SHOULD** 効果を選ぶ前に、きっかけ、状態の変化、行き先を決めます。
- **D-MOTION-5 · MUST** 動きは、無関係な内容、下書き、読んでいる位置を保ちます。_Proof: recording_
- **D-MOTION-6 · SHOULD** 同じ操作上の意味を持つ兄弟コンポーネントには、共通のモーションの言葉を与えます。一貫性とは、すべてのコンポーネントを動かすことではありません。
- **D-MOTION-7 · MUST** 動きを使う場合、新しい意図は現在の表示から動きを中断または反転でき、飛び、古い完了、二重の起動を生みません。_Proof: recording_
- **D-MOTION-8 · MUST** フィードバックは即時のままにします。アニメーションは入力のロックではありません。_Proof: recording_
- **D-MOTION-9 · SHOULD** 挿入や削除のあいだ、文字が目に見えて押しつぶされたり、退場するコントロールが生きているアクションの上を横切ったりしないようにします。不透明度とレイアウトを連携させて、結果が読めるようにします。
- **D-MOTION-10 · MUST** モーション軽減時も、目に見えて理解できる最終状態を保ちます。_Proof: browser_
- **D-MOTION-11 · MAY** スプリングを使ってかまいません。行き過ぎ（オーバーシュート）は必須ではありません。

例と限界は任意の[コンポーネントの作り込みに関する調査](./REFERENCE_RESEARCH.md#component-craft-设计垂点--wxaddesign)を、証拠のとり方は[時間軸の検証](./ACCEPTANCE.md#review-motion-over-time)を参照してください。

- **D-MOTION-12 · SHOULD** テーマのパレットはまとまって切り替わるようにします。暗黙のパレットのフェードや `transition: all` は避け、ホストが意図して確かめた連携効果の箇所でだけ明示的に有効にします。
- **D-MOTION-13 · MUST** 作業面に戻ったとき、事実の値と読める内容は、数値のカウントアップなしにすぐ表示します。_Proof: browser_
- **D-MOTION-16 · SHOULD** 作業面に戻るたびに、装飾的なタイトルの登場演出を再生しないでください。
- **D-MOTION-17 · SHOULD** 登場の動きは、その領域が何を持つかによって下の表から選びます。時間差は、ページ全体ではなく、ひとつの領域の中で読む順に付けます。

| 領域が持つもの                                         | 登場                                                                             | その後                                                           |
| ------------------------------------------------------ | -------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| テキスト、見出し、値、フォーム、ナビゲーション、CTA    | なし。最初の描画で表示済み（D-MOTION-13）                                        | なし                                                             |
| テキストに添えた装飾的な図：アイコン群、図解、スケッチ | transform のみ、初めてスクロールで見えたときに一度。読み込み時に見えていればなし | 画面上にあるあいだ、説明的なループを動かしてもよい（D-CRAFT-19） |
| 製品のモックアップやライブデモ                         | 内容にはなし。読み込みの実演は動いてもよい（D-MOTION-14）                        | 読み手自身の操作で動く                                           |
| ステータス表示                                         | なし                                                                             | 活動が続いているあいだだけ脈動する（D-MOTION-15）                |

モーション軽減時は、どの領域も最終状態から始まります（D-MOTION-10）。

- **D-MOTION-14 · MAY** 読み込みの実演は、読み込みを示すために動いてもかまいません。
- **D-MOTION-15 · MUST** ステータスの脈動は、活動が続いているあいだだけ表示します。_Proof: review_

## 6. 内容 — 文言もシステムの一部

- **D-COPY-1 · SHOULD** ボタンは結果を名指しします。文脈で対象が決まらないときは対象を含めます：「プロジェクトをデプロイ」「メンバーを削除」。対象がはっきり名付けられた画面やダイアログでは「保存」「削除」で十分です。汎用的な「OK」は避けます。[文脈に応じた言葉](#words-are-part-of-the-interface)を参照してください。
- **D-COPY-2 · SHOULD** エラーは**何が起きたか**を述べ、次に**どう直すか**を述べます。✅「ビルドに失敗しました：バンドルがサイズ上限を超えています。小さくするか上限を引き上げてください。」 ❌「操作に失敗しました。もう一度お試しください。」
- **D-COPY-3 · SHOULD** 確認やトーストは、完了した**変化**を述べます。✅「プロジェクトを削除しました」。❌「操作に成功しました」。
- **D-COPY-4 · MUST** 完了のフィードバックは、操作が確認されてから表示します。_Proof: unit, browser_
- **D-COPY-5 · SHOULD** 具体的に書きます。どの文も推測を増やすのではなく、取り除くものにします。

## 7. アクセシビリティ — システムはすべての人のために

- **D-ACCESS-1 · MUST** テキストは背景に対して十分なコントラストを保ちます（**WCAG AA**）。 _Proof: browser_
- **D-ACCESS-2 · MUST** 状態を色だけで示さず、アイコンかテキストと組み合わせます（例：緑／赤だけでなく ✓ / ✕ のラベル）。_Proof: review_
- **D-ACCESS-3 · MUST** すべての操作可能な要素は、その面にふさわしい**目に見えるフォーカスリング**を持ちます。「すっきりさせる」ために消してはいけません。_Proof: browser_
- **D-ACCESS-4 · MUST** **キーボードだけですべて操作できること**：マウスでしかできない操作はありません。_Proof: browser_
- **D-ACCESS-5 · MUST** `prefers-reduced-motion` を尊重します。_Proof: browser_
- **D-ACCESS-6 · MUST** ホストが両方の配色に対応しているなら、最初の描画は `prefers-color-scheme` に従います。_Proof: browser_

## 8. 入力とビューポート — モバイルとデスクトップの両方

- **D-INPUT-1 · MUST** 狭い幅でも広い幅でも、マウス、キーボード、タッチに対応します。_Proof: browser_
- **D-INPUT-2 · MUST** アクションへの唯一の経路を隠すのではなく、コントロールを再配置します。_Proof: browser_
- **D-INPUT-3 · MUST** ホバーで示す手がかりには、クリック／タップの代替があります。_Proof: browser_
- **D-INPUT-4 · MUST** ドラッグはキャンセルも含めて Pointer Events を使います。_Proof: browser_
- **D-INPUT-5 · MUST** `touch-action` は実際のドラッグ面に限定して実際のハンドラーと組み合わせ、それ以外の場所では通常のスクロールが動き続けるようにします。_Proof: browser_
- **D-INPUT-6 · SHOULD** 恣意的なブレークポイントより、内容やビューポートに対する相対的な境界（`min()`、`max()`、`clamp()`）を優先します。
- **D-INPUT-7 · SHOULD** ホストの既存のブレークポイントを使い、同じ必要が繰り返し現れたときにだけ、根拠のある共通の役割を導入します。

測った位置は、リサイズ、コンテナの再配置、スクロールのあとでは古くなります。

- **D-INPUT-8 · SHOULD** 狭いレイアウトで読み込むだけでなく、狭いレイアウトへのリサイズも試します。
- **D-INPUT-9 · MUST** 開いているあいだ、オーバーレイの位置はトリガーに追従します。_Proof: browser_

ライフサイクルの仕組みはホストが持ちます。[ranui のエンジニアリング](https://github.com/chaxus/ran/blob/main/packages/ranui/docs/CODING.md#3-state-and-ownership)は実装アダプターのひとつです。

- **D-INPUT-10 · SHOULD** 影響がある箇所では、実際のポインター／タッチのジェスチャー、ホバーの代替、キーボードの経路を試します。ふたつの配色を確かめても、入力の同等性は示せません。

## 9. 構成 — コンポーネントではなくページ

- **D-COMP-1 · SHOULD** まず §10 のページ構造を選び、そのうえでこれらのルールに従ってコンポーネントを組み立てます。

### コンポーネントとページをまたぐスタイルの一貫性

- **D-COMP-2 · SHOULD** 実装の前に、既存のタスクメモか製品デザインの担当先に短いデザインブリーフを記録します。既存のシステムを使います。小さな修正なら、影響する判断だけで足ります。ブリーフでは下の表のうち当てはまる判断をそれぞれ決めます（D-COMP-2）。

「高級感」「モダン」「Claude のように」は調べるべき方向であって、実装できる仕様ではありません。

| 判断             | ブリーフで決めること                                                                                         |
| ---------------- | ------------------------------------------------------------------------------------------------------------ |
| タスクと階層     | 実際の内容、主たるアクション、最初に読むべき焦点。何を退かせ、何をなくせるか。                               |
| 比率             | 文字の役割と行の高さ、行長、コントロールの密度、アイコンの太さ、揃えの背骨を、ホストのトークンで。           |
| 面の言葉         | どの領域に囲いが必要か、入れ子の角丸と内側余白の関係、意味的なアクセントと高さの役割。                       |
| 状態の組み合わせ | 代表的な既定に加え、長い内容、処理中／失敗、狭い幅の入力経路。組み合わさった状態も含めます。                 |
| モーション       | 説明する状態の変化、きっかけと頻度、中断／反転の振る舞い、モーション軽減時の結果。「なし」も有効な答えです。 |
| 参考の判断       | 参考を使う場合は、出典へのリンク、採り入れた原則、ホストのタスクに必要な調整。                               |
| 検証             | 観察できる結果と、それを示すか否定できる実際の画面／録画。                                                   |

- **D-COMP-4 · SHOULD** ブリーフは兄弟コンポーネントやドキュメントの外枠でも使い回し、タスクに応じて強調を変えます。

統一とは、どこでも同じ大きさのコントロールや箱に入った節を並べることではありません。

- **D-COMP-5 · SHOULD** 表現力のあるデモは、ドキュメントの外枠とはっきり区別できるようにします。
- **D-COMP-6 · SHOULD** 視覚的な方向を変える前にブリーフを更新します。レビューで落ちた実装を正当化するために、黙って基準を書き換えないでください。
- **D-COMP-7 · SHOULD** アニメーションさせる前に、代表的な構成の静止画を別の実際の内容と比べ、そのうえで状態の変化と戻りの経路を通常の速度で確かめます。

共通の色だけでは、比率、アイコンの太さ、囲い方、動きの不一致は解消できません。

- **D-COMP-8 · SHOULD** ある例が別の製品から持ち込まれたように見えるときは、ページ固有の継ぎはぎを足すのではなく、その関係を持つトークン／コンポーネント／スタイルで直します。
- **D-COMP-9 · SHOULD** 参考の観察と検証の限界は、任意の[調査索引](./REFERENCE_RESEARCH.md#style-coherence-and-transition-research)に残します。

### 入れ物より先に構造を

- **D-BOX-1 · SHOULD** **箱を使う前に、余白、揃え、太さ、細い線を使います。**

入れ物は、その中身が独立した物体だという主張です。ほとんどの領域に必要なのは、背景、細い線、意図した余白だけです。

- **D-BOX-2 · SHOULD** 箱は**本当に独立した物体**のために取っておきます：ライブデモの舞台、オーバーレイ、浮いているパネル。コードブロック、表、リストの行、前へ／次へのリンク、ギャラリーのセルには使いません。
- **D-BOX-3 · SHOULD** **冗長な入れ子の入れ物と二重の余白を避けます。** 余白のあるパネルの中のカードに、さらに装飾的な枠や内側余白は要りません。
- **D-BOX-4 · SHOULD** 機能上必要な入れ子のコントロールや面は残し、その角丸を実際の内側余白に合わせます。囲うことそれ自体は、箱を足す理由になりません。
- **D-BOX-5 · SHOULD** **常に見えている境界には、それぞれ固有の役目が必要です。** 内容のまとまりは、まず見出し、揃え、近さでつくります。その構造で本当の境界がはっきりしない場合にだけ、枠線、面の塗り、高さを足します。
- **D-BOX-6 · SHOULD** 同じまとまりを、パネルの枠、入れ子のカード、行の罫線、さらに別の内側余白で同時に繰り返さないでください。

薄い線でも余分な階層であることに変わりはありません。コントラストを下げたり短くしたりしても、冗長な囲いは冗長なままです。

下の表は D-BOX-5 と D-BOX-8 を当てはめたものです。

- **D-BOX-8 · MUST** キーボードフォーカスと持続的な選択の手がかりは残します。静止時のレイアウトを静かにするために消してはいけません。_Proof: browser_

| 境界                         | 伝えているなら残す                                             | 繰り返しているだけなら外す                                             |
| ---------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------- |
| フィールド／コントロールの枠 | 値を入力できる場所、または選択できる場所                       | すでに読み取れるコマンドを包む装飾的なラッパー                         |
| 領域の枠や区切り線           | 独立したビューポート、リサイズの境界、タスクの大きな切り替わり | 同じまとまりをすでに明らかにしているタイトルと間隔                     |
| 入れ子の面                   | 独立した浮いた層、プレビュー、ドロップ先、操作の境界           | 既に成立している設定パネルの中の、さらなる入れ物                       |
| フォーカス／選択の輪郭       | キーボードフォーカス、または持続的な選択状態                   | 静止時のレイアウトがそれなしで静かに見えるとしても、この手がかりは残す |

- **D-BOX-9 · SHOULD** 切り抜いたまとまりだけでなく、パネルやページ全体をレビューします。残っている固定の輪郭、塗り、区切りのそれぞれについて、伝えている関係や操作を名指しし、外したら何があいまいになるかを確かめます。

枠は任意です。たどり着けて、それと分かるコントロールは任意ではありません。

### 強調は予算

**色、太さ、バッジ、塗り、高さは希少な資源です。** すべてを強調すると、どれも重要には読めません。

- **D-COMP-10 · SHOULD** 優先度はまず構造と近さで決め、強調はそれに値するひとつのものに使います。

**高さは重要度ではなく、重なりを説明します。**

- **D-ELEV-3 · SHOULD** 影は、本当に内容の上に浮く面のために取っておきます：ポップオーバー、メニュー、ダイアログ、通知。すべてのカードに影を付けないでください。

### 余白は意味を運ぶ

§2 のスケールはリズムであるだけでなく、各段階がひとつの関係を表します。

段階は、その間隔が何を*意味する*かで選びます（D-SPACE-2）：

| 関係                       | 相対的な余白                   |
| -------------------------- | ------------------------------ |
| ひとつのコントロールの部品 | 意図して取るいちばん狭い間隔   |
| 密接に関連するコントロール | コンパクトなグループの間隔     |
| ひとつの内容グループ       | グループのリズム               |
| 別々のグループ             | より大きな隔たり               |
| 大きな領域の境界           | 意図して取るいちばん強い隔たり |

**内側が先、外側が後：** コンポーネント自身の内側余白は、コンポーネントどうしの間隔より先に決めます（D-SPACE-3）。**間隔が狭いほど関係が密接** — 縦のリズムが伝えるのはそれだけです。

- **D-SPACE-6 · SHOULD** 装飾的な区切り線で、間隔が表す関係を打ち消さないでください。

### 兄弟ビューをまたぐ縦のリズム

- **D-SPACE-7 · SHOULD** 固定の高さではなく、関係を繰り返します。タイトル／説明、フィールド／補足、グループ、領域の間隔は、その関係に応じてホストのスケールから選びます。

これらは構成上の判断であって、普遍的なコンポーネントの寸法ではありません。

- **D-SPACE-8 · SHOULD** 翻訳による伸びは自然に任せ、説明がないときに空いた行を残さないでください。
- **D-SPACE-9 · SHOULD** 各間隔の持ち主はひとつにします：親のスタックか、子の明示的なマージンか。個別に書かれた見出し／段落のマージンは、親の間隔に上乗せするのではなくリセットします。
- **D-SPACE-10 · SHOULD** コントロール自身の内側余白、マージンの相殺、インラインのベースラインの余白を勘定に入れます。transform や小さな文字で埋め合わせないでください。
- **D-SPACE-11 · SHOULD** 補足は、それが説明するフィールドやアクションのそばに置きます。
- **D-SPACE-12 · MUST** 非表示の補助要素が、意図しない間隔を残さないこと。_Proof: browser_
- **D-SPACE-16 · SHOULD** 非同期のステータス用に確保した行には、明示した目的と範囲があります。内容が落ち着いてから両方向を測ります。[ACCEPTANCE](./ACCEPTANCE.md) ではこれを V-PROOF-6 として等級付けしています。

`next.top - previous.bottom` が測るのは枠どうしの隔たりであって、字形や行ボックスの余白ではありません。

- **D-SPACE-14 · SHOULD** 行送り、内側余白、細い線は区別します。16px の内側余白と 1px の罫線は、17px の余白トークンではありません。
- **D-SPACE-15 · SHOULD** 独立した期待値を使い、折り返し、リサイズ、補足／エラーの表示、関係する密度を試します。

二重のマージン、幻の行、テキストだけのずれに対する、落ち着きの待ち方と変異による検査は [ACCEPTANCE](./ACCEPTANCE.md#browser-proof) が持ちます。

### 行長が制限するのはテキストであって、カラムではない

- **D-TYPE-4 · SHOULD** **実際の文字体系とフォントに合った、読みやすい行長を選びます。**

ラテン文字の文章なら 1 行 60〜75 文字が出発点の目安ですが、あらゆる文字体系に通じる範囲ではありません。

- **D-TYPE-5 · SHOULD** 対応する幅、ズーム倍率、フォールバックフォントで、実際に近いテキストをレビューします。CJK や複数の文字体系が混じるテキストには、それぞれの判断が必要です。

[WCAG の視覚的提示](https://www.w3.org/WAI/WCAG22/Understanding/visual-presentation.html)も、レベル AAA の達成基準で CJK を区別しています。これはライブラリの必須の既定ではありません。

- **D-TYPE-6 · SHOULD** 表、コードブロック、デモの舞台、画像には、内容が必要とする幅を保たせます。制限するのはテキスト要素であって、それを収めるカラムではありません。
- **D-TYPE-7 · SHOULD** **行長は `rem` で宣言し、`em` は使いません。**

`em` は要素自身のフォントサイズに対して解決されるので、文字が大きいほど行が長くなります。まさに逆です。

- **D-TYPE-8 · SHOULD** **箱に手を伸ばす前に、文字で階層をつくります。**

大きさを一段上げ、色を一段下げるだけで、タイトルと最初の文は、タイトルとリード文になります。新しい入れ物も新しい枠線も要りません。

### レイアウトがふたつのものをひとつの物体だと言うなら、余白も同じことを言う

**共有した枠線、共有した角丸、そしてそのあいだの隙間は矛盾しています。**

- **D-ALIGN-1 · SHOULD** 要素がひとつの物体かふたつの物体かを決め、すべてのプロパティに同じことを言わせます。
- **D-ALIGN-2 · SHOULD** **ある値が別の値と等しくなければならないなら、名前を付けます。** 子が差し引かなければならない間隔は、2 か所に書かれたリテラルではなく、2 回参照されるひとつのカスタムプロパティです。

### カラムは内容があるときだけ確保する

**無条件に宣言したカラムは、そこに入れるものが何もないページでもカラムのままです。**

- **D-ALIGN-3 · SHOULD** トラックの条件は、それを暗示すると思い込んだページ種別ではなく、要素が実際にあること（`:has()`）にします。

### 揃えは仕上げではなく構造

- **D-ALIGN-4 · SHOULD** **揃えの背骨それぞれに名前を付け、それが揃える幾何を明示します。** どの兄弟がどの背骨を共有するかを述べます。ヘッダー、本文、行、アクション、空／読み込み中／エラーの内容も含めます。

ページの内容の背骨、ナビゲーションのカラム、入れ子のフォームラベルの背骨が意図して異なることはあります。

- **D-ALIGN-5 · SHOULD** 戻るボタンと間隔によって、別のタイトルのカラムができることがあります。そのタイトルを黙って本文に揃っているものとして扱わないでください。
- **D-ALIGN-6 · MUST** 任意のアイコンやバッジがないことで、ラベルが宣言したカラムから動くことはありません。_Proof: browser_
- **D-ALIGN-7 · SHOULD** 入れ子の階層は、終わったときに親の背骨へ正確に戻ります。正しいボックスどうしを比べてください。たまたま一致していても、これらは別々の測定です。欠陥のある層を測ることは、[ACCEPTANCE](./ACCEPTANCE.md) で V-PROOF-10 として等級付けしています。

| 幾何                   | 測るもの                                                                                          |
| ---------------------- | ------------------------------------------------------------------------------------------------- |
| 枠                     | `getBoundingClientRect()` によるラッパー／ホストのボーダーボックス                                |
| 内容                   | 実際の枠線と内側余白を除いた内側の端。入れ子のラッパーも含みます                                  |
| テキスト               | 描画されたラベルのテキストノードを囲む DOM の `Range`。折り返しには最初／最後の行の矩形を使います |
| アイコンのビューポート | SVG／viewBox または画像のボックス。描かれた字形のインクはその中で非対称なことがあります           |
| ヒット領域             | 実際のイベントの対象と、そのホバー／フォーカスの面。端の近くの点で確かめます                      |

ボタンの枠が段落に揃っていても、そのテキストが揃っている証明にはなりません。内側余白によって、枠が固定されたままラベルが動くことがあります。`Range` が与えるのは組版上の幾何であって、正確な字形のインクではありません。

- **D-ALIGN-9 · SHOULD** 字形の視覚補正は別に確かめます。Web Components では、ホスト、文書化されたシャドウパーツ、スロットに入ったテキストを、サポートされたテストの継ぎ目を通して測ります。これは [ACCEPTANCE](./ACCEPTANCE.md) の V-PROOF-11 が持ち、本番コードでのシャドウへの問い合わせの禁止や、文書の CSS が境界を越えると思い込むことの禁止も含みます。
- **D-ALIGN-11 · SHOULD** **ヘッダーのコマンドのヒット領域を、レイアウトの埋め草と分けます。** タイトル／メニューのトリガーは、使える幅の範囲で、内容と意図した余白にぴったり沿わせます。残りの空間は別の flex／grid のトラックに吸収させます。
- **D-ALIGN-12 · SHOULD** 長い翻訳に対する切り詰め／折り返しと、隣接するアクションの振る舞いを決めます。
- **D-ALIGN-13 · MUST** D-ALIGN-14 が当てはまる場合を除き、タイトルのトリガーのヒット領域は、ヘッダーの使われていない空間に広がりません（たとえばタイトルボタンへの `flex: 1` によって）。_Proof: browser_
- **D-ALIGN-14 · SHOULD** 意図して幅全体で選択する行は別の役割です。その契約を明示的に記録します。
- **D-ALIGN-15 · MAY** 粗いポインター向けのターゲットは大きくしてかまいません。
- **D-ALIGN-22 · SHOULD** 大きくしたターゲットのホバーの塗りは、無関係な内容にまたがらず、コントロール自身の内容に留めます。
- **D-ALIGN-16 · SHOULD** **共通の祖先から見えるテキストまでの、すべての内側余白を数えます。** 親の内側余白、入れ子のパネルの内側余白、コントロール内部の内側余白、枠線、ナビゲーションのカラムがすべて寄与します。
- **D-ALIGN-17 · SHOULD** 冗長な内側余白は、説明のない負のマージンで打ち消すのではなく、その持ち主のところで取り除きます。
- **D-ALIGN-18 · SHOULD** 空の状態でも、その領域の内容の背骨と幅を保ちます。ゆとりを足しても、ふたつ目の左端を生んだり、コンパクトなアクションを領域いっぱいに広げたりはしません。
- **D-ALIGN-19 · SHOULD** 製品固有の内側余白やターゲットの大きさは、新しい基盤の値や普遍的なコンポーネントの既定ではなく、アプリケーションの別名として保ちます。
- **D-ALIGN-20 · SHOULD** **ふたつのレイアウトの端や間隔が等しいはずなら、1px の違いは欠陥です。** 字形の視覚補正（D-ALIGN-21）だけが許容範囲です。
- **D-ALIGN-21 · SHOULD** 非対称な字形の視覚補正は、文書化した独立したアセット／コンポーネントの判断として扱い、対応する大きさで使い回します。そのあいだも兄弟の間隔、ベースライン、背骨は正確に保ちます。

視覚補正は、スクリーンショットが釣り合って見えるまでページのマージンを少しずつずらしてよいという許可ではありません。

### 選択、リンク、その他の意味の偽り

- **D-SEM-1 · MUST** **選択は持続的な状態であり、決してホバーのようには見えません。** _Proof: browser_

ホバーは一時的なものです。現在の項目にホバーと同じ塗りで印を付けると、インターフェースはひとつの見た目にふたつの名前を持つことになります。

- **D-SEM-2 · MUST** **アクションとリンクの役割は区別できるままにします。** _Proof: browser_
- **D-SEM-3 · SHOULD** インラインのリンクは周囲の文章に対して確かめます。アクションと本文の色がたまたま一致するテーマも含めます。

**リンクは移動し、ボタンは作用します。**

- **D-SEM-4 · MUST** アプリケーションの状態を変えるものは、見た目がどうであれボタンです。_Proof: review, browser_
- **D-SEM-5 · SHOULD** ボタンの形をしたリンクには下線を付けません。

### 限られたパネルの中のコマンドの階層

- **D-CMD-1 · SHOULD** **コントロールの手がかりを消さずに、冗長なグループの囲いを取り除きます。**

設定パネルの中では、見出し、揃え、近さがグループをつくります。ただしそれだけでは、アイコンとラベルはクリックできるようには見えません。

- **D-CMD-2 · SHOULD** 見慣れたメニュー／リストのパターンがすでにアクションを伝えているなら、平らな行を使います。あらゆる文脈で平らな行を求めるわけではありません。
- **D-CMD-3 · SHOULD** 必要とする単独のコマンドには、控えめな独自のボタンの面か機能的な線を与え、対応するすべてのテーマでホバー前から見えるようにします。
- **D-CMD-4 · SHOULD** ボタン自身の形でターゲットを示します。それを囲むカード、くすんだグループの塗り、行の罫線も、固有の境界のテスト（D-BOX-5）を通る必要があります。
- **D-CMD-5 · MUST** 最初に見つけられることを、ホバー、ポインターのカーソル、動詞のラベル、キーボードフォーカスのどれか単独に頼りません。_Proof: browser_
- **D-CMD-6 · SHOULD** ポインターを離した静止状態のパネル全体を、タッチでの利用も含めて確かめます。
- **D-CMD-7 · MUST** コントロールを見つけたあとも、ホバー、押下、無効、キーボードフォーカスは区別できるままにします。_Proof: browser_
- **D-CMD-8 · SHOULD** 長い翻訳のラベルは、不揃いな横並びのボタンの群れにせず、ひとつのコマンドのカラムの中で折り返します。
- **D-CMD-9 · MUST** 即時に実行されるコマンドに、ナビゲーション用のシェブロンを付けないでください。_Proof: review_
- **D-CMD-10 · SHOULD** 隣接するチェックボックスやコントロールと共有する、見えるカラムを宣言します。ボタンの矩形やコマンドグループ内の揃えだけでなく、アイコン／チェックボックスの端とテキストの Range を測ります。
- **D-CMD-11 · MAY** そうしたカラムを保つために、ヒットターゲットを自分の持つ余白（ガター）へ広げてもかまいません。その拡張には名前を付けます。
- **D-CMD-12 · MUST** 広げたヒットターゲットはパネルの内側に留まり、他のターゲットと重ならず、フォーカスが見えるままです。_Proof: browser_
- **D-CMD-13 · SHOULD** 破壊的なコマンドは、復旧や移行のアクションと分けます。
- **D-CMD-14 · SHOULD** 危険のラベルとアイコンで意図を伝え、静止状態のすべてのコマンドに大きな赤い輪郭を付けないでください。いちばん強い危険の塗りは明示的な確認のために取っておきます。
- **D-CMD-15 · MUST** 破壊的なコマンドは、確認、キャンセル、フォーカスの戻り、処理中のガードを保ちます。_Proof: browser_
- **D-CMD-16 · SHOULD** コマンドのパネルは、ホバー状態だけでなく静止状態で検収します。

検収の範囲は、静止状態での見つけやすさ、宣言した共有カラム、パネル全体の境界の階層、ターゲットの範囲、ラベルの切れ、コントラスト、操作の状態です。

- **D-CMD-17 · SHOULD** 実際の描画も確かめます。面の差を自動で調べる検査は見えないコントロールの塗りを捉えますが、ユーザーがアクションを認識できることまでは証明しません。
- **D-CMD-18 · SHOULD** 基盤の役割と、粗い入力のターゲット要件を再利用します。このガイダンスはコンポーネントの既定を何も変えません。

### ひとつの製品に、ひとつのトークン群

- **D-TOKEN-1 · SHOULD** 製品の正式な意味的トークンを使います。別名は読みやすさを高めることがありますが、競合するパレットを作り出すのではなく、その出どころから解決します。
- **D-TOKEN-2 · SHOULD** サードパーティのコンポーネントは、サポートされたテーマ API を通して連携させ、組み合わせた結果を確かめます。

### 密度はコントロールの役割に従う

余白、固有の寸法、ヒットターゲットは、それぞれ別の問題を解きます。小さな字形が、より大きなネイティブのボタンのターゲットを持つこともあります。

- **D-TOKEN-3 · SHOULD** 実際のヒット範囲、フォーカス、隣接する間隔を測ります。
- **D-TOKEN-4 · SHOULD** 繰り返し使うホストの別名は、あるアプリケーションの寸法をライブラリ全体に写すのではなく、基盤トークンから導きます。
- **D-TOKEN-5 · SHOULD** すべての字形を大きくしたり隠れたコントロールのために場所を確保したりせずに、実際の入力方法に合ったターゲットの範囲を選びます。サポートされた公開テーマ API を使います。
- **D-TOKEN-6 · MUST** アイコンだけのコントロールには、アクセシブルな名前を付けます。_Proof: browser_
- **D-TOKEN-7 · SHOULD** ビューポート、細い線、アートワーク、視覚補正の幾何に関する正当な例外を文書化します。

### 作り込みは証拠で評価する

仕上げはタスクの明快さに従うもので、カード、ぼかし、登場演出の決まった組み合わせではありません。

- **D-CRAFT-1 · SHOULD** 実際に近い対象、文言、状態を使って、意図した視覚的な方向を選びます。汎用の空っぽの外枠では、製品の質を示せません。

作業用のインターフェースには、長く読み続けることと頻繁な操作が必要です。マーケティングのページには別の構成が必要なこともあります。

- **D-CRAFT-2 · SHOULD** 実際の内容、言語、端末、繰り返しの利用に照らして、いちばん小さな介入を評価します。

一次資料はそれぞれ特定の問いに答えます：
[Linear の階層](https://linear.app/now/behind-the-latest-design-refresh)、
[Geist のタイポグラフィ](https://vercel.com/geist/typography)、
[視覚的な揃え](https://craft.gustavofior.com/optical-alignment)、
[中断可能性](https://craft.gustavofior.com/interruptibility)。

- **D-CRAFT-3 · SHOULD** それらの原則を、ホストのトークンと実際にできることに合わせて取り入れます。ある製品のピクセル寸法や、取り込み手順をルールとして写さないでください。
- **D-CRAFT-4 · SHOULD** 参考は判断の材料として扱い、追加の指示書としては扱いません。たとえば [Don't Make Me Think](https://sensible.com/dont-make-me-think/) は、走り読み、階層、明快な選択肢について示唆を与えます。

[taste-skill](https://github.com/leonxlnx/taste-skill) は意図した方向づけと批評に、[ryugi](https://github.com/Innei/ryugi) は実行できる作業と新鮮な証拠に示唆を与えます。

- **D-CRAFT-5 · SHOULD** 好みの問題には文脈が要ります。要件であるなら、それが守るタスクか観察できる契約を明らかにします。
- **D-CRAFT-6 · SHOULD** 参考は、それが支える仕事で選びます。ロゴ／アプリのアイデンティティ、マーケティングの構成、頻繁な作業の操作は、それぞれ別の問題を解きます。
- **D-CRAFT-7 · SHOULD** 観察したパターンとその取り入れ方を記録し、結果を実際の内容で確かめます。

任意の[調査索引](./REFERENCE_RESEARCH.md)は、出典を問いに対応づけ、ルール群を増やさずにこの取り入れ方を示しています。

- **D-CRAFT-8 · SHOULD** 方向が定まらないときは、同じ内容、幅、テーマで、実際のホスト上の小さな案をふたつ比べ、一度にひとつの次元だけを変えます。それぞれの違いがタスクにとって何をするのかを説明します。

方向がはっきりしているときや小さな修正なら、そのまま進めます。必須の承認儀式はありません。

- **D-CRAFT-9 · SHOULD** 短い見出しは `text-wrap: balance` で段階的に釣り合わせ、通常の折り返しを保ちます。
- **D-CRAFT-10 · MUST** 見出しにはロケールに依存する手動の改行を入れず、スクリーンショットを保つために切り詰めません。_Proof: browser_
- **D-CRAFT-11 · SHOULD** 長く動的な内容に `pretty` を使う前に、コストと対応状況を確かめます。
- **D-CRAFT-12 · SHOULD** フォントが対応していれば、等幅数字を使って数字の送り幅を安定させます。
- **D-CRAFT-13 · SHOULD** 99 → 100 のような桁数の変化に備えて、意味のあるカラムを確保します。
- **D-CRAFT-14 · MUST** 桁数が変わっても、値が切り詰められることはありません。_Proof: browser_
- **D-CRAFT-15 · SHOULD** 非対称な字形は、再利用できるアセット／コンポーネントの中で補正し、レイアウトの背骨は正確に保ちます。
- **D-CRAFT-16 · SHOULD** 入れ子の角の幾何は実際の内側余白から導きます。まず不要な入れ子の面を取り除きます。
- **D-CRAFT-17 · SHOULD** 動きには役目を与えます：頻繁な操作への即時のフィードバック、中断できる遷移、モーション軽減、即時のテーマ切り替え。§5 を参照してください。
- **D-CRAFT-18 · MUST** 任意の遊び心のある演出が、入力を遅らせたりステータスを覆い隠したりすることはありません。_Proof: recording_
- **D-CRAFT-19 · SHOULD** 画面外の装飾は止め、コストの高い効果を採り入れる前に、実際に近い内容で計測します。

### 言葉もインターフェースの一部

- **D-COPY-6 · SHOULD** 不要な補助ラベルや説明は避けます。説明はレイアウトに任せます。
- **D-COPY-7 · SHOULD** 見出し、グループ分け、近さ、見れば分かるコントロールに、その目的を繰り返す文は要りません。
- **D-COPY-8 · SHOULD** 新しい判断、制約、結果を何も加えない文言は取り除きます。装飾的なバッジやツールチップで置き換えないでください。
- **D-COPY-9 · MUST** アクセシブルな名前、フィールドのラベル、単位、エラー、リスクの開示は残します。_Proof: browser_
- **D-COPY-10 · SHOULD** 初回利用時に役立つ案内は残し、タスクが理解できるままかを試します。
- **D-COPY-11 · SHOULD** 文脈に文脈を語らせます：`User Management` ではなく `Users` とし、ダイアログの問いを本文で繰り返さないでください。
- **D-COPY-12 · SHOULD** 動作（`Click to save`）ではなく結果（`Save`、`Move`、`Delete`）を名指しします。対象は、文脈で決まらないときにだけ含めます。
- **D-COPY-13 · MUST** `Cancel` は確定せずに抜けます。_Proof: browser_
- **D-COPY-14 · SHOULD** 文頭だけを大文字にする書き方を使い、短いラベルには句点を付けず、説明の文には句点を付けます。
- **D-COPY-15 · SHOULD** 完了の前にさらに入力が必要なアクションには `…` をひとつ付けます。すべて大文字の表記は、短いステータス、アイブロウ（見出しの上の小見出し）、頭字語のために取っておきます。

### 組み立てた面のレビューチェックリスト

- **D-REVIEW-1 · SHOULD** 影響を受ける面と、たどり着ける変更後の状態に、以下の問いを当てはめます。関係のないバリエーションは飛ばします。小さな修正で無関係なページを作り直す必要はありません。範囲内の「いいえ」は指摘事項です。

1. 初めての読み手が、推測せずに目的と主たるアクションを見分けられますか？
2. 各コントロールのラベル、状態、結果は、一貫したひとつの結果を述べていますか？
3. 強調は希少ですか — 核となるものに重みがあり、色、バッジ、主ボタンはまれなままですか？
4. もっと少なくできませんか：タスクを弱めずに取り除ける入口、選択肢、状態はありませんか？
5. 名前を付けた背骨は、入れ子や空の状態も含めて、見えるテキスト／内容の層で正確ですか？ナビゲーションのカラムは意図したもので、二重の余白はありませんか？
6. 隣接するコントロールは、宣言したアイコン／テキストのカラムを共有していますか？
7. タイトルのヒット領域は内容に沿っていますか？
8. 繰り返す縦の関係は、折り返した文言や非表示の補足／エラーの内容も含めて、持ち主がひとつの一貫した間隔を使っていますか？
9. 流れる文章は、実際の文字体系、フォント、ズーム倍率で読みやすいですか？流れる文章で**ない**ものはすべて、その行長の制限から外れていますか？
10. ひとつの物体の一部に見える要素はすべて、枠線、角丸**そして**余白で一致していますか？確保したカラムにはすべて実際に内容がありますか？固定の枠、塗り、区切りのそれぞれは、同じグループをもう一度入れ子にするのではなく、固有の境界を伝えていますか？
11. 影響がある範囲で、変更後の関係する状態でも成り立ちますか：空、読み込み中、失敗、長い翻訳、狭い幅、対応するテーマ、モーション軽減、そして **RTL**。
12. レイアウトや操作の変更について、影響を受ける面を、関係する幅とテーマで実際のブラウザーで確かめましたか？単独のアクションは、タッチでの利用も含めてホバー前から認識でき、冗長なグループの囲いはありませんか？

順調な経路のスクリーンショットは、キーボードの振る舞い、フォーカス、動的な内容、リサイズ、失敗からの復旧を証明しません。

- **D-REVIEW-2 · SHOULD** 独立した期待値、実際のランタイム／キャプチャの同一性、ブラウザーでの測定、自動・エージェント・人間それぞれの結果の区別については [ACCEPTANCE](./ACCEPTANCE.md) に従います。

ソースにのみある[ブラウザーの例](https://github.com/chaxus/ran/blob/main/packages/ranui/test/e2e/layout-contract.md)には、セットアップのコマンドとテストユーティリティの詳細が含まれます。これらは公開パッケージの API ではありません。

## 10. 情報アーキテクチャ — 構成より先に形を

- **D-IA-1 · SHOULD** 情報の密度が高いコンソール、ダッシュボード、ワークベンチでは、構成より先に構造を選びます。

API のデータがすべて揃っていても、それはページのデザインではありません。読み手には、対象とその状態や関係を理解し、それから行動するための、はっきりした順序がやはり必要です。

- **D-IA-2 · SHOULD** 単一のコンバージョンのページやランディングページには、密なコンソールのテンプレートではなく、それぞれのタスクに合った構造を与えます。

### コンポーネントの名前を挙げる前に、3 つの問いに答える

- **D-IA-3 · SHOULD** コンポーネントを選ぶ前に、3 つの答えをすべて決めます。

1. **読み手は、着いたときに何を見る必要がありますか？** それが主たる情報です。
2. **それを理解するために、ほかに何が見えている必要がありますか？** 関連するリソース、関連するモデル、文脈。
3. **次に何をしますか？** 判断する、行動する、あるいは考え続ける。

- **D-IA-4 · SHOULD** **ページの主たるモデルはちょうどひとつです。** 補助的なモデルは読み手がそれを理解したり操作したりする助けになってよいですが、最初の画面を奪い合ってはいけません。
- **D-IA-5 · SHOULD** 恣意的なクリック数の予算より、明快であいまいさのない次の選択を優先します。行き先にたどり着けるかだけでなく、読み手が次のアクションを認識できるかを試します。

### 形はペイロードではなくタスクに従う

- **D-IA-6 · SHOULD** 骨組みは、API の配列やルートの ID ではなく読み手の問いから、下の表を使って選びます。

| タスク                                       | 役に立つ形                                           |
| -------------------------------------------- | ---------------------------------------------------- |
| 値や違いを比べる                             | 表または差分                                         |
| リソースを見分けて開く                       | リスト。画像がそれを識別する場合にだけ画像グリッド   |
| ひとつの対象の現在の状態を理解する           | 節に分けた詳細                                       |
| 所有関係や依存関係を理解する                 | ツリーまたは隣接リスト。経路が重要な場合にだけグラフ |
| 次の一歩を計画する／作業を段階に沿って進める | ステップの流れ／移すことそのものが作業ならカンバン   |
| いつ誰が何をしたかを監査する                 | タイムラインまたはトレースの掘り下げ                 |
| 議論する、または続いた文章を読む             | スレッドまたは文書                                   |
| 健全性、傾向、異常を判断する                 | ステータスウォールまたはダッシュボード               |
| 占有や衝突、場所を見つける                   | カレンダーまたは地図／キャンバス                     |
| 次の項目に取り組む／ルールを変える           | マスター・ディテールのワークベンチ／設定フォーム     |

- **D-IA-7 · SHOULD** 過去の出来事と将来の手順、フィルターとカンバン、順序のある文章とフィールドのグリッドを混同しないでください。日付があるというだけでは、カレンダーの理由になりません。
- **D-IA-8 · SHOULD** 複数のビューを出すのは、それぞれが、フィルター／状態／アクションの保守に見合う別個のタスクに役立つときだけにします。

### 情報の種類ごとに置き場所がある

- **D-IA-9 · SHOULD** 下の表のとおり、タイトルや概要の領域では識別とステータスを先に示し、アクション、フィードバック、証拠はその対象のそばに置きます。

| 情報           | 置き場所                                         | 間違った場所                       |
| -------------- | ------------------------------------------------ | ---------------------------------- |
| 識別           | タイトル、対象の概要                             | 最後の列、またはタブの奥           |
| ステータス     | タイトルまたは概要の領域                         | 詳細のフィールドでしか見つからない |
| 属性           | 詳細の本文。人の考え方に沿ってまとめる           | API のフィールド順に平らに並べる   |
| 関係           | 専用の領域かタブ。所有、依存、参照を区別する     | 属性の表に混ぜる                   |
| 変更           | 差分の領域、タイムライン                         | 新しい値だけを表示する             |
| 証拠           | 判断のそば。展開できる                           | どこか別のログページ               |
| アクション     | 主たるものはタイトルの領域、残りはその対象のそば | 「その他」の下に埋もれる           |
| フィードバック | アクションのそば。タスクの文脈を保つ             | 対象から切り離された全体のトースト |

- **D-IA-10 · SHOULD** **どの事実にも、正式な置き場所がちょうどひとつあります。** ほかの場所には、そこへ戻るリンクとなる概要か入口を表示します。
- **D-IA-11 · SHOULD** 既定の読む順序に従います：ページの識別 → 現在のステータスまたは例外 → 主たるタスクと主たるアクション → 判断に必要な情報 → 関係、変更、証拠 → 二次的な情報と頻度の低いアクション。
- **D-IA-12 · SHOULD** **タスクの領域ごとに主たるアクションはひとつ**で、それはいちばん破壊的なものではなく、いちばんありそうな次の一歩です（どれだけの重みを持てるかは §9 の「強調は予算」が決めます）。

### 密度とは実効的な情報量であって、面積あたりのコントロール数ではない

余白を詰めると視覚的な密度は上がりますが、実効的な密度は変わりません。無関係なフィールドを取り除き、比較をひとつの場所にまとめると、本当の密度が上がります。

- **D-IA-13 · SHOULD** **ひとつのページで使う密度は、隣り合うふたつの段階まで**にします：初回利用やリスクのある確認には広め、ほとんどのリストや詳細には標準、熟練者向けのワークベンチにはコンパクト。
- **D-IA-14 · MAY** コンテナの内側余白と行の高さは詰めてもかまいません。
- **D-IA-15 · MUST** 読みやすい本文、目に見えるフォーカスリング、ポインターのターゲットの大きさは、密度によって縮みません（§7、§8）。_Proof: browser_

### 入れ物は構造を直さない

- **D-IA-16 · SHOULD** **ビューごとに、文脈上の戻り先はひとつです。** 外側の「チャットに戻る」と内側の「アーティファクトに戻る」を一緒に表示しないでください。
- **D-IA-17 · SHOULD** 詳細ビューは、すぐ上の親に戻ります。
- **D-IA-18 · MUST** 祖先には、ルートの階層か、はっきり名付けたパンくずリストを通してたどり着けるままにします。_Proof: browser_
- **D-IA-19 · SHOULD** フォーカスの戻りや、長く翻訳された行き先の名前も含めて、道のり全体を確かめます。
- **D-IA-27 · MUST** 親に戻ると、フォーカスは元の項目に戻ります。_Proof: browser_
- **D-IA-20 · MUST** テキストが収まらないときは再配置するか、意味のある短い行き先の名前を使います。省略記号やツールチップで、行き先を示す唯一の手がかりを隠すことはありません。_Proof: browser_
- **D-IA-21 · SHOULD** 親の文脈には、ひとつの構成を選びます。冗長な戻るショートカットに別の名前を付けるためだけにパンくずリストを足したり、その戻るコマンドの上にその親を動かないパンくずとして繰り返したりしないでください。

親を通って戻ることで祖先にすでにたどり着けるなら、その道のりがアクセスを保っており、詳細ヘッダーの行をもう一段足す必要はありません。

- **D-IA-22 · SHOULD** 階層そのものがタスクの助けになるときに、パンくずリストを使います。

**モーダルはナビゲーションの層ではありません。**

- **D-IA-23 · SHOULD** コピーできるリンク、履歴、横並びの比較、再読み込みを越えて残る作業が必要なものには、ルートを与えます。
- **D-IA-24 · SHOULD** モーダルは短い確認かひとつのフィールドのために、ポップオーバーやメニューは一時的な文脈のために、開閉行は段階的な開示のために取っておきます。
- **D-IA-25 · SHOULD** **タブが運ぶのは、ひとつの対象の対等なビューです** — その会話、そのチェック、その差分。無関係なモジュールを運ぶことはなく、それはナビゲーションの仕事です。
- **D-IA-26 · SHOULD** 選んだライブラリに適したプリミティブがないなら、既存の意味的な要素とホストのトークンを使います。サポートされていない API を作り出すのではなく、必要な操作を確かめます。

## 検証チェックリスト（UI を出す前に）

- **D-VERIFY-1 · SHOULD** 影響を受ける面、対応するバリエーション、変わった振る舞いに合わせて検査を選びます。リストを満たすためだけに無関係なフローを作らないでください。

リポジトリの CI は、引き続き完全なゲートを実行します。

- **D-VERIFY-2 · SHOULD** 主たるタスクと主たるアクションが、取り違えようのないものになっています。

影響を受けるレイアウト／テーマの変更は、関係する**狭い幅と広い幅**、対応するテーマで動きます（D-INPUT-1）。マウスとタッチの両方が動きます：ドラッグは Pointer Events を使い、`trigger="hover"` にはタップの代替があります（D-INPUT-3、D-INPUT-4）。キーボードと目に見えるフォーカスは D-ACCESS-3 と D-ACCESS-4 が扱います。

- **D-VERIFY-5 · SHOULD** 変わったすべての**状態**（ホバー、アクティブ、フォーカス、無効、読み込み中、空、エラー）を試します。
- **D-VERIFY-7 · SHOULD** 関係する境界ケースを扱います：長いテキスト、大きな数、ホストが対応する文字体系／ロケール。
- **D-VERIFY-8 · SHOULD** 余白はスケールから、文字は役割から、色は意味的なトークンから取ります。
- **D-VERIFY-9 · SHOULD** ホストの当てはまる検査を実行し、実際のブラウザーの証拠を確かめます。
- **D-VERIFY-10 · SHOULD** 文言は §6 に従います。

色だけによる状態の表示は D-ACCESS-2 が扱います。

- **D-VERIFY-12 · SHOULD** 密な面では：主たるモデルはひとつ、骨組みはペイロードではなく問いから選び、どの事実にも正式な置き場所がひとつ（§10）。
