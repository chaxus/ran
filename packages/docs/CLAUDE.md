# packages/docs — the documentation site

VitePress 2.x (alpha) site published to **https://ran.chaxus.com** via Cloudflare Pages.
Bilingual: English under `src/`, Simplified Chinese under `cn/src/`, mirrored 1:1.

Most of what is non-obvious here is not VitePress — it is the SEO/GEO machinery, the
generated pages, and the Service Worker. Read the relevant section before changing any of it;
each carries a failure mode that is silent.

---

## Layout

```
packages/docs/
├── .vitepress/
│   ├── config.ts          # SEO: canonical, hreflang, per-page description, JSON-LD, sitemap
│   ├── common/index.ts    # shared constants + the inline <script> snippets (SW registration…)
│   └── langs/{en,cn}/     # sidebar + nav per language
├── src/                   # English pages
├── cn/src/                # Chinese pages (same tree)
├── public/                # copied verbatim: sw.js, llms.txt, robots.txt, _headers, fonts…
└── bin/build.sh           # vitepress build + llms-full.txt + Service Worker assembly
```

## Build script conventions (`bin/build.sh`)

**It starts with `set -euo pipefail`. Keep it there.** Without it the script's exit code is
whatever the trailing `echo` returns — i.e. **0 even when VitePress failed to compile**. That
happened: a broken markdown page failed the build, `mv`/`cat` then failed on the missing
`sw.js`, and the script still exited 0 printing `service work file paths have been generate`.
Cloudflare Pages reads that exit code; a build that cannot fail publishes stale output while
reporting success.

If you add a step, assume it will be the one that fails.

## Generated files that are committed

| File                            | Generated by             | Notes                                                                                                                                                             |
| ------------------------------- | ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/ranuts/api.md`             | `pnpm -F ranuts doc:api` | The full 332-symbol reference. Regenerate after changing ranuts' public exports — the same command also writes `packages/ranuts/docs/API.md` for the npm tarball. |
| `.vitepress/dist/llms-full.txt` | `bin/build.sh`           | Not committed; rebuilt every time.                                                                                                                                |

`src/ranuts/api.md` and `packages/ranuts/docs/API.md` are in `.prettierignore` **on purpose**:
Prettier rewrites the illustrative snippet `import { /* … */ } from 'ranuts/utils'` into
`import {} from /* … */ 'ranuts/utils'`, moving the placeholder comment outside the braces.
Regenerating is the only source of truth.

Nothing else should write a build timestamp into a tracked source file. There used to be a
`variable/SERVICE_WORK_VERSION.ts` holding `Date.now()`; every build dirtied the working tree,
history collected "update SERVICE_WORK_VERSION" commits, and two builds of the same commit
produced different source trees.

## SEO

`config.ts` already does the following — verify before assuming something is missing:

- **`cleanUrls: true`**, and canonical / hreflang / sitemap all emit extensionless URLs, so
  they match what Cloudflare Pages actually serves (`/foo`, with `/foo.html` 308-redirecting).
  Getting this wrong once pointed ~214 sitemap and canonical URLs at the redirecting form.
- **Per-page `<meta description>` derived from the page's own first prose paragraph**
  (`deriveDescription`) when there is no frontmatter description. Without it all 316 pages
  shared the site-level description.
- **EN/CN `hreflang` alternates, existence-checked** against `siteConfig.pages` so a
  one-language-only page never advertises a 404 counterpart.
- **`og:` / `twitter:` tags**, and `SoftwareSourceCode` JSON-LD on the ranui/ranuts landings.
- The **home page title** is promoted to the full tagline (otherwise it is just `ran`, since
  `title === site title` suppresses the template).

Site copy is written for SEO/GEO. Don't add decorative taglines to the home page.

## AI / GEO surface

Three artefacts, all reachable without JavaScript:

| Artefact            | What                                                                                                                                           | Maintained                                                             |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `public/llms.txt`   | Curated entry map — summary, doc links, entry points, npm/GitHub                                                                               | **By hand.** Refresh when either package's surface changes materially. |
| `llms-full.txt`     | Every `src/` + `cn/src/` markdown concatenated, each block prefixed with its canonical URL                                                     | Generated per build                                                    |
| `public/robots.txt` | Explicitly allows AI crawlers **including training crawlers** (GPTBot, ClaudeBot, Google-Extended, CCBot, Bytespider) plus the sitemap pointer | By hand                                                                |

Both `llms.txt` and `llms-full.txt` are also linked from `<head>` as `rel="alternate"`. That
is a convention, not a spec — agents normally fetch `/llms.txt` directly; the tags are cheap
insurance.

`llms.txt` is the paragraph a model actually ingests as "what is this project". Treat it as
the highest-leverage prose on the site and keep it current — it had drifted to describing a
ranuts that predated i18n, zip, IndexedDB, Worker and bridge support.

## Service Worker (`public/sw.js`)

Assembled at build time: `bin/build.sh` prepends the precache manifest and
`const VERSION = "<timestamp>"` to the file, and `CACHE_NAME = 'chaxus_ran_' + VERSION`.

Three rules, each of which was previously broken:

**1. The URL stays `/sw.js`. Never put the version in the filename.**
The browser updates a Service Worker by re-fetching **the same URL** and byte-comparing. When
the filename carried the timestamp, a returning visitor's registered `sw<old>.js` no longer
existed on the server, so every update check 404'd — the only remaining update path was "user
loads a page and the inline script registers the new filename". A stable URL restores the
browser's own update path (on navigation, and roughly every 24h) _in addition_ to that one.

Version-in-filename is not needed for freshness either: the version lives in the file's
content, so the bytes change every build, which is exactly what the comparison looks at. And
the browser bypasses its own HTTP cache for the SW main script (`updateViaCache` defaults to
`'imports'`), so a stable URL cannot serve a stale script. `public/_headers` additionally
pins `/sw.js` to `Cache-Control: no-cache` so the CDN edge cannot hold a stale copy either.

**2. The `fetch` handler must be a synchronous function that calls `event.respondWith()`.**
`respondWith` is only valid during the synchronous dispatch of the event; an `async` handler
has already yielded at its first `await`. The handler used to be
`async (event) => { cacheFirst(event.request) }` — async _and_ missing `respondWith`. The
result was a Service Worker that intercepted nothing: install dutifully precached the app
shell and no request ever read it, so users paid the download for zero benefit and offline
did not work.

**3. Strategy is per request type.** HTML navigations (`request.mode === 'navigate'`) are
**network-first with cache fallback** — a docs site must not serve yesterday's prose. Build
output is content-hashed and therefore immutable, so everything else is **cache-first**.

`activate` runs `deleteOldCaches()`, which keeps only the current `CACHE_NAME` — that is what
actually evicts the previous deploy's assets, and it is driven by the version inside the file.

## Gotchas

| Pitfall                                                                | Fix                                                                                                                                                             |
| ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A `{{` in markdown (documenting template syntax, say) breaks the build | VitePress compiles every page as a Vue template. Wrap in `::: v-pre` or `<code v-pre>`.                                                                         |
| A bare `<tag>` in prose breaks the build the same way                  | Same cause — an unclosed element. Backtick it. The ranuts API generator escapes these automatically (`escapeAngles`); hand-written pages must do it themselves. |
| Adding a page but it never appears                                     | The sidebar is hand-maintained in `.vitepress/langs/{en,cn}/index.ts`. A page with no entry is reachable only by URL.                                           |
| Editing `src/ranuts/api.md` directly                                   | Generated. Edit the ranuts source JSDoc and run `pnpm -F ranuts doc:api`.                                                                                       |
| Assuming `screenshots/`-style generated output is ignored by tooling   | Generated artefacts must be added to `.prettierignore` explicitly, or `lint:prettier` goes red the first time someone runs the generator.                       |
| Expecting the CN tree to update itself                                 | `cn/src/` is a manual mirror of `src/`. New pages need both.                                                                                                    |
