# Changelog — 2026-08-08

## packages/ranui — `<r-form>` redesign + native reset/validation for form fields

Started from a docs complaint ("every `<r-form>` demo looks stuck together") and ended up
finding that `<r-form>` never actually collected field values in a real browser, for its
entire history.

### The layout bug

All three `<r-form>` demos slotted fields into the shadow-DOM `<form class="r-form">` through
a named slot (`r-form_content`), always via a single wrapper `<div slot="r-form_content">`.
`.r-form { gap: ... }` only ever had one child (the wrapper) to lay out, so `gap`/`grid` rules
never reached the actual fields.

### The real bug underneath it

Fixing the layout meant reading `Form.connectedCallback` closely, which turned up a stale
snapshot: `new FormData(this._form)` was computed **once, at connect time**, and the `submit`
listener just re-serialized that frozen object forever — `value` never reflected what the user
actually typed.

Fixing _that_ meant writing a real test for it, which is where this stopped being a small fix.
jsdom cannot flatten slots, so the existing unit test only ever asserted against an **empty**
form (`'{}'`) — a test that would pass whether or not FormData collection ever worked at all.
Writing a real-browser (Playwright) test to actually prove the fix surfaced something bigger:

```
new FormData(r-form's internal <form>) → {} always, even for a plain slotted <input>
input.form → null
```

A `<form>` hidden inside shadow DOM can **never** become the form owner of light-DOM children,
even ones rendered through a `<slot>` — the HTML "form owner" algorithm walks the real DOM
ancestor chain, which does not cross into shadow roots. This is not a bug in `<r-form>`'s code;
it's a fundamental limitation of "shadow-DOM `<form>` + slot" as an architecture — one this
component has had since it was written. The `<r-form>` doc's own "Serialized Value" example,
claiming `form.value` would come back `'{"email":"you@example.com"}'`, was apparently never
verified in a real browser.

### The fix: `<r-form>` no longer owns a `<form>`

Verified the alternative empirically first (a minimal custom element with a shadow `<slot>`
wrapping a light-DOM `<form>`): `input.form` is set, `FormData` collects it, and `submit`/`reset`
bubble through the custom element host correctly. So `<r-form>` now:

- Requires a real `<form>` as a child — it does not build one. Shadow DOM is reduced to a
  single passthrough `<slot>` plus `::slotted(form) { ... }` for the default layout (still
  overridable via `--ran-form-*` CSS variables or `sheet`, same convention as every other
  component).
- Listens for `submit`/`reset` bubbling from that `<form>` on `this` (the host) — no need to
  locate the form explicitly, `event.target` is always the form that submitted.
- Calls `event.preventDefault()` on submit. This was never reachable before (the old submit
  listener was on a `<form>` nobody could actually submit through user interaction in a way
  that collected data), so the fact that a real `<form>`'s default submit **navigates the
  page** was never handled. The Playwright test caught this immediately once the form owner
  bug was fixed — clicking submit navigated away and destroyed the test's execution context.

New usage: `<r-form><form>...fields...</form></r-form>` instead of
`<r-form><div slot="r-form_content">...fields...</div></r-form>`. Breaking, pre-1.0 alpha.

### Reset + validation for the fields themselves

`r-input`, `r-checkbox`, `r-select` were already form-associated (`attachInternals()` +
`setFormValue()`), which only ever covered `FormData` collection. None implemented
`formResetCallback` (native `form.reset()` was a silent no-op on them) or
`ElementInternals.setValidity` (a `required` field was invisible to
`form.checkValidity()`/`:invalid`, despite `required` being forwarded to the _inner_ shadow
`<input>`, which the outer form can't see). Added both:

- `formResetCallback()` restores the pre-interaction value/checked state (a snapshot captured
  once on first `connectedCallback`, since none of these components otherwise distinguish
  "current value" from "default value" the way native `<input>` does via `defaultValue`).
  `r-select` reuses its existing `defaultValue` attribute instead of a new snapshot. Restoring
  on reset must work even while `disabled` (native `<input disabled>` still updates on
  programmatic assignment — only *user* interaction is blocked), so the `value` setters on
  `r-input`/`r-select` no longer gate assignment on `!disabled`.
- The `required`/`setValidity` sync (`updateRequiredValidity` in the new `utils/a11y.ts`, shared
  by all three instead of hand-duplicated) calls `setValidity({valueMissing:true}, message,
  anchor)` when `required` and empty, `setValidity({})` otherwise or when `disabled` (disabled
  controls never block validation, matching native semantics) — and mirrors the same state into
  `aria-required`/`aria-invalid` on the host for assistive tech. Passing the anchor turned up a
  wrong assumption along the way: `setValidity`'s anchor does *not* have to be a shadow-DOM
  descendant of the host — the host itself works fine as its own anchor in a real browser
  (verified directly), which is what `r-checkbox`/`r-select` now pass, since they're the
  focusable/tabbable element, not any of their internal shadow parts.
- `r-checkbox` and `r-select` gained a `required` property/attribute — neither had one before
  (`r-input` did). All three gained `checkValidity()` / `reportValidity()` / `validity` /
  `validationMessage` passthroughs.
- All `setValidity`/`checkValidity`/`reportValidity` calls are optional-chained
  (`this._internals?.setValidity?.(...)`) — jsdom's `ElementInternals` stub omits these methods
  entirely (it does implement `setFormValue`, oddly), so this is required for unit tests to run
  at all, not just defensive.

Because the underlying `<form>` is now real, none of this needed any code in `<r-form>` itself:
a `<button type="submit">` inside an invalid `<r-form>` is blocked by the browser's own
constraint-validation pass and shows its native tooltip anchored where the component pointed
it; `<button type="reset">` actually clears fields now. Verified end-to-end with a new
Playwright spec (`test/e2e/form.spec.ts`) — deliberately real-browser, not jsdom, since jsdom's
lack of slot flattening is exactly what let the original bug hide for this long.
